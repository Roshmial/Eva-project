# Цель

Дать агенту рабочую региональную точку выхода с минимальным количеством новой инфраструктуры и с честной диагностикой ограничений: CGNAT, тип IP, доступность узла 24/7, anti-bot и различие между домашним и датацентровым egress.

# Сначала определить контур

1. Проверить текущий внешний IP и географию узла, где работает агент.
2. Уточнить, нужна ли постоянная точка выхода 24/7 или достаточно временной/ручной схемы.
3. Спросить, что уже есть у пользователя:
   - домашний роутер;
   - домашний компьютер, NAS или мини-PC;
   - белый IP или только серый WAN;
   - готовый VPS, proxy или VPN.
4. Для пользователя с local-first предпочтением сначала пытаться использовать уже имеющийся домашний контур, а не сразу уводить решение в новый облачный сервер.

# Диагностика домашнего контура

1. Проверить WAN IP на роутере.
2. Если WAN IP в диапазоне `100.64.0.0/10`, это CGNAT: прямой входящий VPN на роутер почти наверняка недоступен без белого IP.
3. DDNS сам по себе CGNAT не лечит: при private WAN он не делает роутер доступным извне.
4. Если роутер умеет VPN Server (WireGuard, OpenVPN, IPSec), это полезно только при белом IP или другой схеме достижимости.
5. Если дома есть только Android или другое ограниченное устройство, не считать его полноценной точкой для устойчивого туннеля. Нужен обычный компьютер, NAS или мини-PC.

# Выбор сценария

## Сценарий A — быстрый тест без новой инфраструктуры

Использовать домашний компьютер как временный exit node через Tailscale.

Когда подходит:
- есть домашний ПК;
- он может быть включён на время проверки;
- белого IP нет;
- задача — proof of concept, а не 24/7 production.

## Сценарий B — чистое домашнее решение

Заказать у провайдера белый IPv4 и поднимать VPN Server на домашнем роутере или хосте.

Когда подходит:
- нужен более устойчивый домашний egress;
- провайдер даёт белый IP за вменяемые деньги;
- пользователь готов поддерживать домашний контур.

## Сценарий C — отдельный региональный VPS или proxy

Использовать облачный узел только если домашний контур неудобен, а доступность 24/7 важнее local-first экономии.

# Tailscale как быстрый мост

## Что важно заранее

- Для тестового сценария обычно хватает бесплатного плана Tailscale.
- Tailscale полезен именно тем, что работает за NAT и CGNAT через исходящие подключения.
- Он не решает проблему выключенного домашнего ПК: когда ПК выключен, региональная точка выхода исчезает.

## Домашний Windows-PC как exit node

1. Установить Tailscale.
2. Авторизоваться в tailnet.
3. Выполнить в PowerShell от имени администратора:

`tailscale up --advertise-exit-node`

4. Проверить:
   - `tailscale status`
   - `tailscale debug prefs`
5. В `tailscale debug prefs` признаком правильной локальной настройки будет:

`"AdvertiseRoutes": ["0.0.0.0/0", "::/0"]`

6. После этого обязательно проверить админку Tailscale: узел может быть настроен локально, но ещё не одобрен или не распознан как рабочий exit node другими узлами tailnet.

## Важная ловушка

Даже если на Windows `tailscale debug prefs` показывает `AdvertiseRoutes` для `0.0.0.0/0` и `::/0`, другой узел может всё ещё отвечать `node ... is not advertising an exit node`.

Тогда нужно:
1. повторно выполнить `tailscale up --advertise-exit-node`;
2. проверить Tailscale admin console на предмет approve или enable exit node;
3. только после этого пробовать использовать узел как exit node с другой машины.

# Непривилегированный Linux-сервер: portable userspace Tailscale

Если на сервере нет root или `sudo` требует пароль, можно поднять временный Tailscale-клиент без системной установки.

Шаги:
1. Скачать официальный архив `tailscale_<version>_amd64.tgz` с `pkgs.tailscale.com`.
2. Распаковать его в домашний каталог.
3. Запустить `tailscaled` в userspace-режиме, например с локальным SOCKS5 и HTTP proxy listener.
4. Использовать отдельный socket-файл.
5. Выполнить `tailscale up` и получить одноразовый auth URL.
6. После авторизации проверять `tailscale status` через этот socket.

Это хороший способ для proof of concept, когда нельзя или не хочется менять системный сетевой контур сервера.

# Проверка результата

1. На сервере проверить `tailscale status`.
2. Убедиться, что видны оба узла: сервер и домашний ПК.
3. Если exit node одобрен, назначить домашний ПК как exit node и перепроверить внешний IP и географию.
4. Проверять не только соединение, но и реальную пользовательскую цель: открываются ли проблемные сайты из нужного региона.

# Практические выводы

- Не путать «узел виден в tailnet» и «узел реально работает как exit node».
- Не путать «российский IP» и «успешный обход anti-bot»: часть сайтов всё равно режет automation и датацентровые контуры.
- Для local-first пользователя сначала делать быстрый домашний proof of concept, а уже потом решать, нужен ли отдельный VPS.
- Если нужен устойчивый 24/7 egress, временная схема через домашний ПК — это проверка гипотезы, а не финальная архитектура.
