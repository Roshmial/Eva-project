# Когда использовать

Связанные reference-файлы:
- `references/hermes-web-mvp-chat-jobs-polish.md` — lessons learned for chat sidebar limits, embedded help, job-driven chats, admin-only job params, and smoke-test rewrites after UI/contract changes.
- `references/profile-tabs-thread-recipients-and-safe-patching.md` — паттерн для жёстко заданного пользователем UI-pass: ровно заданные вкладки/таблицы/плашки, thread-based recipients поверх user-owned backend и безопасная доводка больших `index.html + app.js` через адресные патчи.
- `references/dom-sync-null-guards-and-browser-smoke.md` — практический паттерн для рассинхрона `index.html`/`app.js`: null-safe DOM guards, секционный patching и порядок live browser-smoke после крупных UI-перестроек.


Используй навык, когда пользователь просит:
- "пройтись по интерфейсу"
- убрать перегрузку, дубли, тёмную тему, тяжёлые карточки
- сделать UI "под ключ", а не дать только рекомендации
- улучшить русский пользовательский слой

## Дополнительные ловушки для local-first cleanup

- Если меняешь UI-контракт, в том же проходе обновляй smoke-сценарии и backend smoke-тесты. Типовые ловушки: убрали пункт из верхней навигации, но browser smoke всё ещё ищет старый `data-screen`; переключили jobs API с read-only на writable, но тесты всё ещё ждут `400` вместо успешного create/update.
- Если в проекте уже есть локальный jobs engine, ACL, recipients и runs, не наращивай поверх него внешний read-only bridge как основной контур UI. Сначала верни frontend и публичный API на существующую local-first модель, а bridge оставляй только как интеграционный слой там, где он действительно нужен.
- Для chat→cron UX проверяй не только форму, но и полный рабочий путь: создание draft из текущего чата, перенос prompt/context, create/edit job, subscribe/unsubscribe, recipients и повторный smoke после смены UI-контракта.

- улучшить русский пользовательский слой во frontend
- привести local-first admin/chat UI к более зрелому продуктному виду

Особенно уместно для MVP с большим количеством форм, админских блоков и настроек профиля.

# Цель

Не просто перекрасить интерфейс, а уменьшить когнитивную нагрузку:
- один смысл -> одно место редактирования
- вторичная информация -> тише визуально
- служебные/технические формулировки -> в нормальный русский
- формы и настройки -> без лишнего количества одновременно видимых параметров

# Основные принципы

1. Сначала упростить информационную архитектуру, потом полировать стили.
2. Не лечить дубли косметикой: если профиль/стиль/настройка редактируются в 2-3 местах, оставить один основной путь.
3. Для рабочих text-heavy интерфейсов по умолчанию предпочитать светлую тему.
4. Уменьшать количество карточек, плашек, chips и вложенных контейнеров.
5. Делать русский пользовательский слой взрослым и спокойным: без жаргона, без англицизмов "для красоты", без внутренних инженерных формулировок.
6. После правок обязательно подтверждать не только синтаксис, но и живую работоспособность.

# Порядок работы

## 1. Аудит структуры

Проверь:
- какие сущности дублируются (например, профиль, стиль ответа, summary, modal, quick action)
- какие блоки конкурируют за внимание на одном экране
- где есть слишком много параметров, видимых без необходимости
- где вторичные действия стоят рядом с главным действием и засоряют интерфейс

Критические сигналы:
- один и тот же параметр можно менять в нескольких местах
- одинаково тяжёлые карточки для primary и secondary контента
- история, системные данные и CRUD смешаны на одном визуальном уровне

## 2. Упрощение информационной архитектуры

Применяй правила:
- редактирование одной сущности оставлять в одном месте
- sidebar держать коротким: навигация + минимум контекста
- topbar держать компактным: раздел + 1 shortcut + статус
- help/system/history не должны конкурировать с основным рабочим сценарием
- редкие/служебные параметры уводить в "Дополнительно" или вторичные секции
- если backend поддерживает только просмотр и 1-2 безопасных действия, UI должен честно показывать read-only/operations режим, а не декоративное create/edit-обещание
- допустимые локальные улучшения без backend-поддержки помечать явно: например, browser-local ярлык, локальный фильтр, локальная группировка

## 3. Визуальный cleanup

Для рабочего local-first web UI по умолчанию:
- светлый фон
- белые карточки
- мягкие бордеры
- спокойный один акцентный цвет
- меньше теней
- меньше радиусов и "пухлости"
- меньше крупных плашек

Стремись к тому, чтобы иерархия строилась через:
- заголовок
- подпись
- отступ
- типографику

а не через постоянные коробки внутри коробок.

## 6. Проверка product/backend truth перед UX-решением

Для экранов задач, админки и других operational-сущностей сначала проверь, какой контур уже существует в проекте на самом деле:
- полноценный local-first engine в своей БД и backend-модели;
- урезанный read-only bridge к внешнему контуру;
- смешанный режим, где ядро уже локальное, но UI/API оставлены в safe-view фасаде.

Правило выбора:
- если в проекте уже есть полноценный local-first engine с ownership, ACL, recipients, runs и update-path, по умолчанию возвращай UI/API на него;
- не закрепляй read-only фасад только потому, что он уже выведен во frontend;
- внешний bridge оставляй только если локальный контур реально не покрывает нужный сценарий.

Практический сигнал, что надо переключать экран на локальный engine, а не полировать фасад:
- в backend уже есть таблицы/модели вида `jobs`, `job_acl`, `job_recipients`, `job_subscriptions`, `job_runs`;
- уже существуют функции create/update/execute/visibility checks;
- а frontend при этом всё ещё показывает «безопасный просмотр» или отключённый create/edit.

В такой ситуации UX-правильное решение — не улучшать текст про ограничения, а вернуть реальный CRUD/ownership/recipients path на существующий local-first контур.


Минимум:
- syntax check JS (для браузерного JS используй нативную проверку вроде `node --check`, а не Python-инструменты)
- syntax check вспомогательных Python frontend/server файлов, если они есть
- поиск по остаткам старых id/handlers/removed flows
- проверка на duplicate DOM ids
- live HTTP check frontend/backend, если локальный запуск доступен
- smoke/regression tests backend, если frontend завязан на backend contracts

Если пользователь просит «проверь всё», «заверши проверку» или «запиши выводы», закрывай задачу полным verification bundle:
- backend smoke/regression;
- нативный JS syntax check;
- Python syntax check для backend/frontend-serve файлов;
- live HTTP check backend/frontend;
- проверка duplicate DOM ids;
- быстрый triage-проход для отделения runtime/auth/bootstrap-проблем от продуктовых дефектов;
- если backend smoke падает на `ModuleNotFoundError` или аналогичном локальном import-path сбое, перепроверь запуск из канонического service/workdir перед выводом о регрессии;
- короткий финальный статус с явным разделением: что подтверждено технически, что подтверждено живым UI, а что упало только из-за launch/cwd-контура.

После такого closeout pass по крупной теме фиксируй итог в действующий `decision-log.md`, а не оставляй вывод только в сообщении.

Нельзя считать задачу завершённой только по визуальному замыслу или только по патчу файла.

Если cleanup уже доведён до рабочего состояния, сделай ещё и aftercare-закрытие:
- вынеси временные e2e/probe-скрипты из `tmp/` в канонический project-path (`scripts/`, root `package.json`, README);
- очисти `tmp/` от одноразовых probe/debug-хвостов и старых локальных `node_modules`;
- оставь в `tmp/` максимум `.gitkeep` и короткий README с правилом, что постоянные smoke-сценарии там не живут;
- после cleanup обязательно повторно прогоняй smoke, чтобы подтвердить, что уборка ничего не сломала.

# Чек-лист решений

Во время cleanup отдельно ответь себе:
- Удалён ли дубль профиля/настроек?
- Остался ли один главный путь редактирования?
- Не перегружен ли composer вторичными действиями?
- Не слишком ли тяжёлый admin screen?
- Нет ли giant cards / giant empty states / card-inside-card без причины?
- Качественный ли русский на пользовательском слое?
- Подтверждён ли runtime после удаления старых modal/handler flows?
- Не остались ли JS-ссылки на удалённые quick actions, кнопки или DOM id после cleanup?
- Сделан ли повторный UX/UI review уже после runtime-проверки, а не только до правок?
- Проверен ли повторный UX/UI review не только по внешнему виду, но и по функциональным сценариям?
- Если продуктовый сценарий опирается на артефакты, документы или логи, есть ли в основном рабочем контуре нормальная загрузка файлов?
- Если загрузка файлов уже нужна, встроена ли она в главный composer/рабочий поток, а не вынесена в отдельный тяжёлый экран или служебную модалку?
- Видит ли пользователь состояние файлов до и после отправки: выбраны, удалены из очереди, обработаны, сохранены без извлечения текста, ошибка обработки?

# Функциональный UX review для рабочих chat/UI-сценариев

После визуального cleanup отдельно проверь главный рабочий сценарий как продуктовый поток, а не как набор блоков.

Для chat-first/local-first UI это обычно означает:
- основной вход должен оставаться единым: текст, контекст и вложения живут в одном composer;
- если появляются файлы, пользователь должен видеть выбранные файлы до отправки и уметь убрать лишние;
- ограничения надо показывать заранее рядом с действием: сколько файлов можно приложить, какой лимит размера, какие форматы реально разбираются;
- в ленте сообщений вложения лучше показывать компактными attachment-card, а не вываливать сырой технический текст;
- extracted text нужен прежде всего для backend/agent flow, а не как огромный кусок UI;
- для неподдерживаемых или неразобранных форматов интерфейс должен честно говорить, что файл сохранён без извлечения текста, а не создавать ложное ощущение полной обработки.
- для cron/jobs/admin-экранов полезно разделять: реальное backend-имя сущности, более читаемое визуальное имя и источник этого визуального слоя; если имя локальное, это должно быть явно подписано как browser-local, а не как серверное редактирование.
- если экран задач начинает собирать сущности из нескольких источников, не строй новый параллельный контракт без необходимости: сначала проверь, нет ли уже готового bridge/adapter, который нормализует внешний контур в текущую web-модель. В UI и API явно протаскивай `source_of_truth`/`read_only`, не хардкодь подпись источника в detail/list и не обещай редактирование там, где источник фактически read-only.
- если backend даёт только run/pause/resume/read, это и должно быть главным UX-сценарием экрана задач; создание, ACL и полное редактирование нельзя имитировать полуживыми формами.
- post-login boot не должен держать весь интерфейс заложником поздних secondary/admin-запросов: базовый app shell должен открываться после обязательного минимума, а jobs/admin/history/reference-данные лучше догружать отдельно с мягкой деградацией через banner/status.
- в профиле summary лучше собирать в 2-3 компактных смысловых tiles, а не в тяжёлые card-inside-card блоки;
- если пользователь прямо просит «отдельные плашки внутри профиля», не ограничивайся одной общей summary-карточкой: раздели экран минимум на отдельные смысловые блоки уровня «кто вы для системы», «как отвечать по умолчанию», «файлы и повторное использование»;
- если пользователь задаёт точную IA, соблюдай её буквально, а не «примерно похоже»: например, «ровно 3 вкладки», «таблица, а не карточки», «warning-плашка до открытия диалога». Такие требования надо сначала закрепить в DOM/разметке и названиях секций, а затем в том же проходе синхронизировать `app.js`-state, render-функции и обработчики; нельзя считать задачу почти готовой только по HTML/CSS-каркасу;
- если пользователь просит вынести информационные плашки из ленты чата и сделать их постоянной частью вкладки, трактуй это как изменение IA экрана, а не как косметику: плашки должны жить в верхнем layout экрана, отдельно от message feed, и проверяться вместе с `switchScreen`, `loadThread`, scroll-логикой и composer state;
- если пользователь при этом отдельно просит, чтобы такие плашки не «прилипали» при прокрутке, не полагайся на визуальное расположение блока: явно проверь/сними `position: sticky`, унаследованные sticky-классы и поведение контейнера прокрутки; для intro/help/policy-блоков на chat-screen по умолчанию нужен обычный flow, а не sticky-header;
- при правках scroll-поведения чата не смешивай два разных сценария: существующий чат по умолчанию открывается внизу, у последнего сообщения; пустой/новый чат и явное действие `Вверх` — это отдельные сценарии с прокруткой к началу; после переноса плашек вне ленты заново проверь связку `loadThread` → `renderMessages(...)` → `switchScreen('chat')`;
- если в сообщениях есть status badge внутри пользовательского bubble, проверяй контраст не только на белом фоне, но и на синем/акцентном фоне user-message: зелёный on blue легко становится нечитаемым; для статусов вроде `Текст извлечён` по умолчанию лучше делать отдельный более контрастный variant, а не переиспользовать мягкий success-chip;
- если пользователь отдельно указывает, что не нужен специальный action-кнопочный путь вроде «Сделать cron из чата», убирай не только кнопку из HTML, но и весь связанный JS-path (`els`, listeners, helpers, secondary prompts). Для chat-first UX главный путь через обычный диалог важнее отдельной дублирующей quick action;
- если для chat-first интерфейса нужна policy/warning-плашка для всех пользователей, по умолчанию делай её backend-driven и управляемой из админки: enabled/disabled + редактируемый текст, отданный через bootstrap/admin endpoints, а не жёстко зашитый текст только во frontend;
- для job-driven chat UX допустим полезный компромисс: во frontend пользователь выбирает чаты/контуры, а backend уже переводит это в owner/user-модель, если реальные job-thread сущности по-прежнему принадлежат пользователям. Это лучше, чем снова тащить в UI прямой список users, когда пользователь мыслит задачами через чаты;
- в списке пользовательских файлов полезен отдельный meta-блок над списком: сколько файлов показано и что делают текущие фильтры;
- в админских справочниках шумные payload/history-данные лучше держать в `details`, а на верхнем уровне показывать только краткую сводку по датасету и компактные item-card.
- если пользователь отдельно просит «проверь, что файлы приходят в чат от Hermes», этого нельзя закрывать только по экрану `Мои файлы`: нужен живой сценарий `composer -> attach -> send -> attachment в сообщении -> повторная видимость в профиле`.

- если пользователь просит переработать admin overview под продуктовый, а не технический взгляд, по умолчанию строй диаграммы как time-series: по горизонтали дата/время, по вертикали количество; агрегацию делай переключаемой минимум между день/неделя/месяц, а не заменяй это статическими KPI-плашками или декоративными progress-bar;
- если пользователь потом просит упростить `Управление -> Обзор`, трактуй это как правку информационной архитектуры, а не как скрытие данных «на время`: ненужные summary-карточки и обзорные таблицы удаляй из DOM и из `renderAdmin()`, а не просто прячь CSS-ом;
- если в chat-first/local-first продукте запрос уже явно задаёт внешний источник (`из интернета`, `по открытым источникам`, URL, `внешний обзор`) и ожидает dashboard/result, не заставляй такой сценарий сначала проходить через local-only clarification только из-за дефолтного `local_first`: правильный cleanup-pass должен доводить policy-switch внутри существующего dashboard-flow так, чтобы explicit external intent сразу попадал в global/web path;
- такой фикс нужно делать внутри уже существующего route/policy переключателя, а не плодить ещё один phrase-level special route рядом с dashboard/collection логикой;
- после удаления overview-блоков обязательно добавляй null-guards для старых `els.admin...` ссылок и вычищай больше неиспользуемый render-код, иначе admin screen легко ломается на обращении к уже удалённым контейнерам;
- для такого упрощения overview целевое состояние должно быть буквально подтверждено в live runtime: на экране остаются только нужные KPI/графики/сигналы, а удалённые блоки действительно исчезают из snapshot/browser-приёмки;
- для time-series overview сначала подтверждай backend-контур отдельно от браузера: authenticated `day/week/month` endpoint должен отдавать `200` и осмысленные bucket'ы до live UI-приёмки; если видишь `404`, сначала проверь stale process / не тот runtime на порту, а не объявляй маршрут отсутствующим;
- если после добавления endpoint получаешь `500`, сначала смотри live log текущего backend-процесса и только потом правь frontend: для таких pass'ов типовая проблема — не визуальный баг, а старый handler или несовместимый helper в свежем route;
- если пользователь просит «оставить только admin», сначала используй поддержанный admin/API-path для soft-delete non-admin пользователей; физическую зачистку через прямой SQL делай только вторым шагом и только после подтверждения live DB path и schema, иначе легко чистить не тот файл или не ту схему;
- для operational DuckDB в этом контуре не предполагай default schema: сначала проверь, не лежат ли таблицы под `app.*`; если direct SQL по `users`/`sessions` говорит, что таблиц нет, это может быть не пустая БД, а schema-qualified layout, и cleanup надо писать как `app.users`, `app.sessions` и т.д.
- если browser-приёмка тормозит или даёт timeout, не считай backend-неготовность доказанной: сначала закрывай API verification и process truth, а уже потом возвращайся к живому UI.

Предпочтительный local-first паттерн:
- frontend показывает очередь файлов и статусы;
- backend сохраняет файлы локально в data/workspace контуре и кладёт метаданные в сообщение;
- поддерживаемые форматы дают извлечённый текст в основной агентный контекст;
- новая инфраструктура не добавляется без явной необходимости.

# Практические pitfalls

## 0. Не закрывай pass до фактического тестирования

Если пользователь после внедрения правок говорит по смыслу «сначала надо протестировать», это не формальность и не просьба о красивом summary.

Правило:
- не помечай verification как завершённый;
- не закрывай все TODO как completed;
- не фиксируй тему в `decision-log.md` как окончательно закрытую до живого smoke по основным потокам.

Даже если синтаксис, backend smoke и HTTP readiness зелёные, это ещё не равно подтверждённому UI-flow.

Минимум для closeout после такого уточнения пользователя:
- реальный вход в UI;
- основной пользовательский сценарий;
- проверка того места, которое только что менялось (например, upload/reuse/admin switching);
- честная фиксация blocker, если живой сценарий не пройден.

Дополнительное правило для user-driven UI cleanup:
- после каждого крупного пакета сверься не только с собственным списком работ, но и с исходным списком требований пользователя пункт за пунктом;
- не считай задачу закрытой, если конкретный пользовательский дельта-запрос («админка изменилась», «кнопка появилась», «метрика видна», «название перестало плавать») не подтверждён отдельно;
- зелёные smoke/triage не заменяют проверку продуктовых дельт, которые пользователь явно называл.

## 1. Cleanup без runtime-дочистки

Если browser/e2e-визуальная проверка тормозит или flaky, не останавливайся на этом месте. Доведи техническую верификацию до конца по лестнице: JS syntax check, Python syntax check, smoke/API сценарий, HTTP readiness frontend/backend. В ответе честно разделяй: что подтверждено технически, а что осталось только без визуального pass.

## 2. Attachment-only модель файлов

Если продукт уже движется к пользовательскому контуру `Мои файлы`, не оставляй файл только как вложение одного сообщения. Следующий cleanup-pass должен проверять reuse файлов из профиля, фильтры/поиск, статусы извлечения и отсутствие дублирования между user text и автоматически собранным attachment-context в чате.

## 3. Cleanup без runtime-дочистки

Если убираешь визуальный дубль действия (например, quick action в topbar при сохранении основного пути через sidebar/profile screen), не останавливайся на HTML/CSS.
Обязательно проверь:
- event listeners в JS;
- обращения к удалённым `id` и `querySelector`;
- screen switching и secondary shortcuts;
- живой `navigate -> snapshot -> console` сценарий после правок, если UI проверяется через Hermes browser tools.

Иначе легко получить косметически чистый интерфейс с мёртвыми обработчиками или неполной browser-приёмкой.

## 4. Ложная редактируемость на read-only backend

Если backend для сущности поддерживает только просмотр и ограниченный набор безопасных операций, нельзя оставлять в UI декоративные create/edit-paths "на будущее".

Правило:
- сначала проверь реальные API-возможности;
- затем перестрой экран под честный сценарий: список, detail, run/pause/resume, safe actions;
- неподдержанные операции либо убирай, либо заменяй на явное пояснение, где это делается на самом деле;
- локальные browser-only улучшения допустимы, но должны быть явно отделены от серверного состояния.

Хороший паттерн для задач:
- compact list;
- detail справа;
- отдельный блок описания;
- тяжёлые параметры под `details`/"Показать всё";
- явная подпись, если визуальное имя хранится только локально в браузере.

## 6. Smoke flaky после UI-пакета

Если автоматический UI smoke после нового UI-пакета падает, не объявляй сразу ни "реальную регрессию", ни "тест сломан".

Сначала раздели три вещи:
- продуктовый дефект в реальном UI;
- хрупкость ожидания/тайминга smoke-сценария;
- отдельный runtime-шум browser/Playwright-контура.

Минимальный порядок:
- syntax check;
- backend/API smoke;
- проверка, что smoke вообще ходит в свежий runtime, а не в старый процесс на локальных портах;
- при необходимости перезапуск реального backend/frontend контура, который обслуживает `8788/8790` или другие канонические localhost endpoints проекта;
- живой browser-проход по изменённому сценарию;
- только потом корректировка smoke-скрипта.

Если UI smoke ловит 404/старый контракт на уже исправленном endpoint, сначала проверь не код, а live-process truth: какой именно backend сейчас слушает порт, не висит ли старый процесс, и не надо ли перезапустить текущий local runtime.

В финальном статусе явно пиши, что именно подтверждено вручную в живом UI, а что пока остаётся хвостом автоприёмки.

## 7. Большие HTML/JS-экраны: сначала точечная синхронизация, потом verification

Для local-first MVP на ванильных `index.html + app.js` не делай крупный cleanup как «массовую перепись всего файла», если экран уже живой и связан множеством `id`, `data-*` и render-функций.

Безопасный порядок:
- сначала перечитай нужные блоки разметки и JS-точки входа;
- затем вноси адресные патчи по секциям, а не тотальный rewrite;
- если пользователь дал точный список UI-дельт, преврати его в checklist по DOM-элементам, текстам, секциям и обработчикам;
- после смены HTML-каркаса сразу доводи связанные JS-функции: `render*`, `set*Section`, listeners, summary helpers, scroll handlers;
- отдельно проверь карту DOM-ссылок `els`: если в разметке удалён или переименован блок, старое безусловное `innerHTML`/`classList`/`value` обращение даёт ложный runtime-defect уже после удачного рендера других секций; для вторичных admin/history/reference-блоков по умолчанию добавляй null-guards, если элемент может отсутствовать в новой IA;
- только потом запускай smoke/runtime.

Практические сигналы, что нельзя останавливаться на HTML/CSS:
- вкладки уже переименованы/переставлены в DOM, но `state` и `switch`-логика ещё старая;
- контейнер уже переведён под таблицу, но `render...()` всё ещё рисует карточки/список;
- в HTML уже вернули placeholder блока, но `render...()` его не наполняет;
- copy в интерфейсе уже сменили с user-based на chat-based, а payload/summary helpers всё ещё работают в старой терминологии;
- browser snapshot уже показывает рабочий экран, но поверх него висит banner-ошибка из-за одного старого secondary DOM-hook. В такой ситуации сначала устрани конкретную null-ссылку и перезайди в экран, а не объявляй весь pass сломанным.

Типовая ловушка: объявить pass «почти готовым» после удачного HTML-патча. Для такого стека это часто означает именно опасную половину работы — визуальный каркас уже сменился, а поведение ещё нет.

Дополнительная ловушка второго UI/UX-pass:
- если экран уже правился несколькими адресными патчами, не опирайся на старые частичные чтения крупных файлов как на истину для следующего шага;
- перед новым блоком правок перечитай целиком актуальный render-блок и связанный backend-контракт хотя бы на уровне нужной секции (`renderAdmin`, `renderMessages`, jobs/admin endpoints, DOM ids);
- иначе легко получить ложное ощущение прогресса: `index.html` уже новый, `app.js` наполовину старый, backend payload третий, и ошибка выглядит как UX-дефект, хотя это обычный рассинхрон контракта.

# Для пользователя Миши

Если работаешь для Миши:
- не ограничивайся аудитом; при запросе "правь всё и сразу" нужно реально вносить изменения
- светлая тема предпочтительнее тёмной
- минимизируй дубли смыслов
- русский на фронте должен быть человеческим и аккуратным
- после cleanup обязательно делай повторный UX/UI review, а не только техническую проверку
