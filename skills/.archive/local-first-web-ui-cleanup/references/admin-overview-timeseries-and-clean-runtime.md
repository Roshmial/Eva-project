# Admin overview time-series и clean runtime

Когда полезно:
- второй или третий UI/UX pass по local-first web admin screen;
- пользователь просит сделать `Обзор` продуктовым и просит именно диаграммы, а не только KPI;
- после cleanup есть риск смотреть не в тот runtime или не в ту БД.

Ключевые уроки:

1. Для `Обзор` в web-first админке безопасный default — time-series, а не набор статических плашек.
- По оси X: дата/время.
- По оси Y: количество.
- Минимальный переключатель агрегации: `day / week / month`.
- Типовые web-метрики: новые пользователи, новые чаты, сообщения, job runs, сессии.

2. Если browser-проверка и API-проверка расходятся, сначала проверяй runtime truth.
- Канонический frontend origin может отличаться от временного static server origin.
- Backend может разрешать CORS только для одного origin.
- Пустой или «старый» результат API часто означает не баг логики, а старый процесс на порту или проверку через неканонический origin.

3. Для local-first cleanup нельзя считать найденный локальный `.duckdb`/`.sqlite` файл автоматически активным source of truth.
- Сначала сверяй, что именно текущий backend процесс реально обслуживает runtime.
- Только после этого чисти users/demo data напрямую.

4. После UI cleanup по админке продуктовая чистота данных важна почти так же, как код.
- Нужно отдельно проверять users, files, operations/history, а не только references.
- Иначе `Обзор` и таблицы выглядят рабочими, но показывают test/smoke-мусор и искажают KPI.

Мини-checklist:
- диаграммы реально рендерятся в живом UI;
- переключение day/week/month реально меняет buckets;
- проверен канонический frontend origin;
- проверено, что backend на нужном порту — актуальный процесс;
- перед cleanup users определён живой source of truth;
- после cleanup повторно проверены KPI, users, files, operations.
