# Upload-first UX в local-first web UI

Контекст класса задач:
- в существующий local-first web MVP добавляется загрузка файлов;
- нельзя ограничиваться только визуальной чисткой интерфейса;
- UX нужно проверять по функциональному сценарию целиком: выбор файла, отправка, отображение результата, повторная доступность пользователю.

Ключевой урок
- Если файл участвует в пользовательском рабочем процессе, его нельзя проектировать только как вложение одного сообщения.
- Минимально зрелая модель: файл должен жить в двух связях одновременно:
  1. как attachment конкретного message/thread;
  2. как user-level сущность, видимая владельцу в его личном контуре.

Почему это важно
- attachment-only модель делает файл одноразовым и плохо объясняет пользователю, где потом искать уже загружённые материалы;
- user-level список файлов делает сценарий понятным: "я загрузил документ -> он виден в сообщении -> он остался у меня в списке файлов";
- это создаёт базу для следующих шагов без новой инфраструктуры: повторное использование файлов, фильтрация, скачивание, просмотр, повторный анализ.

Практический шаблон для local-first MVP
1. Backend:
   - принять `multipart/form-data` без ломки обычного JSON-сценария;
   - сохранить файл локально;
   - извлечь текст из поддерживаемых форматов, если это помогает основному workflow;
   - записать metadata файла в message-level структуру;
   - отдельно записать metadata файла в user-level таблицу/список.
2. Frontend:
   - показать выбранные файлы до отправки;
   - после отправки показать вложения в сообщении;
   - в профиле или личной панели показать список "Мои файлы";
   - после upload обновлять не только chat/thread, но и пользовательский файловый список.
3. UX-review:
   - проверять не только внешний вид, но и сценарий: attach -> send -> see in chat -> see in personal area;
   - оценивать, не дублируется ли один и тот же смысл сразу в тексте сообщения, preview и карточке вложения;
   - сокращать шум: если attachment уже рендерится карточкой, не нужно повторять его длинное служебное описание в основном тексте.

Проверка и верификация
- Для mixed stack проверять frontend и backend нативными для них способами.
- Не использовать Python syntax-check как замену JS/runtime-проверке frontend.
- Минимальный проход верификации после таких изменений:
  - backend smoke/API test;
  - frontend runtime/syntax check подходящим инструментом;
  - ручной или browser-driven сценарий upload end-to-end.

Когда применять
- local-first чат/кабинет/assistant UI;
- добавление upload-функции в существующий текстоцентричный интерфейс;
- cleanup, где важен не только light/minimal UI, но и зрелый пользовательский сценарий вокруг файлов.
