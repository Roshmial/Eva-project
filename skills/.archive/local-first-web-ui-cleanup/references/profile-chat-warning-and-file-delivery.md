# Профиль, глобальная chat warning-плашка и проверка file-delivery в Hermes-чате

Когда полезно:
- пользователь после cleanup-pass говорит, что профиль всё ещё собран не так и просит отдельные плашки;
- нужно предупредить всех пользователей о внешней LLM-модели и риске конфиденциальных данных;
- нужно доказать, что файлы реально доходят до рабочего чата Hermes, а не просто сохраняются в профиле.

## Паттерн решения

### 1. Профиль
Не держать одну общую summary-карточку, если пользователь хочет смысловое разделение.
Практический минимальный набор плашек:
- `Кто вы для системы`;
- `Как отвечать по умолчанию`;
- `Файлы и повторное использование`.

Это лучше, чем одна сваленная summary-карточка, потому что разделяет:
- identity/context;
- response-style defaults;
- file contour.

### 2. Глобальная warning-плашка для чатов
Если предупреждение должны видеть все пользователи, а администратор должен им управлять:
- не хардкодить текст только во frontend;
- хранить настройку в local backend, например как JSON в `app_settings`;
- отдавать значение через `/api/bootstrap` всем авторизованным пользователям;
- дать admin endpoints для чтения/изменения, минимум `GET/PATCH`.

Минимальная форма управления в админке:
- включена / выключена;
- текст warning-плашки;
- статус сохранения.

Хороший default-текст для chat-first интерфейса:
`Внимание! Работа ведется с использованием внешней LLM-модели. Не загружайте и не обсуждайте конфиденциальную информацию.`

### 3. Проверка file-delivery
Если пользователь просит «проверь, что файлы приходят в чат от Hermes», этого недостаточно:
- увидеть файл в `Мои файлы`;
- увидеть локальный upload success;
- увидеть attachment только в backend payload.

Нужен живой сценарий:
1. выбрать файл в composer;
2. убедиться, что он виден в очереди на отправку;
3. отправить сообщение;
4. увидеть attachment-карточку или attachment-блок прямо в ленте Hermes-чата;
5. проверить, что файл также виден в `Профиль -> Мои файлы`.

Если есть extracted text, его надо показывать читаемо и компактно. Плохой контраст бейджа `Текст извлечён` — реальный UX-дефект, а не косметика.

## Runtime-проверка для localhost smoke
Если UI smoke начинает ловить 404 по новому endpoint после уже внесённого backend-патча:
- сначала проверить, не ходит ли smoke в старый процесс на `8788/8790`;
- посмотреть, какой PID слушает порт;
- при необходимости убить старый процесс и поднять свежий backend из текущего кода;
- только потом трактовать ошибку как продуктовую регрессию.

Признак такой ситуации:
- backend unit/smoke tests зелёные;
- syntax зелёный;
- а Playwright/UI smoke получает `404` по endpoint, который уже точно есть в коде.

Это часто означает stale runtime, а не неверный patch.
