# Hermes Web MVP: chat/jobs/admin polish lessons

Когда применять:
- cleanup pass по local-first web MVP с чатами, jobs, профилем и админкой;
- когда UI уже работает, но пользователь добивает продуктовую механику и просит убрать конфликтующие элементы;
- когда после UI/contract changes нужно синхронно обновить smoke-тесты.

Ключевые уроки

1. Не оставляй отдельный раздел «Справка», если пользователь просил встроенные подсказки.
- Help нужно раскидывать по месту использования: чат, jobs, профиль, админка.
- Отдельный help-screen создаёт лишнюю навигацию и выглядит как дублирующий раздел.

2. Sidebar чатов должен быть коротким и управляемым.
- Показывай только последние 10 активных чатов.
- Для каждого чата выводи время последней активности.
- Полный список открывай в отдельном modal-окне без искусственного лимита.
- Не держи одновременно несколько пересекающихся переключателей вида «Все чаты» и «Архив», если они не дают ясно различимый результат.

3. При открытии чата пользователь должен попадать в конец диалога.
- После загрузки thread/messages обязательно прокручивай к последним сообщениям.
- Это особенно важно в рабочих чатах и job-chat сценариях.

4. Верхняя навигация должна быть компактной.
- Если профиль уже доступен отдельной кнопкой/карточкой, не дублируй его в top nav tabs.
- Сервисный статус вида «Готово к работе · hermes-api» логичнее держать рядом с профильным блоком, а не как отдельный доминирующий элемент.

5. Для jobs различай backend permissions и frontend visibility.
- Permissions: creator + admin могут edit/run; остальные нет.
- Visibility: это отдельная фронтовая/продуктовая настройка показа, не подменяй ею backend security.
- В detail-view и modal явно разводи эти два слоя в подписях.

6. Блок «Параметры» в jobs не должен светиться всем подряд.
- Если параметры технические или содержат системный prompt/runtime payload, показывай их только админу.
- Для обычного пользователя важнее статус, расписание, доступ, получатели и история запусков.

7. Для модели «один job — один чат» в user-scoped thread architecture не пытайся срочно строить shared-thread engine.
- Если текущая схема threads привязана к user_id, делай per-user materialized job-thread с общим job_id.
- При добавлении получателя создавай связанный job-thread.
- При удалении получателя убирай связанный job-thread.
- Доставку run-результатов направляй только в связанные job-thread’ы.

8. После смены UX/API-контракта обязательно обновляй smoke, а не только код.
- Если удалена nav-кнопка профиля, UI smoke должен перейти на новый селектор.
- Если jobs больше не read-only, backend smoke должен проверять новый writable contract, а не старое отклонение create/update/run.
- Для таких задач «код зелёный, smoke красный» обычно значит не новый баг, а устаревший test contract.

Мини-чеклист для похожих задач
- убрать дубли навигации и конфликтующие переключатели;
- ограничить sidebar активным кратким списком;
- вынести полный список в modal;
- проверить scroll-to-bottom при открытии чата;
- развести visibility vs permissions;
- скрыть admin-only технические блоки;
- проверить create/update/run/recipient flows у jobs;
- переписать smoke-тесты под новый контракт;
- только после этого считать cleanup завершённым.
