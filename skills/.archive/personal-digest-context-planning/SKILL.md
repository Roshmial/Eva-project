# Когда использовать

Используй этот навык, когда нужно проектировать, дорабатывать или тестировать персональные daily/weekly дайджесты, утренние брифы, weekly review или другие регулярные сообщения для пользователя.

Особенно применимо, когда дайджест должен зависеть не только от дня недели и погоды, но и от:
- будущих задач по конкретным датам;
- поездок и городов пребывания;
- уже купленных билетов и зафиксированной логистики;
- планов на месте;
- личных дат вроде дня рождения.

# Главная идея

Персональный дайджест должен опираться не только на недавний чат, но и на устойчивый слой будущих планов.

Если пользователь уже знает, где он будет в конкретный день, бессмысленно генерировать generic-рекомендации для домашнего города. Дайджест должен адаптироваться под реальный день, реальное место и реальную логистику.

# Что считать контекстом первого уровня

1. Датированные обязательства.
   - поездки;
   - билеты;
   - вылеты и переезды;
   - встречи;
   - дедлайны;
   - дни рождения и прочие личные даты.

2. География дня.
   - в каком городе пользователь будет утром / днём / вечером;
   - будет ли это день переезда;
   - есть ли смысл давать прогулку, маршрут или только лёгкий план.

3. Активные длинные темы.
   - не вся история обсуждений подряд;
   - только те задачи, у которых есть следующий практический шаг и которые реально влияют на ближайшие дни.

# Источники контекста

Предпочтительный порядок:
1. Google Calendar или другой календарь пользователя — события, поездки, дни рождения, окна занятости.
2. Локальный структурированный реестр планов/поездок — источник деталей, которых нет в календаре.
3. Decision-log — зафиксированные решения и принятые варианты.
4. Session history — только как вспомогательный источник, если structured-layer неполон.

# Правила адаптации дайджеста

1. Если на конкретную дату уже зафиксирована поездка, day-brief должен отражать именно её.
   Примеры:
   - день приезда в Волгоград → вечерняя прогулка по Волгограду;
   - день маршрута → подсветить логистику и ключевую точку дня;
   - день в Астрахани → дать локальный маршрут по Астрахани, а не совет по Москве.

2. Если на дату есть жёсткий переезд, не перегружай день второстепенными целями.
   Переездный день — это особый тип дня.

3. Если на дату есть личная значимая дата, она должна явно появиться в тексте.
   Пример: день рождения — не просто скрытый факт в календаре, а повод изменить тон и содержимое сообщения.

4. Если пользователь уже определил город, не подставляй generic hometown defaults.
   Особенно это важно для прогулок, маршрутов, кафе, досуга и локальных дел.

5. Если контекст поездки неполный, дайджест не должен выдумывать детали.
   Лучше коротко сказать, что день завязан на переезд/город, и предложить следующий реалистичный шаг.

# Формат мышления для recurring-дайджестов

Перед генерацией сообщения дайджест должен ответить себе на 5 вопросов:
1. Какой сегодня день по календарю?
2. Где пользователь физически будет сегодня?
3. Есть ли сегодня переезд, вылет, прибытие или фиксированная бронь?
4. Есть ли сегодня приоритетная задача по длинной теме?
5. Есть ли личная дата, которая должна изменить тон или содержание?

# Отдельное правило для travel-дней

Если день связан с поездкой, полезнее всего давать один из трёх типов помощи:
- маршрут дня;
- вечернюю прогулку / лёгкий локальный план по месту;
- напоминание о ключевой логистике.

Не надо смешивать travel-day с обычным productivity-day шаблоном, если это ломает реализм.

# Pitfalls

- Генерировать московские прогулки, когда пользователь уже находится в другом городе.
- Давать абстрактные self-development идеи в день переезда, игнорируя жёсткую логистику.
- Пытаться каждый раз восстанавливать будущее только по переписке без structured-layer.
- Прятать день рождения или другую значимую личную дату в фоне, никак не отражая её в тексте.
- Считать, что календаря достаточно сам по себе: у поездок часто есть важные детали, которых в событии нет.

# Что считать хорошим результатом

Хороший персональный дайджест:
- чувствует конкретную дату, а не только день недели;
- знает, где пользователь будет;
- меняет рекомендации под поездку и город;
- опирается на реальные будущие планы;
- не выглядит как generic текст, который можно было отправить в любой день.
