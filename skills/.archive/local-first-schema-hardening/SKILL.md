# Когда применять

Используй этот skill, когда нужно усилить целостность данных в local-first приложении, где:

- есть уже работающая SQLite/DuckDB/Postgres-подобная схема;
- есть legacy import или bootstrap migration из старой базы;
- добавляются `NOT NULL`, `DEFAULT`, `version`, `UNIQUE`, optimistic locking;
- нужно усилить multi-user корректность без полного переписывания стека.

Типичные случаи:

- добавление `version` для optimistic locking;
- добавление новых обязательных полей в существующую таблицу;
- добавление уникальных индексов поверх уже накопленных данных;
- исправление race-condition через DB-level invariant, а не только через код.

# Главный принцип

Схему нельзя ужесточать изолированно от миграции старых данных.

Если добавляешь:

- новое `NOT NULL` поле;
- новое поле с `DEFAULT`;
- уникальный индекс;
- compare-and-swap по `version`;

то обязательно синхронно проверь и обнови:

1. `CREATE TABLE` и текущую схему;
2. path `ALTER TABLE` или `ensure_column`;
3. legacy import и backfill;
4. cleanup или dedupe перед созданием уникального ограничения;
5. API contract и тесты на конфликтные записи.

# Рабочая последовательность

## 1. Сначала определи инвариант данных

Явно зафиксируй, что именно должно стать истинным после миграции:

- у каждой сущности есть `version >= 1`;
- у `job-thread` только одна запись на `(user_id, job_id)`;
- stale update должен давать `409`, а не тихо перетирать данные;
- новые обязательные поля не могут быть `NULL` ни в новой, ни в legacy-записи.

Если инвариант не сформулирован, миграция почти всегда получается частичной.

## 2. Добавь новые поля в схему и в path донастройки колонок

При добавлении поля проверь оба места:

- создание таблицы с нуля;
- донастройка существующей базы (`ensure_column`, `ALTER TABLE`, backfill).

Для полей вида:

- `version INTEGER NOT NULL DEFAULT 1`
- `display_name TEXT NOT NULL DEFAULT ''`
- `flag INTEGER NOT NULL DEFAULT 0`

недостаточно только добавить колонку — нужно гарантировать, что старые строки получат допустимое значение.

## 3. Обнови legacy import одновременно со схемой

Это обязательный шаг.

Если legacy import собирает payload по колонкам, то для каждого нового обязательного поля должен быть явный fallback.

Пример типов fallback:

- `version` -> `1`
- текстовое обязательное поле -> `''`
- bool или int flag -> `0`
- scope или status поле -> безопасное дефолтное значение вроде `'disabled'`
- JSON поле -> валидный минимальный JSON

Антипаттерн:

- добавить `NOT NULL` поле в таблицу;
- не обновить legacy import;
- получить падение bootstrap/migration на вставке старых строк.

## 4. Уникальные индексы вводи только после cleanup или dedupe

Если добавляешь `UNIQUE`, не создавай индекс в лоб, пока не доказано, что старые данные уже чистые.

Правильный порядок:

1. найти потенциальные дубли;
2. выполнить deterministic cleanup или dedupe;
3. только после этого создавать `UNIQUE INDEX`.

Это особенно важно для shared сущностей вроде:

- `(user_id, job_id)`
- `(entity_id, recipient_id)`
- `(owner_id, external_ref)`

Антипаттерн:

- сначала создать unique index;
- потом разбираться, почему миграция падает на уже существующих дублях.

## 5. Optimistic locking делай сквозным контрактом

Если вводишь `version`, этого недостаточно на уровне БД.

Нужно закрыть весь путь:

1. response API возвращает `version`;
2. frontend или admin client отправляет `version` обратно при update;
3. backend update использует compare-and-swap (`WHERE id = ? AND version = ?`);
4. при конфликте backend возвращает `409` и стабильный код ошибки вроде `version_conflict`;
5. UI умеет показать понятное сообщение и попросить перезагрузить данные.

Если один из слоёв пропущен, optimistic locking становится декоративным.

## 6. Сначала RED-тесты, потом правка, потом повторный смоук

Минимальный пакет проверок:

- stale update профиля или сущности возвращает `409`;
- stale update shared entity возвращает `409`;
- после subscribe/create-path не появляются дубли там, где обещан unique invariant;
- bootstrap или legacy migration проходит на старых данных;
- существующий smoke suite остаётся зелёным.

# Типовые pitfalls

## Pitfall 1. Добавили `NOT NULL`, но забыли legacy payload mapping

Симптом:

- новая чистая база работает;
- на старой базе или legacy import приложение падает при старте или bootstrap.

Что делать:

- найти mapping, который собирает payload для legacy rows;
- добавить fallback для каждого нового обязательного поля;
- повторно прогнать bootstrap или migration test.

## Pitfall 2. Добавили unique index до дедупликации

Симптом:

- миграция падает на `Constraint Error` или duplicate key;
- код вроде правильный, но rollout уже сломан.

Что делать:

- временно убрать раннее создание индекса;
- сделать cleanup или dedupe;
- создавать индекс только после cleanup.

## Pitfall 3. Добавили `version` в БД, но не прокинули в UI/API

Симптом:

- поле существует, но stale save всё равно проходит;
- или backend не может отличить конфликт от обычного обновления.

Что делать:

- вернуть `version` в detail/list responses;
- отправлять `version` из клиента при `PATCH`;
- использовать compare-and-swap в SQL.

## Pitfall 4. Починили correctness, но забыли human contract

Симптом:

- backend честно отдаёт `409`;
- пользователь видит просто «ошибка сохранения».

Что делать:

- ввести стабильный код ошибки (`version_conflict`);
- на frontend дать понятное объяснение: данные изменились в другой сессии или другим пользователем, нужно обновить экран.

# Что считать достаточным результатом

Можно считать задачу завершённой, если одновременно выполнено всё ниже:

- новая схема поднимается на чистой базе;
- legacy migration не падает на старых данных;
- уникальные инварианты защищены на уровне БД;
- stale writes больше не перетирают данные молча;
- regression или smoke tests проходят;
- UI понимает `version_conflict` хотя бы на базовом уровне.

# Когда не надо усложнять

Не нужно сразу тащить новый стек, event bus, отдельную БД или распределённые блокировки, если задача решается:

- `version` и compare-and-swap;
- backfill и defaults;
- dedupe и unique index;
- несколькими точечными API и UI изменениями.

Сначала дожимай корректность в текущем local-first контуре. Только потом решай, нужен ли архитектурный переезд.
