# Markdown table transition regression — 2026-06-24

## Когда пригодится

Использовать, когда пользователь жалуется не на «пропавший markdown», а на более узкий симптом:
- таблица начинается слишком рано;
- вводный текст «прилипает» к таблице;
- таблица визуально уезжает сразу после вводных слов, хотя должна идти отдельным блоком.

## Реальный урок

Не сводить такой баг автоматически к двум популярным версиям:
1. markdown не распознался и ушёл в plain-text path;
2. table renderer / CSS сломан.

Есть третий частый класс проблем: block segmentation внутри `renderMarkdownContent(...)`.

## Конкретный паттерн поломки

В `renderMarkdownContent(...)` paragraph loop был слишком жадным:
- собирал обычный paragraph block;
- не останавливался перед строкой, которая уже является заголовком markdown-таблицы;
- из-за этого вводный абзац и таблица попадали в один block pass.

Типовой маркер старта таблицы:
- текущая строка соответствует заголовку `| ... |`
- следующая строка соответствует separator line `| --- | --- |`

## Правильная диагностика

Проверять в таком порядке:
1. Есть ли у сообщения реальная markdown-разметка.
2. Попадает ли оно в markdown path.
3. Если да — правильно ли parser делит block'и:
   - paragraph
   - table
   - list
   - quote
   - code fence
4. Только после этого проверять CSS / table renderer.

## Правильный фикс

Не отключать markdown глобально.

В paragraph-сборщике добавить stop-condition: если текущая следующая строка — это начало markdown-таблицы, paragraph должен завершиться до неё.

Идея условия:
- `^\s*\|.+\|\s*$` для header line
- `isMarkdownTableSeparator(nextLine)` для separator line

## Практический вывод

Если жалоба звучит как:
- «md есть, но таблица начинается не там»
- «после вводных слов всё ушло в таблицу»

то сначала проверять transition `paragraph -> table`, а не делать широкие исправления классификации markdown/plain-text.
