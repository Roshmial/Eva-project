# Когда использовать

UI-правила для этого класса задач:
- По умолчанию проектируй светлую тему, если интерфейс состоит в основном из текста, списков и форм.
- Не допускай множественных точек редактирования одного и того же смысла: один экран редактирования и не более одного краткого summary-блока.
- Не дублируй настройки профиля/персонализации одновременно в sidebar, topbar, welcome-блоках, модалках и отдельных экранах.
- Избегай тяжёлых крупных плашек, вложенных карточек и визуального шума. Иерархию строй через типографику, отступы и компактные secondary-элементы.
- Проверяй русский язык как отдельный acceptance-критерий: без инженерного жаргона вроде raw cron, source of truth, workspace-visible и без разговорных или небрежных формулировок.
- В admin-формах отдельно проверяй отсутствие дублирующихся DOM id и конфликтов между режимом формы и пользовательскими полями.
- При UI-аудите обязательно проходи по чек-листу: тема/цвет, дубли смыслов, плотность карточек, перегрузка полями, качество подписей и ошибок, визуальный вес системных блоков.

# Когда использовать

Используй этот навык, когда нужно:
- убрать hardcode справочников из frontend;
- перевести справочники в backend-таблицы и admin CRUD;
- подготовить систему к состоянию «только развернули, ещё не работали»;
- пересобрать local-first admin/chat UI без дублирования профиля, перегруза карточками и тёмой SaaS по умолчанию;
- привести frontend к светлой, спокойной, русскоязычной рабочей поверхности;
- оставить operational web-слой чистым для тестирования фронта;
- развести operational source of truth и analytical layer без дублирующих master-таблиц;
- дать администратору ручное управление пользователями, ролями и ограничениями.

# Принципы

1. Local-first по умолчанию.
- Не выносить справочники во внешний SaaS или отдельный сервис, если задача решается в текущем backend.
- Не строить параллельные контуры хранения одного и того же смысла.

2. Operational и analytical слои не смешивать.
- Runtime/master-данные живут там, где рождаются.
- Analytical hub получает snapshots и views, но не становится новым source of truth.

3. Frontend не должен быть носителем справочной истины.
- Во frontend допустим только rendering и минимальная клиентская логика.
- Значения справочников, стартовых подсказок, help-контента, feedback reasons, job templates должны приезжать из backend.

4. Clean bootstrap важнее красивой демо-наполненности.
- Для сценария «чистая база / первый запуск» оставляй только базовые сущности для настройки.
- Никаких старых synthetic threads/messages/jobs в operational web DB.
- Допустим один admin account и backend-seeded reference data.

5. Admin surface должен быть полным по базовому управлению.
- Администратор должен уметь вручную создавать пользователей.
- Администратор должен уметь редактировать роль, ограничения, профильные поля, пароль.
- Администратор должен уметь править элементы справочников через UI, а не через код.
- Если пользователь требует логирование и версионность, это не «nice to have»: сразу закладывай audit trail для админских правок и явное поле версии у изменяемых сущностей.
- Если интерфейс пользовательский, все label-ы, статусы и сообщения на уровне фронта должны быть приведены к языку продукта; внутренние key/value допустимы на английском только как технические значения, не как подписи.

# Обязательная последовательность

1. Сначала проверь, что сейчас hardcoded во frontend и backend.
- Ищи starter prompts, help articles, feedback reasons, templates, role lists, status lists и подобные каталоги.
- Отдельно проверь, не зашиты ли справочники прямо в render-функциях frontend.

2. Спроектируй backend-слой справочников.
- Нужна таблица catalog/dataset и таблица items.
- Для items держи минимум: dataset_key, item_key, label, sort_order, is_active, payload_json, timestamps.
- Если нужны фиксированные наборы, seed делай в backend-таблицы, а не в frontend-константы.

3. Переведи runtime endpoint-ы на backend-справочники.
- bootstrap
- feedback/reasons
- help/starter/job-template related payloads
- любые admin/meta endpoint-ы, которые раньше читали hardcode.

4. Добавь admin CRUD.
- Endpoint-ы на чтение и изменение элементов справочников.
- Endpoint-ы на ручное создание/редактирование пользователей.
- Не ограничивай admin только CSV import, если вручную создавать пользователей — явное требование.

5. Доработай frontend admin UI.
- Отдельный блок справочников.
- Отдельная форма ручного создания/редактирования пользователя.
- Не требуй от админа править JSON/код в репозитории ради базовой настройки сервиса.

6. После изменений обязательно проверь живой результат.
- Syntax check backend/frontend.
- Запуск backend.
- Реальные API вызовы.
- Сценарии: create user, update user, fetch references, create/update reference item.
- Проверка clean bootstrap state в operational DB.
- Отдельно сверяй, что данные не только вернулись из API, но и физически сохранились в БД.
- Если backend на DuckDB использует агрегаты и joins по users/reference, проверяй SQL на совместимость: все неагрегированные поля должны быть в GROUP BY, иначе admin list/detail может падать только на живом запросе.
- Если browser-инструмент странно рендерит локальный frontend, не делай вывод «UI сломан» без дополнительной проверки: отдельно проверь отдачу index.html/app.js по HTTP и разделяй проблему приложения и проблему инструмента проверки.

# Пользовательский режим работы для Миши

Если задача поставлена под ключ в разработке:
- не дроби искусственно на отдельные промежуточные артефакты вроде «сначала только матрица» без явной пользы;
- считай, что нужно сразу собирать целостный data layer, API и admin surface;
- если в постановке пропущены шаги, сама достраивай обязательные действия;
- проверяй не только код, но и логичность всей цепочки: storage -> API -> frontend -> analytical layer;
- если нужны дополнительные действия для рабочего результата, либо выполняй их сама, либо явно предлагай как следующий обязательный шаг.

# Паттерн данных

Рекомендуемая форма:
- operational DB:
  - users
  - threads
  - messages
  - feedback
  - reference_catalogs
  - reference_items
- analytical layer:
  - raw snapshots operational таблиц;
  - unified views;
  - final summary views.

Не делай:
- отдельные дублирующие таблицы под тот же справочник в разных слоях;
- магическое склеивание identity между разными source systems;
- frontend fallback на старые hardcoded arrays как тихий запасной режим.

# Проверочный чек-лист перед сдачей

- Backend-справочники физически созданы в БД.
- Seed справочников идёт в backend-таблицы.
- Frontend не содержит hardcoded business dictionaries.
- Admin может вручную создать пользователя и назначить ему роль.
- Admin может задать ограничения и профильные поля пользователя.
- Admin может редактировать элементы справочников через UI.
- Operational web DB чиста от synthetic historical artifacts.
- Analytical hub продолжает быть только analytical layer.
- Все ключевые изменения подтверждены живыми проверками, а не только patch-ами.

# Частые ошибки

- Оставить CSV import как единственный способ создания пользователя.
- Убрать hardcode из одного endpoint-а, но оставить его в bootstrap/help/jobs payload.
- Очистить frontend DB, но забыть проверить demo seeding и флаги первого запуска.
- Считать задачу завершённой после patch-а без реального прогона API и UI.
- Подменить clean bootstrap красивой демо-наполненностью.
