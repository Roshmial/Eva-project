# Reference-driven personalization and governance

Когда в local-first admin-контуре есть настраиваемые пользовательские параметры ответа (например `tone`, `answer_depth`, `interaction_mode`), не оставляй их как frontend hardcode. Веди их как обычные backend-справочники с единым governance-контуром.

## Что считать правильной моделью

- Backend — источник истины для списков значений.
- Профиль пользователя хранит стабильные machine keys, а не локализованные подписи.
- Frontend получает списки значений из bootstrap/reference API, а не из локальных массивов.
- Русские labels показываются только как UI-представление.
- Неактивные справочные значения не должны silently приниматься в новые записи.

## Обязательные шаги

1. Заведи отдельные dataset keys для каждого управляемого параметра персонализации.
2. Добавь seed-значения с полями уровня: `key`, `label`, при необходимости `prompt_value`, `sort_order`, `is_active`.
3. Сделай backend-функции:
   - получить активные keys;
   - получить map `key -> label`;
   - нормализовать профиль;
   - валидировать профиль до записи.
4. Проведи валидацию через все write-path:
   - admin create/update;
   - self-service profile update;
   - import/upsert;
   - любые косвенные обновления пользователя.
5. На чтении собирай UI-summary через labels из справочников, но в runtime/prompt используй стабильные keys или выделенное `prompt_value`.
6. Во frontend полностью убери hardcoded options. Select/filters/modals должны строиться из bootstrap/reference данных.
7. Для user-facing UI держи фронт полностью на русском уровне подписей, статусов и ошибок.
8. Для admin-контура считай логирование и версионность базовыми, а не дополнительными свойствами:
   - audit log на изменения;
   - version в управляемых сущностях;
   - история изменений для проверки кто и что поменял.
9. После реализации не останавливайся на коде: прогоняй живой сценарий end-to-end.

## Минимальный сценарий проверки

1. Получить bootstrap и убедиться, что новые dataset уже приходят во frontend.
2. Сохранить профиль с валидными keys.
3. Проверить, что невалидный key отвергается backend-ом с понятной ошибкой.
4. Перечитать профиль и убедиться, что summary/labels пришли корректно.
5. Отправить сообщение и проверить, что персонализация реально дошла до слоя генерации ответа.
6. Деактивировать одно из значений справочника и проверить контролируемое fallback-поведение.

## Частые ошибки

- Оставить frontend массивы как фактический источник списка значений.
- Сохранять в профиль русские labels вместо стабильных keys.
- Валидировать только admin CRUD, но забыть про `/me` и import.
- Считать задачу завершённой после patch/write без живого прогона.
- Добавить справочники, но забыть про audit/history/version.
- Сделать backend правильно, но оставить пользовательский фронт частично на английском.

## Когда это особенно важно

- Когда одни и те же параметры участвуют и в профиле пользователя, и в prompt/personalization логике.
- Когда значения должны редактироваться администратором без деплоя frontend.
- Когда продукт local-first и нельзя плодить отдельные несвязанные конфиги для UI и runtime.
