# Когда использовать

Используй для задач вида:
- проверить, какие модели в standard/reasoning списках Hermes Web реально отвечают на прод/удалённом хосте;
- переставить default model и fallback order без изменения кода;
- подтвердить, что backend/frontend действительно подхватили новый порядок.

# Что это решает

В таких задачах недостаточно просто посмотреть `.env` или `config.yaml`.
Нужно отдельно подтвердить 4 вещи:
1. список моделей в конфиге;
2. живая доступность моделей реальным прогоном;
3. факт перезапуска нужных процессов;
4. что новые env-переменные реально попали в runtime-процессы и видны через health.

# Пошаговый протокол

1. Найди текущий источник порядка моделей.
- Смотри как минимум:
  - `~/.hermes/.env`
  - `~/.hermes/config.yaml`
  - backend-код, где читаются `HERMES_WEB_HERMES_API_MODEL`, `HERMES_WEB_STANDARD_MODEL_CANDIDATES`, `HERMES_WEB_REASONING_MODEL_CANDIDATES`.
- Не предполагай заранее, что runtime берёт порядок только из одного места.

2. Проверь живость моделей реальным вызовом.
- Гони короткий запрос через `hermes chat -q` по каждой модели отдельно.
- Фиксируй минимум:
  - provider
  - model
  - exit_code
  - latency
  - хвост stdout/stderr
- Для массовой проверки удобнее маленький Python-скрипт через ssh/runuser, чем много ручных вызовов.

3. Меняй порядок сначала в env, потом перезапускай runtime.
- Для Hermes Web стандартный рабочий путь:
  - обновить `HERMES_WEB_HERMES_API_MODEL`
  - обновить `HERMES_WEB_STANDARD_MODEL_CANDIDATES`
- Если задача про reasoning-маршрут, отдельно трогай `HERMES_WEB_REASONING_MODEL` и `HERMES_WEB_REASONING_MODEL_CANDIDATES`.

4. После изменения env обязательно проверь runtime, а не только файл.
- Убедись, что старые процессы backend/frontend остановлены.
- Подними их заново с тем же env.
- Проверь `/proc/<pid>/environ` у живых процессов и сравни значения переменных.
- Это важнее, чем доверять факту перезаписи `.env`.

5. Проверь health-endpoint.
- Для backend Hermes Web используй health и смотри, что `default_model` совпал с ожидаемым.
- Если есть routing-блок в health, проверь и его лимиты/режимы заодно.

# Практические команды и сигналы проверки

Типовой набор проверок:
- поиск упоминаний моделей и env-ключей по проекту;
- чтение `~/.hermes/.env`;
- просмотр текущих pid backend/frontend;
- чтение `/proc/<pid>/environ`;
- `curl` в backend health;
- опционально `curl`/доступность frontend.

Минимальный критерий «изменение реально применилось»:
- новый порядок есть в `.env`;
- новые процессы запущены;
- у этих pid в `environ` новый порядок;
- health возвращает новый default model.

# Порядок принятия решения по fallback

Для user-facing web-чата оценивай не только качество модели, но и:
- живость здесь и сейчас;
- латентность;
- риск upstream rate limit;
- обратимость решения.

Хороший практический подход:
- если модель быстрая и живая, можно ставить первой;
- если уже был замечен 429/rate limit, держи это как явный риск даже если текущий тест зелёный;
- второй моделью ставь более устойчивый fallback, а не просто «следующую по престижу».

# Пойманный на практике нюанс

`openrouter/owl-alpha` может быть живой в моменте, но ранее уже давал upstream `429 rate-limited`.
Значит, при постановке `owl-alpha` первым нужно явно считать это компромиссом: скорость/удобство выше, но риск кратковременного rate limit тоже выше.

# Чего не делать

- Не объявляй модель «живой» только потому, что она есть в списке.
- Не ограничивайся правкой `.env` без проверки runtime pid/env.
- Не говори, что порядок применился, пока health и `/proc/<pid>/environ` это не подтвердили.
- Не смешивай standard и reasoning маршруты в одну неразличимую проверку.

# Результат, который нужно вернуть пользователю

Коротко и прикладно:
- какой новый порядок установлен;
- что именно изменено (`default model`, `standard candidates`);
- что backend/frontend перезапущены;
- чем подтверждено применение (env у pid + health);
- если есть риск вроде `owl-alpha` rate limit, назвать его прямо одним предложением.
