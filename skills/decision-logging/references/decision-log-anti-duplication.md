# Decision log anti-duplication policy

## Назначение

Эта памятка нужна для случаев, когда агент одновременно работает с `decision-log.md`, длинной историей сессий в `state.db` и крупными tool outputs / runtime-логами.

Главная цель: не превращать `decision-log.md` в дубль session history.

## Роли слоёв хранения

### 1. `state.db`
Хранит оперативную историю:
- пользовательские сообщения;
- ответы агента;
- tool results в достаточно компактном, но всё ещё рабочем виде;
- материал для `/resume`, `session_search`, history и диагностики.

### 2. `decision-log.md`
Хранит только устойчивые итоги:
- какие решения приняты;
- какие варианты отклонены;
- почему выбрали именно этот путь;
- какие условия потребуют пересмотра.

### 3. Raw-артефакты / файлы
Хранят полные тяжёлые данные:
- длинные логи;
- полные tool outputs;
- дампы, отчёты, трассировки;
- backup-артефакты.

Именно сюда должны уходить большие operational-детали, если они нужны целиком.

## Что нельзя дублировать в decision-log

Не копировать в журнал решений:
- полные stdout/stderr;
- длинные журналы `journalctl`;
- сырые diff / stack trace / browser dumps;
- пошаговую стенограмму отладки;
- длинные текстовые summary, которые просто пересказывают session transcript.

Если запись выглядит как «мини-копия всей сессии», она неправильная.

## Что писать вместо этого

Вместо сырого лога писать коротко:
- что именно решили;
- какой root cause подтвердился;
- какой fix внесён;
- чем проверено;
- где лежит полный артефакт, если он нужен.

Хороший шаблон:
- `Agreed`: что приняли как рабочее решение;
- `Implemented`: какие изменения реально внесены;
- `Verified`: чем подтверждено;
- `Open questions`: что сознательно оставили на потом.

## Когда ссылаться на артефакт, а не копировать его

Ссылайся на файл/артефакт, если:
- вывод длиннее нескольких десятков строк;
- важна полнота лога, а не его пересказ;
- данные нужны для возможного повторного аудита;
- это backup, dump, patchset или диагностический отчёт.

В записи decision-log достаточно указать путь и смысл артефакта.

## Практическое правило

Если информацию можно восстановить из `state.db`, файла-артефакта или git diff, в `decision-log.md` должен остаться только управленческий смысл этой информации, а не её полная копия.

## Специальный случай: storage optimization

При задачах оптимизации хранилища разделяй:
- решение по политике хранения;
- фактически внесённые изменения в runtime/код;
- измеримый эффект;
- остаточные риски.

Но не дублируй:
- целиком SQL-диагностику;
- длинные dbstat-выгрузки;
- полные журналы tool results.

Правильная запись: короткое решение + проверка + ссылка на backup / patch / артефакт.
