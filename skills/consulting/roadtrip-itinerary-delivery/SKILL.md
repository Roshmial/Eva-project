# Когда использовать

Используй этот навык, когда пользователь просит не просто маршрут поездки, а уже прикладную схему исполнения:
- по дням;
- с must-see точками;
- с кафе рядом;
- со ссылками на карты и справочные страницы;
- с понятной инструкцией, как перемещаться между точками.

Особенно полезно, когда поездка длинная, автомобильная и в ней есть сочетание:
- межгородских перегонов;
- 1–3 полных дней в городе;
- транзитных остановок;
- одного-двух тяжёлых по логистике дней.

# Цель

Дать пользователю не абстрактный обзор, а рабочий маршрут, который можно открыть в дороге и реально использовать без дополнительной расшифровки.

# Принципы сборки

1. Сначала фиксируй каркас поездки.
   - Даты.
   - Города ночёвок.
   - Полные дни в ключевых точках.
   - Ограничения пользователя по возвратам, повторным ночёвкам и нежелательным заездам.

2. Затем дели точки на три слоя.
   - Обязательные.
   - Хорошие, но необязательные.
   - Лишние для этой версии маршрута.

3. Не превращай ответ в энциклопедию.
   Для каждой точки достаточно:
   - зачем ехать;
   - ссылка на карту;
   - при наличии — ссылка на Wikipedia или понятную справочную страницу;
   - 1–2 кафе рядом.

4. Для каждого дня обязательно давай механику перемещения.
   Пользователь должен сразу понять:
   - где ехать только на машине;
   - где разумно оставить машину и идти пешком;
   - где лучше взять такси;
   - где день надо сознательно разгрузить.

5. Сложные дни помечай прямо.
   Если есть перегон на 10+ часов, это нужно явно назвать тяжёлым днём и рекомендовать ранний выезд, короткие остановки и отказ от насыщенной вечерней программы.

# Рекомендуемая структура ответа

Сначала короткий вывод:
- общий контур маршрута;
- главный риск по логистике;
- 1–2 слова о темпе поездки.

Если пользователь просит маршрут "визуально", "на карте" или "схемой", меняй формат ответа:
- сначала давай саму карту / ссылку / визуальный артефакт;
- затем только короткую расшифровку сегментов;
- не возвращайся к длинному текстовому описанию без явной просьбы.

См. также: `references/route-visualization.md`.

Дальше блок "Ключевые переезды":
- дата;
- откуда → куда;
- километры;
- ориентировочное время.

Дальше основная часть по дням:
- дата и город;
- смысл дня;
- точки;
- кафе рядом;
- как перемещаться.

В конце:
- что точно не пропускать совсем;
- какая часть маршрута самая тяжёлая;
- что перепроверить перед выездом.

# Формат точки

Для каждой ключевой точки используй компактную форму:
- название;
- почему это must-see или зачем она нужна в маршруте;
- карта;
- справочная ссылка;
- кафе рядом;
- как добираться именно в рамках этого дня.

# Как выбирать кафе

1. Не пытайся делать ресторанный гид.
2. Достаточно 1–2 вариантов рядом с ключевой точкой.
3. Для транзитных природных точек кафе лучше искать не "у объекта любой ценой", а в ближайшем посёлке или у въезда.
4. Если день длинный и переездный, приоритет у понятной и быстрой еды, а не у красивой подборки.

# Как выбирать точки

1. В городе на 1 полный день — 2–3 основные точки максимум.
2. В городе на 2 полных дня — разведи день по смыслу:
   - исторический/обязательный;
   - более спокойный/районный/атмосферный.
3. На транзитном дне — одна сильная точка, а не россыпь мелких остановок.
4. Если объект логистически ломает весь день, прямо помечай его как опциональный, даже если он красивый.

# Когда пользователь просит визуализацию после согласования маршрута

1. Зафиксируй уже согласованный контур поездки.
   - Не пересобирай маршрут заново.
   - Не открывай повторно спор о городах и ночёвках, если новых вводных не появилось.

2. По умолчанию визуализируй именно текущую версию маршрута.
   - Сначала карта или ссылка на карту.
   - Затем короткая подпись по сегментам.

3. Предпочтительный порядок артефактов:
   - одна удобная ссылка на маршрут целиком, если сервис это позволяет;
   - если нет — набор ссылок по ключевым перегонам;
   - если картографическая ссылка неудобна или хрупка — простая схема или HTML/SVG-карта как запасной вариант.

# Pitfalls

- Не перегружай ответ слишком большим числом точек на день.
  Если пользователь уже дал рабочий контур, не надо снова проектировать поездку с нуля и набрасывать лишние варианты.

- Не смешивай длинную и короткую версии в одном сообщении.
  Нужно сразу дать один цельный, удобный для использования вариант.

- Если пользователь просит визуализацию маршрута, не отвечай повторным обсуждением логики поездки.
  На этом шаге нужен картографический результат: ссылка, схема или скриншот, а не ещё один текстовый разбор.

- Не прячь тяжёлые места маршрута за красивыми формулировками.
  Если перегон объективно тяжёлый, это надо назвать прямо.

- Не заставляй пользователя самому восстанавливать механику перемещения.
  Если есть музей, набережная и удалённый район, обязательно объясни, что делать пешком, что на машине, а что лучше вынести в отдельный выезд.

- Не делай вид, что все красивые точки одинаково обязательны.
  В длинной автопоездке логистика важнее полноты списка.

- Не предлагай "приятный город для ночёвки", если он уводит маршрут в сторону.
  Для технической остановки сначала проверяй геометрию маршрута: насколько город лежит по ходу, а уже потом смотри, насколько он сам по себе симпатичный.

- Если пользователь явно говорит, что город ему нужен не для прогулок, а для встречи или просто сна, не трать маршрутный бюджет на его sightseeing-ценность.
  В таких случаях приоритет — удобный вечер, ранний выезд и отсутствие лишнего крюка, а не "самая приятная промежуточная точка".

# Мини-чеклист перед финальным ответом

Проверь, что в ответе есть:
- весь маршрут по дням;
- обязательные точки без раздувания списка;
- хотя бы по 1–2 кафе рядом с ключевыми местами;
- ссылки на карты;
- понятная инструкция по перемещению;
- явное предупреждение о самом тяжёлом перегоне.

# Что считать хорошим результатом

Хороший результат — это маршрут, который можно:
- быстро прочитать целиком;
- сохранить в заметки;
- открыть в дороге без дополнительной доработки;
- использовать как практическую шпаргалку, а не как вдохновляющий, но расплывчатый текст.
