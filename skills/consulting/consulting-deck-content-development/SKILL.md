# Consulting deck content development

## Workflow

1. Establish the canonical artifact. If the user declares a Markdown brief the base, edit and agree that file first; do not change Gamma or another visual deck until explicitly asked.
2. Inspect the source before restructuring it: extract the text, slide count, aspect ratio, theme colors and fonts, reusable media, and a visual montage when rendering is available. Then classify every slide: executive summary, role value, mechanism, case, operating cycle, scaling, delivery, governance, or commercial close. When adapting an approved reference, build a numbered slide-function map and preserve both sequence and block allocation; six reference case slides remain six case slides unless the user explicitly approves a new storyline. Remove slides that only repeat the next slides.
3. When reducing a deck to a client one-pager, rebuild the hierarchy instead of shrinking the slides. Use this reading order: offer and management outcome → client problem/decision → compact value mechanism → three or four executive benefits → evidence with explicit status → rational starting step → scope, timing, price, and boundaries. Keep only information needed for a first client decision; move methodology detail and secondary cases out.
4. Write conclusion-led titles that state the decision, benefit, or outcome. Avoid process labels and constructions of the form “не X, а Y”; state the positive conclusion directly.
5. Keep one offer name throughout. Describe embedded calculation methods as part of the offer instead of creating a second product by wording.
6. Normalize evidence slides to a compact, repeatable shape. For proposed use cases use “Ситуация → Что сравниваем/рассчитываем → Решение → Потенциальный эффект”; for historical evidence use “Ситуация → Что сделали → Что получили”. A case must begin with a distinct client situation and end with a decision or evidenced outcome; never label a deliverable or method component such as a roadmap or application portfolio as a case. Separate generic operating scenarios from concrete measured cases, and retain both only when their evidence level differs clearly. Keep each case slide near 50–80 words plus short labels so methodology does not crowd out the case block.
7. Preserve claim status exactly: historical, calculated, potential, and realized effects are different claims. Upgrade a result to realized only when the user explicitly supplies that evidence. On a one-pager, place the status next to the number in readable type: label a range as potential, mark historical examples as results of separate analogous projects and not a client forecast, and state the dependency on scope/data quality. Do not rely on a tiny footer to qualify a dominant number. Keep unlike KPIs separate: never merge a natural-volume reduction and a monetary saving under one percentage unless the source proves that exact relationship. Match every KPI to the thing being sold: a strategy slide needs evidence about strategy quality, maturity, decision alignment, or goal attainment; do not substitute downstream migration or implementation outcomes.
8. Separate pilot depth from full-model depth. Define pilot outputs as concrete model artifacts and calculations; define full-model outputs as deeper logic and operating capabilities. Avoid presenting pilot work as “confirming potential” when the intended result is current-cost assessment.
9. Validate taxonomy layers before writing scaling slides. Keep cost pools, resources, solutions, and consumers separate; label commercial scopes that cross standard taxonomy objects as offering-specific constructs.
10. For a C-level sales slide about a diagnostic questionnaire, lead with the assessed domains and give each domain a concise business-readable description. Present the offer as a short study based on 1–2 interviews that produces an aggregate maturity score, a domain profile, limiting gaps, and prioritized recommendations. Default to a title plus a one-third sales column and a two-thirds executive scorecard: the narrow column explains what the study is, how it runs, and three client benefits; the main area shows each domain on one common maturity scale with current level, target level, and the gap between them, followed by strong areas, limiting gaps, and priorities. This follows the reusable pattern `overall score → domain profile → current/target gap → actions` and shows the product's result, whereas a radial map mainly explains methodology coverage. Use a circle only when the user's purpose is to explain scope, interdependence, or a cycle. Before assessment, mark any filled profile as an illustrative example rather than client data; alternatively show an unfilled result template. Do not lead with a maturity ladder or explain every score level unless the user explicitly asks. Show a peer benchmark or percentile only when a valid comparative base exists, and keep it distinct from the target profile. If the questionnaire has a fixed recommendation catalog, name its verified size. Use known companies only as sourced public practice anchors, never as if the diagnostic had assigned them a maturity score; add a short disclaimer to that effect.
11. When showing recurring value realization, distinguish strategy, roadmap execution, benefit control/accompaniment, and strategy refresh. State that sustained effect comes from both adaptive strategy revision and ongoing execution support; do not depict a one-way roadmap as the whole strategy.
12. Generate the visual deck only from the approved source. Split one source slide into one visual card, remove production metadata and speaker notes from visible content, and derive the expected card count from the source.
13. Export and verify slide count, aspect ratio, placement of key facts, unchanged appendices, and prohibited content. When PDF and PPTX are generated through separate layout engines, keep one canonical copy block and synchronized geometry; rebuild both after every content or spacing correction so the editable source cannot lag behind the client PDF. Structural/text checks do not substitute for a visual review. For Gamma diagrams, require native editable shapes and text rather than generated images: exports can replace failed diagram images with gray placeholders even when the editor generation reports success. Export both PDF and PPTX, render the PDF, inspect every changed slide, and check minimum font sizes and page bounds programmatically. For a portrait one-pager, inspect the full page and separate top/bottom crops: title wrapping can push the subtitle out of the hero, while metric notes and CTA text can cross card boundaries without being obvious at full-page scale. After every correction, regenerate both formats and inspect the exact final render rather than an earlier preview. If repeated Gamma edits still export the core scorecard or diagram as a placeholder, stop regenerating and build the required visual deterministically as editable PPTX shapes; generate a matching PDF, render it, and run the same fix-and-verify cycle. If a later regeneration regresses to placeholders or loses a working diagram, deliver the last visually verified artifact rather than the newest generation.

## User-facing content rules

- Give each executive role several distinct benefits; keep diagnostic questions in speaker notes.
- Use mechanism slides to explain how information becomes a decision, and case slides to prove what happened.
- Keep a single headline value range and prevent historical percentages from looking like additive promises.
- For a client one-pager, prefer a client-ready PDF plus an editable PPTX source unless the user requests a single format; keep the PDF to exactly one page and verify the PPTX contains one portrait A4 slide.
- Show scalability through peer solution groups rather than a mixed list of technologies, spend classes, and organizational domains.
