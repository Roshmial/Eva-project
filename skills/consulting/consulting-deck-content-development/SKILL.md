# Consulting deck content development

## Workflow

1. Establish the canonical artifact. If the user declares a Markdown brief the base, edit and agree that file first; do not change Gamma or another visual deck until explicitly asked.
2. Classify every slide before writing: executive summary, role value, mechanism, case, operating cycle, scaling, delivery, governance, or commercial close. When adapting an approved reference, build a numbered slide-function map and preserve both sequence and block allocation; six reference case slides remain six case slides unless the user explicitly approves a new storyline. Remove slides that only repeat the next slides.
3. Write conclusion-led titles that state the decision, benefit, or outcome. Avoid process labels and constructions of the form “не X, а Y”; state the positive conclusion directly.
4. Keep one offer name throughout. Describe embedded calculation methods as part of the offer instead of creating a second product by wording.
5. Normalize evidence slides to a compact, repeatable shape. For proposed use cases use “Ситуация → Что сравниваем/рассчитываем → Решение → Потенциальный эффект”; for historical evidence use “Ситуация → Что сделали → Что получили”. A case must begin with a distinct client situation and end with a decision or evidenced outcome; never label a deliverable or method component such as a roadmap or application portfolio as a case. Separate generic operating scenarios from concrete measured cases, and retain both only when their evidence level differs clearly. Keep each case slide near 50–80 words plus short labels so methodology does not crowd out the case block.
6. Preserve claim status exactly: historical, calculated, potential, and realized effects are different claims. Upgrade a result to realized only when the user explicitly supplies that evidence. Match every KPI to the thing being sold: a strategy slide needs evidence about strategy quality, maturity, decision alignment, or goal attainment; do not substitute downstream migration or implementation outcomes.
7. Separate pilot depth from full-model depth. Define pilot outputs as concrete model artifacts and calculations; define full-model outputs as deeper logic and operating capabilities. Avoid presenting pilot work as “confirming potential” when the intended result is current-cost assessment.
8. Validate taxonomy layers before writing scaling slides. Keep cost pools, resources, solutions, and consumers separate; label commercial scopes that cross standard taxonomy objects as offering-specific constructs.
9. For a C-level sales slide about a diagnostic questionnaire, lead with the assessed domains and give each domain a concise business-readable description. Present the offer as a short study based on 1–2 interviews that produces an aggregate maturity score, a domain profile, limiting gaps, and prioritized recommendations. Default to a title plus a one-third sales column and a two-thirds executive scorecard: the narrow column explains what the study is, how it runs, and three client benefits; the main area shows each domain on one common maturity scale with current level, target level, and the gap between them, followed by strong areas, limiting gaps, and priorities. This follows the reusable pattern `overall score → domain profile → current/target gap → actions` and shows the product's result, whereas a radial map mainly explains methodology coverage. Use a circle only when the user's purpose is to explain scope, interdependence, or a cycle. Before assessment, mark any filled profile as an illustrative example rather than client data; alternatively show an unfilled result template. Do not lead with a maturity ladder or explain every score level unless the user explicitly asks. Show a peer benchmark or percentile only when a valid comparative base exists, and keep it distinct from the target profile. If the questionnaire has a fixed recommendation catalog, name its verified size. Use known companies only as sourced public practice anchors, never as if the diagnostic had assigned them a maturity score; add a short disclaimer to that effect.
10. When showing recurring value realization, distinguish strategy, roadmap execution, benefit control/accompaniment, and strategy refresh. State that sustained effect comes from both adaptive strategy revision and ongoing execution support; do not depict a one-way roadmap as the whole strategy.
11. Generate the visual deck only from the approved source. Split one source slide into one visual card, remove production metadata and speaker notes from visible content, and derive the expected card count from the source.
12. Export and verify slide count, aspect ratio, placement of key facts, unchanged appendices, and prohibited content. Structural/text checks do not substitute for a visual review. For Gamma diagrams, require native editable shapes and text rather than generated images: exports can replace failed diagram images with gray placeholders even when the editor generation reports success. Export both PDF and PPTX, render the PDF, inspect every changed slide, and check minimum font sizes and page bounds programmatically. If repeated Gamma edits still export the core scorecard or diagram as a placeholder, stop regenerating and build the required visual deterministically as editable PPTX shapes; generate a matching PDF, render it, and run the same fix-and-verify cycle. If a later regeneration regresses to placeholders or loses a working diagram, deliver the last visually verified artifact rather than the newest generation.

## User-facing content rules

- Give each executive role several distinct benefits; keep diagnostic questions in speaker notes.
- Use mechanism slides to explain how information becomes a decision, and case slides to prove what happened.
- Keep a single headline value range and prevent historical percentages from looking like additive promises.
- Show scalability through peer solution groups rather than a mixed list of technologies, spend classes, and organizational domains.
