# When to use
Use when the user asks for:
- text for a presentation or slide;
- a short market/system/vendor comparison to paste into PPT/DOCX;
- a concise list of platforms/products/cases with links;
- an executive summary where over-expansion harms readability.

## Core rule
Default to a **one-slide-first** delivery unless the user explicitly asks for a deck, several slides, or a detailed appendix.

# Output shape
1. Give a short title or framing sentence.
2. Give 3-5 compact bullets or 1 short paragraph plus bullets.
3. If products/systems are listed, add vendor links inline or as a short link list.
4. Keep wording presentation-safe: short, precise, and defensible.

# Scope discipline
- Do not call a list "full" unless it was actually verified as market-complete.
- Prefer labels such as "топ-5", "ключевые", "наиболее релевантные", or "подтвержденные в открытых источниках".
- If evidence is partial, say so briefly and move on.

# Comparison rules for systems/platforms
When comparing systems:
- separate **specialized performance/KPI systems** from **broader HR/HCM cores with KPI features**;
- avoid duplicative confusion such as treating a specialized add-on and a base HR core as the same class;
- if a product is retired/discontinued, flag that clearly before including it in a top list;
- prefer current vendor pages over secondary rankings when validating product existence.

# Evidence rules
Split mentally into:
- confirmed facts from vendor or credible project/case source;
- reasonable interpretation;
- unknown / not publicly confirmed.

Never upgrade "mentioned in a conference note" into a fully documented case with proven outcomes.

# User-specific delivery lessons embedded
For this user, poor delivery patterns in this task class were:
- expanding a one-slide ask into a 10-slide structure;
- labeling a shortlist as "full" without verifying the market;
- leaving product-class distinctions implicit and creating confusion.

Corrective behavior:
- compress first;
- state scope honestly;
- explain class distinctions in one sentence when similar products appear side by side.

## Compressing research into a 5–6 slide executive narrative

When a user asks to adapt an already researched topic into 5–6 slides, do not reproduce the report section-by-section. Rebuild it as a decision narrative:

1. Value proposition / strategic shift.
2. Transformation stages.
3. Confirmed operating cases.
4. Regional or market comparison, when it changes the conclusion.
5. Target operating model.
6. Constraints, process changes, and realistic horizon.

For a deck built from external research:
- distinguish confirmed live cases, announced initiatives, and vendor marketing claims directly in the slide wording;
- give the audience one clear takeaway per slide;
- reserve source links for a small footer or an appendix, rather than filling the body with raw URLs;
- do not treat manufacturers, regulators, and airlines as interchangeable evidence classes: manufacturers show technology horizons, regulators show conditions and limits, airlines show operational adoption;
- make process redesign explicit when proposing an AI-native model: shared KPI, decision rights, exception management, and changed operator roles are part of the transformation.

## Stage-scale integrity in transformation decks

When a deck groups cases by transformation stages, define one scale before assigning any company and carry it identically through the report, comparison matrix, and slides.

For product-led transformation narratives, anchor every stage in three fields:
1. what the passenger buys;
2. one short label for the company's management model;
3. a separately labeled operating result or capability.

Keep each field on one semantic plane across all stages. Do not mix a product label (`Digital service`), a sentence about process (`Functions work separately`), and an outcome (`Preventing disruption`) in the same visual tier. For a passenger-airline transformation, a consistent pair can be:
- Product: Ticket → Digital service → Predictable flight → Protected journey → Guaranteed arrival.
- Management model: Functional management → Digital coordination → Predictive management → Scenario-based network management → End-to-end outcome management.

Show optimization results in a separate row or layer, for example: local efficiency → synchronized service → disruption prevention → network protection → goal preservation.

A useful sequence is: scheduled flight → digital service → predictive operation → network recovery → guaranteed arrival. The labels may change by domain, but the semantic jump between stages must remain stable.

## Maturity-scale integrity: first fix the unit of analysis

Before assigning logos, ask one non-negotiable question: does the slide rate a **specific use case** or the **company as a whole**? These are different deliverables.

### Use-case maturity
A named process may be staged by its strongest confirmed working mechanism. For example, automated passenger recovery can be agentic in that one process while the parent airline remains at an earlier company-wide stage.

### Company maturity
A company-level stage describes the prevailing material operating model across OCC/dispatch, crew, aircraft and maintenance, disruption recovery, turnaround and ground operations. A customer chatbot, a vendor partnership, a laboratory, or even one advanced production case must not elevate the company by itself.

For company-level ratings:
- require regular production use, material scale, and evidence across more than one connected operating function before moving from Digital-native to ML-native;
- require broadly used AI recommendations in operational decisions, with humans retaining authority, before calling a company AI-assisted;
- require delegated cross-functional execution, controls, audit, override and demonstrated scale before calling a company Agentic AI-native;
- use transition placements (`1→2`, `2→3`, `3→4`) when public evidence supports direction but not the full next-stage threshold;
- do not force a quota of companies into every stage. An empty stage, especially Agentic AI-native, can be the central market finding;
- do not infer People-native from a lack of press releases. This requires positive evidence that material processes remain predominantly manual and disconnected.

Rules:
- State the unit explicitly in the title or subtitle: `зрелость компаний в целом` or `зрелость отдельных процессов`.
- If a company publicly claims a later stage but evidence is still mainly strategy or vendor marketing, label it explicitly as a stated target, not as achieved maturity.
- Keep infrastructure enablers such as digital identity, standards, or data exchange outside the airline maturity scale. Explain them as cross-cutting conditions.
- If several companies appear in one visual block, retain a separate stage label for each company. Do not merge companies with different maturity into one blended label.
- Recheck the final deck after revisions: stage names, case labels, product promises, and the declared unit of analysis must use the same wording everywhere.

## Product-led stage slide format

When the user wants the maturity scale shown as a transformation slide, use the same compact fields in every stage:
1. product received by the passenger;
2. management-model label in the same grammatical form;
3. data status;
4. event-response mode;
5. decision owner and basis.

A strong company-level scale is:
- Ticket / Functional management / delayed facts / slow reactive response / person by regulation;
- Digital service / Digital coordination / real-time facts / fast reactive response / rules with human exceptions;
- Predictable flight / Predictive management / facts plus forecast / proactive response / forecast-guided rules and human exceptions;
- Managed route / AI-assisted management / real-time facts, forecasts and alternatives / context-adaptive response / human decision on AI recommendation;
- Timely arrival / Agentic AI-native / continuous data and forecast / proactive autonomous response / AI execution with human control.

Do not shorten the middle row into prose that shifts semantic plane. It must remain a management-model label across all five stages.

# Example micro-template
Заголовок: <1 sentence>

Краткий ввод: <1-2 sentences on what this class of systems gives the business>

Топ-системы:
- <system 1> — <5-10 words of why it matters>
- <system 2> — <5-10 words>
- ...

Сноска по охвату:
- Список отражает <top/key/relevant/confirmed> решения и не претендует на полный рынок без отдельной верификации.
