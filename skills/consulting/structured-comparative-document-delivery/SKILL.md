# structured-comparative-document-delivery

## Когда применять

Используй этот навык, когда нужно:
- переработать клиентский аналитический документ, исследование, memo, briefing или большой раздел отчета;
- перевести текстовую «простыню» в структурированные таблицы;
- сравнивать решения, продукты или вендоров по единой рамке критериев;
- несколько раз перестроить раздел по обратной связи пользователя без потери фактов;
- сделать раздел полезным для заказчика, а не просто описательным.

Типичный сигнал: пользователь говорит что-то вроде:
- «не оно»;
- «не так понял задачу»;
- «нужны единые таблички по классам»;
- «каждую систему сравнивать по одним и тем же блокам»;
- «где нет информации, так и пиши: нет данных».

## Цель

Не просто красиво переписать текст, а довести документ до формата, в котором:
- структура соответствует последнему пользовательскому указанию;
- логика сравнения прозрачна;
- дефицит данных обозначен честно;
- выводы пригодны для принятия решений.

## Рабочий протокол

### 1. Сначала зафиксируй текущий режим сравнения

Перед правкой явно определи, чего пользователь хочет сейчас:
- сравнение **по классам решений**;
- сравнение **посистемно**;
- единые таблицы по классам, но с комментариями внутри ячеек;
- одинаковая рамка критериев для всех решений;
- универсальный шаблон по блокам без рейтинговых ярлыков.

Важно: если пользователь несколько раз менял формат, приоритет всегда у **последней формулировки**, а не у предыдущих договоренностей.

### 2. Не смешивай разные режимы подачи

Если пользователь просит:
- **«по классам»** — не скатывайся в длинные посистемные абзацы;
- **«каждую систему по 10 блокам»** — не подменяй это агрегированной картиной по классу;
- **«единые таблицы»** — не возвращай текстовую россыпь;
- **«без оценок»** — не добавляй скрытые рейтинговые ярлыки вроде «сильная / слабая», «высокий / низкий», если это не было прямо согласовано.

### 3. При дефиците данных разделяй две вещи

Никогда не смешивай:
1. **статус наличия данных**;
2. **рекомендацию, что уточнять у вендора / поставщика**.

Это разные сущности и они должны жить отдельно.

### 4. Используй явный словарь статусов данных

Когда информации не хватает, пиши прямо одним из стандартных статусов:
- `есть данные`;
- `частично раскрыто`;
- `публично не раскрыто`;
- `данных недостаточно`;
- `нет данных`;
- `нужно уточнить`.

`Нужно уточнить` — это не замена отсутствующим данным. Это отдельная рекомендация после честной маркировки статуса.

### 5. Табличная логика для клиентского документа

Если нужен практичный раздел, таблица обычно должна отвечать минимум на четыре вопроса:
- что известно по открытому контуру;
- чего по открытому контуру не хватает;
- что именно нужно уточнить;
- как это влияет на выбор или риск.

Минимально полезные строки в сравнительной таблице:
- блок / критерий;
- что видно по открытому контуру;
- что лучше уточнять;
- при необходимости — комментарий о риске или управленческом значении.

### 6. После каждой крупной правки проверяй не обещание, а факт

Если задача про документ, deliverable — это реально обновленный артефакт.
Нельзя останавливаться на фразах:
- «я переделала»;
- «теперь логика такая-то»;
- «раздел исправлен».

Нужно довести до подтверждаемого результата: файл реально пересобран, версия реально обновлена.

Минимальный цикл проверки после структурной правки:
1. внести change через `patch`, а не через полную перезапись файла, если меняется только раздел;
2. перечитать именно измененный диапазон файла;
3. пересобрать артефакт, если пользователь работает с `.docx`, `.pptx`, экспортом или другой производной формой;
4. только после этого описывать результат пользователю.

## Специальные правила для Миши

### 1. Не маскировать отсутствие данных умными формулами

Запрещенные подмены, если на деле данных нет:
- «критично понимать»;
- «важно уточнить»;
- «нужно подтверждать»;
- «следует отдельно выяснить».

Такие формулы допустимы только в строке рекомендаций, но не вместо статуса данных.

Вместо этого:
- сначала пиши `публично не раскрыто` / `данных недостаточно` / `нет данных`;
- потом отдельно — что именно имеет смысл уточнить.

### 2. Документ должен быть полезен заказчику

Не ограничивайся описанием «что это за продукт». Показывай:
- что реально можно понять из открытых материалов;
- что рынок обычно не раскрывает;
- где основная зона риска;
- какие вопросы нужно вынести на demo / техсессию / коммерческое обсуждение.

### 3. Не спорь с последней корректировкой пользователя

Если пользователь сначала просил один формат, а потом сменил логику, не пытайся сохранять старую структуру ради внутренней последовательности. Надо перестроить раздел под последнюю команду.

## Шаблоны подачи

### Вариант А. Единые таблицы по классам решений

Используй, когда пользователь хочет именно группировку по классам.

Логика:
- один класс решений = одна таблица;
- столбцы = решения внутри класса;
- строки = единые блоки оценки;
- внутри ячеек = краткий содержательный комментарий.

Под таблицей или внутри таблицы отдельно показывай:
- что видно по открытому контуру;
- что лучше уточнять.

### Вариант Б. Посистемное сравнение по единой рамке

Используй, когда пользователь хочет, чтобы **каждая система** проходила по одним и тем же блокам критериев.

Логика:
- одно решение = один структурированный блок;
- внутри блока одинаковые критерии для всех;
- без общего балла, если он не согласован.

## Питfall'ы

### Питfall 1. Преждевременный отчет о том, что все уже переделано

Если документ еще не обновлен фактически, нельзя писать пользователю, что задача уже решена.

### Питfall 2. Подмена статуса данных рекомендацией

Фраза вроде «критично понимать, как устроен lifecycle моделей» не сообщает, есть ли данные. Это плохая подача.

Правильная форма:
- `публично не раскрыто, как устроен lifecycle моделей`;
- `лучше уточнить: версии пайплайна, роли, контроль релизов, traceability`.

### Питfall 4. Полная перезапись файла там, где нужен локальный ремонт

Если пользователь просит переделать один раздел, не надо по умолчанию переписывать весь документ через `write_file`.
Это повышает риск:
- потерять ранее согласованные правки в соседних разделах;
- незаметно откатить удачные формулировки;
- потом отчитываться по памяти, а не по фактическому состоянию файла.

Предпочтение по умолчанию:
- локальный `patch`;
- затем `read_file` по измененному диапазону;
- затем пересборка итогового артефакта.

## Критерии качества перед отдачей

Проверь:
- документ реально обновлен, а не только описан;
- текущий формат соответствует **последнему** запросу пользователя;
- одинаковые сущности сравниваются одинаково;
- разные классы решений не сведены в ложную единую плоскость, если пользователь это запретил;
- дефицит данных помечен честно;
- рекомендации не подменяют факты;
- таблицы читаются как рабочий инструмент для заказчика.

## Когда дополнять references/

Если в сессии накопились:
- конкретные словари статусов;
- типовые формулировки для секций документа;
- удачные шаблоны строк сравнительных таблиц;
- выдержки из внешних источников, на которые потом придется снова опираться,
сохраняй их в `references/` как компактные заготовки для следующих проходов.
