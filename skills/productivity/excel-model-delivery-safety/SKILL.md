# Excel model delivery safety

## Delivery rules

- Lock the target Excel runtime before choosing the implementation: exact generation (for example Office 2019 versus Microsoft 365), desktop/web, macro policy, internet availability, and permission to install add-ins or runtimes. Do not build first and discover compatibility from the user's repair dialog.
- Python in Excel is a Microsoft 365 cloud capability. Never package `_xlfn.PY` or `pythonScripts.xml` for Office 2019, call it offline, or present it as a zero-dependency workbook; Office 2019 will remove unsupported formulas during repair.
- For a requested single-file workbook, reject any architecture that still depends on an external interpreter, add-in, web service, or unsupported calculation engine. If the required optimizer cannot run natively in the declared Excel version, state the architectural constraint before producing an artifact and offer a portable executable or an explicitly scoped VBA rewrite.
- Lock the delivery artifact as well as the Excel runtime: distinguish a Python script, a double-click launcher, an embedded Excel module, and an autonomous desktop application before implementation. If the user asks for a ready `.exe` with file selection, provide a standalone Windows GUI with a native `.xlsx` picker and no Python/runtime installation; do not relabel a `.cmd` bootstrapper as an application. The application must write a new output workbook beside the selected source and must not overwrite the source.
- When cross-compiling a Windows GUI without a Windows host, separate a portable calculation core from the platform UI. Run the identical core end-to-end on the authoritative workbook, verify the PE architecture, output ZIP/XML, source hash, and changed OOXML parts, but mark the native file dialog, SmartScreen behavior, and Excel refresh as externally unverified until a real Windows test. Ship an SHA-256 checksum and state when the binary is unsigned.
- Treat Microsoft Excel compatibility as the acceptance target when the user will open the workbook in Excel. A successful LibreOffice recalculation and ZIP integrity check are necessary but insufficient.
- Never reserialize complete worksheet XML with generic XML libraries for cosmetic edits. This can remove Excel namespaces such as `x14`, `xr2`, `mc`, and `xdr`, causing Excel to replace worksheet components even though LibreOffice still opens the file.
- After the final tabular-engine save, do not apply direct worksheet XML rewrites. Prefer losing cosmetic tab colors over risking workbook repair.
- Preserve a clean pre-cosmetic engine-saved artifact and compare hashes before delivery.
- Validate formulas after a real recalculation, verify no `#REF!`, `#N/A`, or `#VALUE!`, and confirm user-input data against the authoritative source workbook.
- Translate every agreed business requirement into an executable acceptance assertion before building. Validate at the same grain as the requirement: a rule for every product-month cohort must be recomputed for every cohort, never replaced by a portfolio average, maximum threshold, or summary status. A technically valid workbook with weaker business semantics is a failed artifact.
- For optimization workbooks, keep separate evidence for feasibility and optimality. Prove integer/nonnegative quantities, all business constraints, and independent recomputation of costs first; claim “minimal overage” or “optimal” only when the exact search/solver supplies a bound or exhaustive proof. Label heuristics and time-limited incumbents explicitly.
- When full cost includes paid staff, idle capacity, licenses, and other shared resources, implement the agreed allocation to each sale cohort before checking margin. Do not infer cohort margin from aggregate portfolio margin; aggregation can hide unprofitable products.
- For role-based multi-user models, separate visible input surfaces by data owner and keep complex calculation sheets hidden. Use numeric zero for blank numeric links and empty text only for identifiers/text fields; empty strings in arithmetic may create `#VALUE!`.
- When repairing a user-provided reference workbook, treat it as authoritative for user data. Restore formulas from a compatible donor only after proving sheet/row alignment and preserving every non-formula input value.
- ZIP validity, OOXML parsing, macro extraction, and local execution of copied calculation code do not prove that Excel will retain formulas or execute the workbook. For `.xlsm` and version-specific features, require a native acceptance test in the exact target Excel version: open without a repair log, compile the VBA project, confirm formulas remain, click each user-facing button, verify the real calculation and outputs, save, close, and reopen. If that runtime is unavailable, label the workbook as a compatibility-test build rather than a finished working tool.
- Before attaching any workbook, reconcile it against a requirements matrix with three states: verified, externally blocked, failed. Never promote a structural smoke-test workbook or a delegated implementation claim to final delivery while a mandatory business assertion is failed or unverified. If a delivered candidate is later found semantically wrong, revoke it explicitly and use a new filename/version so the user cannot confuse it with the corrected artifact.
- Keep VBA failure paths independent of partially initialized objects: capture `Err.Number` and `Err.Description` first, and check `Not ws Is Nothing` before writing status to a worksheet. This prevents a missing or repaired sheet from hiding the root cause behind runtime error 91.
- If desktop Microsoft Excel is unavailable, state that limitation explicitly and ask for the Excel repair report after the user's first open. Do not claim Excel compatibility solely from LibreOffice tests.
