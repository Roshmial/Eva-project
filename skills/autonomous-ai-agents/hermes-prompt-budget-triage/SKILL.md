# Hermes prompt-budget triage

## Когда использовать

Используй этот навык, когда симптом похож на один из таких:
- Hermes стал многословнее без пользы;
- ухудшилась дисциплина tool use;
- агент хуже держит инструкции, формат или русский стиль;
- качество заметно просело после добавления skills, toolsets, memory/profile записей или новых правил;
- нужно понять, проблема в модели/провайдере или в раздутом fixed prompt surface.

Это не общий навык по настройке Hermes. Это точечная процедура ранней диагностики.

## Почему это high-leverage

`hermes prompt-size` работает офлайн и быстро показывает фиксированную нагрузку до пользовательского запроса:
- system prompt;
- skills index;
- memory;
- user profile;
- tool schemas.

Если этот слой уже раздут, агент начинает тратить контекст не на задачу, а на обслуживающую обвязку. В таких случаях смена модели или длинные рассуждения часто лечат симптом, но не причину.

## Минимальная процедура

1. Зафиксируй симптом.
- Что именно ухудшилось: краткость, tool discipline, точность, follow-through, русский язык, качество live-verification.

2. Сними prompt budget.
- `hermes prompt-size --platform cli --json`
- если проблема проявляется в gateway, дополнительно:
  - `hermes prompt-size --platform telegram --json`
  - или нужную платформу.

3. Проверь, не в локальных ли кастомизациях причина.
- `hermes --safe-mode --help`
- при необходимости изолированный oneshot:
- `hermes --ignore-user-config --ignore-rules -z "<короткий воспроизводимый запрос>"`

4. Разложи вклад по слоям.
- Смотри не только на total bytes, но и на крупнейшие компоненты.
- Обычно первыми кандидатами на cleanup являются:
  - лишние toolsets и тяжёлые tool schemas;
  - разросшийся system prompt;
  - skills index с большим числом редко полезных навыков;
  - memory/profile записи, которые перестали быть high-signal.

5. Исправляй самый большой и наименее ценный слой.
- Не начинай со смены модели, если основной вес сидит в fixed prompt.
- Не создавай новый infrastructure path, если хватает локального cleanup:
  - отключить неиспользуемые toolsets;
  - сократить или архивировать слабополезные agent-created skills;
  - убрать дубли и устаревшие memory/profile entries;
  - переписать слишком длинный skill так, чтобы trigger и procedure остались, а балласт ушёл.

6. Перемерь после изменения.
- Повтори `hermes prompt-size ... --json`.
- Если менялась runtime-конфигурация, проверь вступление в силу через новую сессию или restart, где это требуется.

## Как интерпретировать результат

Сильный сигнал проблемы есть, когда:
- fixed prompt surface выглядит большим сам по себе и съедает заметную часть доступного контекста ещё до задачи;
- largest contributors явно не соответствуют частоте их реального использования;
- tool schemas занимают непропорционально много при задачах, где половина toolsets не нужна;
- skills index разросся быстрее, чем выросла полезность ответов.

Практическое правило:
- если деградация похожа на «стал тупее/болтливее/хуже пользуется инструментами», `prompt-size` нужно запускать в самом начале, а не в конце после долгих гипотез.

## Наблюдение, подтверждённое в live-проверке

В текущем профиле `default` live-замер показал fixed prompt порядка 146 KB и на `cli`, и на `telegram`, при этом крупнейшие слои были:
- tool schemas — около 42%;
- system prompt — около 38%;
- skills index — около 16%.

Это не универсальная норма и не жёсткий лимит, а operational signal: при похожих симптомах сначала нужно проверять prompt surface, а потом уже спорить о модели.

## Чего не делать

- Не лечить всё сменой провайдера без измерения prompt budget.
- Не придумывать новые демоны, БД и внешние сервисы для задачи, которая решается локальным cleanup.
- Не сокращать полезные инструкции вслепую; сначала смотри, какой слой реально самый тяжёлый.
- Не считать `hermes-agent` skill достаточной заменой этой процедуре: общий справочник полезен, но в инциденте нужен короткий runbook.

## Проверка

Перед финальным выводом убедись, что есть:
- live output от `hermes prompt-size`;
- при необходимости live output от `--safe-mode` или `--ignore-user-config --ignore-rules`;
- конкретный самый тяжёлый слой;
- конкретное локальное действие, которое уменьшает surface;
- повторный замер после изменения, если изменение уже было внесено.
