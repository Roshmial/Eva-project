# Когда использовать

Используй этот навык, когда нужно проектировать, чинить или проверять в local-first web UI:
- список задач и карточки задач;
- ручное назначение получателей задачи;
- self-subscribe / unsubscribe пользователей;
- доставку результатов задач в отдельные job-чаты;
- согласованность frontend, backend, БД и live runtime для job-delivery flows.

# Цель

Сделать модель рассылки понятной и управляемой:
- создатель/админ явно назначает получателей;
- self-subscribe существует как отдельный, управляемый механизм;
- доставка идёт в отдельные job-чаты, а не в исходные пользовательские/рабочие чаты;
- UI не захламлён техническими полями, которые мешают чтению списка задач.

# Базовая модель, которую нужно удерживать

Разделяй два механизма и не смешивай их в формулировках и коде.

1. Назначенные получатели
- Это основной механизм.
- Создатель или админ вручную добавляет пользователей и/или чаты как источники доставки.
- На backend это обычно отдельный список recipients (`fixed_user`, `fixed_thread`, и т.п.).

2. Самоподписка пользователей
- Это дополнительный механизм.
- Пользователь сам включает или выключает получение задачи только если это разрешено настройками задачи.
- На backend это должен быть отдельный контур subscriptions, а не переиспользование recipients.

# Обязательные продуктовые правила

## 1. Self-subscribe не должен быть безусловным

Если self-subscribe оставляют в продукте, у задачи должны быть явные настройки:
- `self_subscribe_enabled` — включено/выключено;
- `self_subscribe_scope` — кто может подписываться.

Минимально достаточные scope для MVP:
- `disabled`
- `visible_users`
- `workspace`

Смысл:
- `disabled` — самоподписка выключена;
- `visible_users` — подписаться может тот, кто уже видит задачу;
- `workspace` — подписаться может любой активный пользователь workspace.

## 2. Проверка должна быть не только на фронте

Никогда не ограничивай self-subscribe только скрытием кнопки.

Обязательно:
- backend endpoint `/subscribe` должен валидировать `self_subscribe_enabled` и `self_subscribe_scope`;
- backend должен возвращать явную ошибку, если самоподписка запрещена;
- frontend должен использовать backend-флаг вида `can_self_subscribe`, а не гадать по роли пользователя.

## 3. Доставка — в отдельный job-чат

Если пользователь или чат выбран как получатель, delivery model должна быть такой:
- backend резолвит целевого пользователя;
- затем создаёт или использует отдельный `job`-thread / `job`-chat;
- сообщение отправляется туда, а не в исходный выбранный chat-thread.

Это особенно важно для сценария `fixed_thread`: выбор чата не означает отправку в этот чат. Чат нужен как способ определить владельца/контекст, а результат должен жить в отдельном job-чате задачи.

# Правила для UI

## Общее пользовательское название задачи

Если пользователь говорит, что «техническое название не передаёт содержание», по умолчанию разделяй два имени задачи:
- `name` — техническое/служебное название;
- `display_name` — общее пользовательское название, одинаковое для всех пользователей.

Правила реализации:
- общее название должно храниться в backend/БД, а не в `localStorage` и не в browser-only draft;
- frontend должен показывать `display_name` как основное читаемое имя, а при пустом значении делать fallback на `name`;
- в detail view техническое имя нужно оставлять отдельно и явно подписывать как техническое, а не подменять им пользовательское название;
- для editable local jobs изменение общего названия лучше проводить через существующий `PATCH /api/jobs/<job_id>`, а не через отдельный специальный endpoint, если текущий API уже позволяет обновлять job-поля.

Чего не делать:
- не оставляй параллельно два источника правды: backend `display_name` и frontend alias в `localStorage`;
- не выдавай browser-local alias за «сохранённое название задачи» — это создаёт ложное ощущение общей модели, хотя другие пользователи его не увидят;
- не переименовывай ради этого техническое `name`, если пользователь просил его сохранить.

Отдельно проверяй mixed-source сценарий:
- для локальных Web MVP jobs `display_name` можно делать редактируемым серверным полем;
- для импортированных / read-only Hermes cron jobs сначала проверь, действительно ли текущий backend-мост поддерживает такое поле. Не притворяйся, что локальная модель названий уже автоматически распространяется на read-only cron-источники.

Приёмочный минимум для этого класса правок:
1. миграция/добавление поля в БД;
2. сериализация `display_name` в list/detail API;
3. сохранение через create/update/PATCH;
4. UI fallback `display_name -> name`;
5. smoke-проверка, что один пользователь сохранил название, а другой увидел то же значение.

## Список задач

Если пользователь жалуется, что карточки задач перегружены, по умолчанию сокращай список до трёх вещей:
- название;
- техническое имя;
- статус.

Не тащи в список вторичные технические поля вроде:
- расписание (`каждый день` и т.п.);
- приватность / visibility;
- служебные recipient summaries;
- пометки про отдельные job-чаты.

Такие поля уместнее в detail view или в модалке редактирования.

## Модалка редактирования задачи

Если self-subscribe поддерживается, в модалке нужен отдельный блок:
- переключатель режима (выключена / разрешена);
- выбор scope;
- короткая подсказка, что self-subscribe не заменяет ручное назначение получателей.

Подсказка должна разделять смыслы:
- recipients задаёт админ/создатель;
- subscriptions включает сам пользователь, если это разрешено.

## Detail и модалка не должны прятать модель доставки в техничке

Если пользователь жалуется, что экран задач перегружен или непонятен, сначала упрощай продуктовую модель, а не косметику.

Минимальные правила для detail view:
- не держи один смешанный блок вроде `Приватность и доставка`, если он одновременно показывает visibility, source-of-truth и recipients;
- не выводи в основной detail шумные служебные поля вроде raw `Источник`, `source_of_truth`, JSON `Параметры и контекст`, если они не нужны пользователю для ежедневной работы;
- разведи два отдельных блока:
  - `Кто видит задачу` — доступ к просмотру и управлению;
  - `Кому приходит результат` — список фактических получателей результата;
- в каждом блоке дай короткую поясняющую фразу, что это разные сущности и они не заменяют друг друга.

Практическое правило copy:
- `доступ` != `доставка`;
- `получатели` != `самоподписка`;
- `чат-источник` != фактический target доставки, если продуктовая модель создаёт отдельный job-чат.

## Подбор получателей должен быть отдельным действием, а не длинным ковром чекбоксов

Если задача редактируется в модалке, не прячь работу с получателями в бесконечный блок `настроек`.

Предпочтительный паттерн:
- в detail view отдельная кнопка `Добавить получателей`;
- в модалке отдельный блок `Кому приходит результат`;
- в верхней части блока — текущий список уже выбранных получателей;
- ниже — явное действие `+ Добавить получателей`, которое раскрывает picker;
- picker по умолчанию можно держать свернутым, чтобы не раздувать форму, пока пользователь не начал подбор.

Для access действует похожее правило:
- `+ Добавить доступ` должен быть отдельным действием;
- доступ не должен быть визуально смешан со списком получателей.

Критически важное уточнение для detail view:
- кнопки `Добавить получателей` и `Добавить доступ` не должны открывать полную modal `Управление задачей` / `Редактирование задачи`, если пользователь хочет только точечно изменить состав людей;
- для этих действий нужен отдельный узкий picker / modal выбора пользователей;
- полную форму задачи оставляй для `Открыть настройки`, `Редактировать` или `+ Новая задача`, а не для мелких membership-операций.

Минимальный UX-паттерн:
- detail -> `Добавить получателей` -> открывается только выбор получателей;
- detail -> `Добавить доступ` -> открывается только выбор пользователей для доступа;
- внутри picker не тащи расписание, prompt, deliver и остальные поля общей настройки задачи.

## Для рассылки по людям фильтруй по пользовательским признакам

Если в рабочей области больше нескольких пользователей, не оставляй подбор получателей простым длинным списком.

Минимально полезные фильтры для recipient picker:
- `Имя или email`;
- `Роль`;
- `Подразделение` / team.

Желательное поведение:
- текстовый поиск ищет минимум по `name`, `email`, `role`, `team`, `title`;
- пользователь видит выбранных получателей отдельно от полного списка кандидатов;
- пустой результат фильтра честно показывается отдельным сообщением, а не пустым белым блоком.
- кнопки точечных действий в detail/picker держи компактными; не раздувай `Добавить получателей` и `Добавить доступ` до визуального доминирования над содержимым карточки.
- карточки/плашки пользователей в picker должны быть плотными: умеренные padding/gap, короткая вторичная строка, без ощущения «гигантских плиток», если задача — быстрый выбор людей, а не подробный профильный просмотр.

## Кнопка подписки в detail view

Кнопку `Добавить в рассылку` / `Убрать из рассылки` показывай не по грубой роли (`viewer`, `subscriber`) и не для всех подряд, а по условию:
- пользователь уже подписан; ИЛИ
- backend сказал, что `can_self_subscribe = true`.

# Backend checklist

При внедрении self-subscribe проверь все слои:

1. Схема БД
- новые поля в `jobs`;
- миграция существующей БД через `ensure_column` или эквивалент.

2. Нормализация payload
- валидация `self_subscribe_scope`;
- принудительный `disabled`, если флаг выключен.

3. Serialization
- job detail/list должны возвращать:
  - `self_subscribe_enabled`
  - `self_subscribe_scope`
  - `can_self_subscribe`
  - `is_subscribed`

4. Create / Update SQL
- новые поля должны реально сохраняться и обновляться, а не только жить в frontend draft.

5. Subscribe endpoint
- проверка правил self-subscribe;
- понятная ошибка при запрете.

# Runtime verification checklist

Не считай задачу завершённой, пока не проверены оба аспекта: модель получателей и живая доставка.

Минимальный live-pass:
1. Создать/обновить задачу с новыми настройками self-subscribe.
2. Проверить, что UI сохранил значения и корректно их перечитал.
3. Проверить сценарий `disabled`:
- обычный пользователь не видит кнопку или получает запрет при subscribe.
4. Проверить сценарий `visible_users` или `workspace`:
- пользователь может подписаться.
5. Запустить задачу и подтвердить по runtime/БД/истории доставку в отдельный `job`-чат.
6. Если выбран конкретный chat-thread как recipient source, дополнительно проверить, что сообщение не ушло в исходный чат.

# Hermes cron vs local Web MVP jobs

Если в одном UI смешаны:
- локальные задачи Web MVP;
- импортированные/bridge-задачи Hermes cron,

не пытайся бездумно уравнивать их внутреннюю модель, но и не считай cron-задачи по определению «нередактируемыми» для продуктовой маршрутизации.

Правильное разделение такое:
- Hermes cron остаётся source of truth для `schedule`, `prompt`, базового `deliver` и факта запуска.
- Web backend может и должен держать поверх этого product-level overlay для recipients, если пользовательский сценарий требует назначения получателей администратором.
- Для cron-задачи допустима двухслойная модель:
  - слой Hermes: raw `deliver` и cron runtime;
  - слой Web: назначенные пользователи/чаты-источники, отдельные job-чаты и fan-out результата.

Практическое правило проектирования:
- если пользователь говорит, что «администратор должен назначать получателей cron-задачи», не отвечай reflex-логикой «у Hermes cron есть только deliver»;
- сначала раздели `базовый transport target Hermes` и `продуктовую адресацию внутри Web`;
- затем добавь overlay-хранилище recipients в backend, вместо попытки втиснуть всё в raw `deliver` UX.

Рекомендуемый минимальный паттерн для Hermes cron в local-first Web:
1. Не переписывай расписание и не дублируй cron scheduler внутри Web.
2. Храни admin-managed recipients отдельно от локальных `job_recipients` local jobs, если cron job id текстовый и живёт вне local `jobs.id`.
3. Привязывай отдельные job-чаты по `external_job_id` / `hermes_job_id`, а не только по integer `job_id`.
4. Забирай готовый результат из локальных артефактов Hermes (`~/.hermes/cron/output/<job_id>/*.md`), если это уже существующий рабочий путь.
5. Доставляй результат каждому назначенному пользователю в отдельный job-чат.

Что показывать в UI:
- `deliver` по-прежнему полезно показывать как transport/source detail;
- но блок `Кто получает результат` для cron-задачи может быть полноценным admin-managed picker пользователей, если backend поддерживает overlay recipients;
- пояснение должно честно говорить: расписание и базовый deliver живут в Hermes, а маршрутизация по пользователям управляется через Web API.

Когда НЕ надо ограничиваться только `deliver`:
- если есть явный сценарий дайджестов/рассылок, где один cron-run должен быть разложен по нескольким людям;
- если пользователь прямо требует, чтобы администратор назначал получателей внутри продукта;
- если результат должен приходить не в один общий чат/target, а в отдельные job-чаты разных пользователей.

Если bridge-модель cron уже отдаёт `deliver`, detail view не должен подменять продуктовую модель фиктивным recipient вроде `Администратор`; показывай либо реальный transport target, либо overlay recipients, либо оба слоя с понятными подписями.

См. также session reference: `references/hermes-cron-routing-overlay.md`.

# Типовые ловушки

- Смешать recipients и subscriptions в один смысловой слой.
- Спрятать кнопку на фронте, но оставить backend subscribe без проверки.
- Считать, что `fixed_thread` означает доставку в этот же thread.
- Пытаться редактировать Hermes cron job теми же полями, что и локальную Web MVP задачу.
- Упереться в ложную дихотомию: либо raw `deliver`, либо вообще никакой продуктовой маршрутизации для Hermes cron. Для cron-задач часто нужен overlay recipients поверх базового Hermes transport.
- Показывать для cron-задачи фиктивный recipient вместо реального `deliver` target или overlay recipients.
- Хранить user-facing routing Hermes cron задач только в raw `deliver`, если по продуктовой модели нужны отдельные job-чаты на пользователей.
- Засорить список задач полями, полезными только разработчику, а не пользователю.
- Проверить только код и не подтвердить реальный runtime с фактическим `job`-thread.

# Что говорить пользователю

Если пользователь говорит «админ может сам подписывать пользователей», уточняй и проговаривай модель прямо:
- админ назначает получателей задачи;
- пользовательская self-subscribe — отдельный дополнительный контур;
- доступность self-subscribe управляется параметрами задачи.

Не называй ручное назначение recipients и self-subscribe одним и тем же словом без пояснения — это почти гарантированно создаёт путаницу.
