# Session note: Hermes Web MVP jobs UI and delivery semantics

Ключевые прикладные выводы из сессии:

1. Для списка задач пользователь попросил убрать перегрузку и оставить только:
- название;
- техническое имя;
- статус.

2. Важно различать два механизма:
- recipients: админ/создатель вручную назначает пользователей или чаты как получателей;
- subscriptions: пользователь сам подписывается только если это разрешено настройками задачи.

3. Для Hermes Web MVP критично не писать формулировку «рассылка в выбранный чат», если backend модель такая:
- выбранный thread может использоваться как источник владельца/контекста;
- фактическая доставка должна идти в отдельный `job`-chat (`thread_kind='job'`).

4. При реализации self-subscribe нужен единый сквозной набор полей:
- backend DB: `self_subscribe_enabled`, `self_subscribe_scope`;
- backend API: плюс вычисляемый `can_self_subscribe`;
- frontend draft/modal/save: те же поля;
- subscribe endpoint: серверная проверка, а не только скрытие кнопки.

5. Хороший UX-текст для модалки:
- self-subscribe не заменяет ручное назначение получателей;
- назначенных получателей задаёт создатель/админ отдельно.

6. Проверочный минимум после изменений:
- UI перечитывает сохранённые настройки;
- `disabled` реально запрещает подписку;
- `visible_users` или `workspace` реально разрешают её;
- запуск задачи создаёт/использует отдельный job-чат, а не пишет в исходный обычный чат.
