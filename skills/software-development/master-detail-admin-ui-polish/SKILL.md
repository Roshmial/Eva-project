# Когда применять
- Экран админки или рабочего web UI построен как master/detail: список слева или сверху, detail справа или ниже.
- Пользователь говорит, что экран "сыроват", "жирный", слишком крупный, перегруженный карточками или плохо читается на desktop.
- Нужно не придумывать новый продукт, а аккуратно дополировать текущий экран и подтвердить результат по живому runtime.

# Цель
Сделать экран визуально собраннее без полной переработки архитектуры:
- яснее главный сценарий;
- меньше ощущение "карточек в карточках";
- лучше selected-state и связь списка с detail;
- компактнее верхняя панель и метаблоки;
- реальная проверка в браузере, а не только патч в коде.

# Подход
1. Сначала сделать live-аудит экрана.
   - Зафиксировать текущую иерархию: header, toolbar, list, detail, secondary sections.
   - Отдельно отметить, где экран визуально тяжёлый: избыток рамок, большие gap/padding, слишком много одинаковых чипов, разнесённые метаданные, лишняя шапочность.
   - Для desktop отдельно смотреть первый экран без скролла.

2. Не раздувать редизайн.
   - Если пользователь просит "дополировать", работай как cleanup pass, а не как rebuild.
   - Сохраняй текущую информационную архитектуру, если проблема решается плотностью, иерархией и ритмом.

3. Править сначала системные источники тяжести.
   Типовые рычаги:
   - уменьшить padding/gap и радиусы в list/detail;
   - сделать toolbar компактнее и ближе к рабочему режиму;
   - усилить selected-state у активного элемента списка;
   - ослабить повторяющиеся статусы и вторичные чипы;
   - собрать растянутые метаданные в компактный mini-summary;
   - убрать лишний повтор имени сущности, если он не даёт новой информации;
   - primary-действие сделать визуально главным, а не равным всем остальным.

4. Для master/detail проверять не только первый элемент.
   - После правок обязательно переключить хотя бы ещё один элемент списка.
   - Подтвердить, что active-state, заголовок detail, вторичный идентификатор и кнопки действий синхронно обновляются.
   - Не считать экран проверенным, если видели только default selection.

5. Проверять runtime в двух плоскостях.
   - Функционально: список переключается, detail меняется, кнопки/фильтры живы.
   - Визуально: иерархия читается, экран стал спокойнее, критических поломок нет.

# Что обычно работает
- Компактный section-toolbar вместо длинной описательной шапки.
- Более плотный list-row/list-card с ясным active-state.
- Detail-hero + короткий summary-column + mini-meta вместо большого растянутого метаблока.
- Перенос вторичных описаний в менее контрастный слой.
- Снижение веса одинаковых статусов, если они повторяются почти у всех элементов.

# Проверка готовности
Считать pass завершённым, только если подтверждено всё ниже:
- экран открыт в live runtime;
- целевой раздел реально активирован;
- хотя бы один дополнительный элемент списка выбран после правок;
- detail показал согласованное обновление данных;
- console без JS errors;
- визуально нет критических развалов layout;
- пользовательская цель закрыта именно на desktop-экране, если жалоба была про desktop-плотность.

# Питfalls
- Не ограничиваться CSS-патчем без runtime-подтверждения.
- Не делать все карточки одинаково важными: это оставляет экран тяжёлым даже после уменьшения отступов.
- Не сохранять лишний дубль имени/slug/source, если он не помогает различать сущности.
- Не проверять только первую выбранную задачу/запись: легко пропустить поломку синхронизации master/detail.
- Если есть пользовательский micro-pass типа "ещё чуть компактнее" или "скрыть блок в welcome/detail", делать точечный второй проход, а не новое переизобретение экрана.

# Когда навык не подходит
- Нужен полный redesign продукта с новой IA.
- Экран ещё функционально сломан, и сначала нужна отладка runtime, а не polish.
- Пользователь просит только продуктовый аудит без изменений в коде.
