# Dashboard fallback and follow-up routing lessons

## Когда обращаться к этой заметке

Используй для live-debugging случаев, когда пользователь говорит, что "дашборд есть, но он пустой / бессмысленный / это не дашборд", и непонятно, виноват renderer или backend payload.

## Реальный паттерн сбоя

В одном живом сценарии пользователь дал нормальный запрос уровня:
- собрать данные из интернета;
- сделать аналитику по истории развития BI-решений и BI-практик;
- вернуть дашборд.

В backend сохранился формально валидный `dashboard_result`, но по сути он был pseudo-dashboard:
- один текстовый summary-абзац;
- `text_list` с оговорками;
- `bar_list` и `pie_list`, построенные не из аналитических данных, а из технического fallback-поля (`source_mode=global_only`, label источника и `ratio=1.0`).

UI-контейнер при этом мог рендериться корректно. Проблема была не в отсутствии окна, а в том, что сам payload был семантически плохим.

## Главный диагностический порядок

Не начинай с предположения "сломался renderer".

Проверь цепочку по порядку:
1. исходный user request;
2. фактически собранные sources/documents/rows;
3. сохранённый `dashboard_result` payload в БД или API;
4. только потом renderer и CSS.

Если `dashboard.sections` уже содержат фальшивые visual blocks, frontend может быть ни при чём.

## Чёткое правило для fallback-визуализации

Нельзя считать допустимым visual fallback, если графическая секция построена только из:
- `source_mode`;
- `global_only` / `local_first` / других routing-policy токенов;
- label источника;
- connector name;
- route name;
- иных технических meta-полей, которые не являются предметом аналитики пользователя.

Практическое правило:
- если у visual section нет real data-bearing items, лучше вернуть честный evidence/text board;
- не дорисовывать `bar_list` / `pie_list` только ради того, чтобы выполнить минимум по количеству секций.

## Что считать real data-bearing item

Visual section считается содержательной, если items несут хотя бы один реальный аналитический срез:
- числовой `value`;
- полезный `ratio`;
- структурное распределение между несколькими категориями;
- timeline/segment comparison, вытекающий из реальных данных.

Один item со значением типа `value="global_only"`, `ratio=1.0` — это не аналитика, а техническая заглушка.

## Правило для коротких follow-up жалоб

Если после `dashboard_result` пользователь пишет короткую проблемную реплику вроде:
- "а где сам дашборд?"
- "это не дашборд"
- "пусто"
- "без данных"
- "не то"

то это нужно трактовать как repair/follow-up к предыдущему dashboard, а не как новый standalone dashboard request по последней короткой фразе.

### Что делать правильно

При таком follow-up:
1. найти предыдущий содержательный `dashboard_result` в треде;
2. найти предыдущий содержательный user request, на который тот dashboard строился;
3. использовать именно его как effective request text для rebuild/repair path;
4. только если предыдущий предмет запроса действительно не найден — идти в clarification.

### Что делать нельзя

Нельзя отвечать пользователю "тема дашборда не указана", если она была явно указана в предыдущем запросе, а текущая короткая реплика — лишь жалоба на качество уже отданного dashboard.

## Архитектурный вывод

Правильная логика такая:
- сначала данные;
- потом аналитическая сборка смысла;
- потом подбор формы под смысл;
- потом renderer, который устойчиво рисует валидный contract.

Неправильная логика:
- любой ценой собрать `dashboard_result` envelope;
- добить его фальшивыми visual sections;
- считать проблему frontend-ошибкой только потому, что "окно нарисовалось".

## Проверка фикса

После правки обязательно проверь два слоя:

1. Локальная тестовая проверка
- unit/smoke test на то, что `normalize_external_dashboard_payload` не добавляет fake visual fallback без реальных data-bearing items;
- test на то, что короткий follow-up про плохой dashboard переиспользует предыдущий тематический запрос.

2. Live runtime verification
- не только health/runtime;
- проверить на реальном thread payload, что effective request text для follow-up резолвится в исходный тематический запрос, а не остаётся короткой жалобой;
- по возможности прогнать безопасный temp-thread сценарий через `process_chat_task`.

## Короткая формула для будущих сессий

Если пользователь говорит "дашборд есть, но это не дашборд":
- сначала докажи, что именно лежит в payload;
- не путай container-render с quality of analytics;
- не рисуй графики из routing metadata;
- короткий complaint-follow-up чини через previous request reuse, а не через новый blank dashboard build.
