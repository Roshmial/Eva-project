# Gateway-coupled web services over SSH tunnels

Короткая памятка для случаев, когда UI открывается через `ssh -L`, а затем внезапно начинает давать `Connection refused`.

## Симптом

- SSH-сессия ещё жива.
- В локальном SSH выводе появляется:
  - `channel ...: open failed: connect failed: Connection refused`
- Раньше тот же URL уже открывался.

## Что это часто значит

Проблема не в самом туннеле, а в удалённом listener.
Туннель успешно приходит на удалённую машину, но на `127.0.0.1:<port>` больше никто не слушает.

## Частая причина

Frontend/backend были запущены как дочерние процессы Hermes gateway или другого управляющего процесса.
Когда родитель перезапустился или упал, дочерние web-процессы получили `SIGTERM` и пропали.
Внешне это выглядит как «туннель сломался», хотя реально умер удалённый сервис.

## Быстрая проверка

1. Проверить listener на удалённой стороне: `ss -ltnp`.
2. Проверить HTTP health локально на сервере.
3. Проверить journald / supervisor logs родительского процесса.
4. Если web-процессы были стартованы из agent-сессии или background tool, проверить, не умер ли сам родитель.

## Надёжный фикс

Для web-сервисов, которые должны жить дольше agent-сеанса, выносить их из lifecycle gateway:
- `systemd --user` unit;
- контейнер с restart policy;
- отдельный process manager.

После перевода обязательно перепроверить:
- `systemctl --user status` или эквивалент supervisor;
- `ss -ltnp`;
- health endpoint;
- только потом — SSH tunnel с клиентской стороны.
