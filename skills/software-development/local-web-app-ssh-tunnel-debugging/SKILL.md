# Когда применять

Используй для локальных или self-hosted web MVP, которые:
- открываются через `ssh -L`;
- имеют отдельные frontend/backend порты;
- ломаются на `Failed to fetch`, CORS или недоступном backend;
- нужно быстро довести до рабочего product-like состояния, а не только “поднять демо”.

Особенно уместно, когда пользователь хочет работать через один проброшенный порт и не хочет вручную объяснять конечному пользователю второй backend URL.

# Принцип

Для tunnel-first сценария по умолчанию делай frontend same-origin точкой входа:
- UI открывается по одному URL;
- запросы идут на `/api` того же origin;
- frontend-сервер проксирует `/api` на backend.

Это обычно надёжнее, чем требовать отдельный туннель на backend-порт или рассчитывать на прямую доступность `127.0.0.1:<backend_port>` на клиентской машине.

# Порядок работы

1. Подтверди фактическую схему доступа.
- Посмотри, как пользователь открывает UI: локально, через SSH-туннель, reverse proxy, Docker port mapping.
- Если есть `ssh -L <front>:127.0.0.1:<front>`, считай single-port UX целевым сценарием, пока не доказано обратное.

2. Проверь, куда реально ходит frontend.
- Ищи абсолютные backend URL в `config.js`, `app.js`, env и HTML.
- Ищи признаки поломанной схемы: `http://127.0.0.1:<backend_port>`, отдельный `apiBaseUrl`, ручной CORS-костыль.

3. Если frontend и backend разведены по портам — сведи их на same-origin.
- Во frontend-конфиге по возможности используй `/api`, а не абсолютный URL.
- Если статика раздаётся простым сервером, добавь небольшой proxy-слой на frontend-порту.
- Не ломай прямой backend-эндпоинт: удобно оставить backend живым на отдельном порту для smoke-проверок.

4. Прогони живые проверки, а не только чтение кода.
- `curl` по frontend URL;
- `curl` по `/api/health`, `/api/service-info`, `/api/setup/status` через frontend origin;
- синтаксические проверки Python/JS;
- smoke-тесты backend;
- при UI-проблемах — headless Chromium/Playwright-скриншот и console errors.
- если пользователь жалуется на внезапный `Connection refused` после того, как всё уже открывалось, отдельно проверь не только сам туннель, но и жизненный цикл удалённого frontend/backend-процесса.

4a. Проверь, не режет ли frontend dev-server внешний host по allowlist.
- Для Vite/аналогичных dev-server туннель может быть поднят корректно, но внешний URL всё равно отдаст `403` / `Blocked request. This host ... is not allowed`.
- В таком случае сначала проверь прямой локальный `200` на frontend, потом внешний host через tunnel, и только после этого меняй frontend config.
- Для Vite рабочий фикс — добавить `server.allowedHosts` и перезапустить frontend-процесс; для временного внешнего доступа допустим широкий режим вроде `allowedHosts: true`, если это осознанный short-lived tunnel.
- После фикса обязательно проверь same-origin API через тот же внешний host, а не только корневую HTML-страницу.

4b. Проверь, не привязаны ли web-сервисы к lifecycle другого процесса.
- Если frontend/backend были подняты как дочерние background-процессы Hermes/gateway/IDE task runner, рестарт родительского процесса может молча их убить.
- В такой схеме SSH-туннель может оставаться поднятым, но на удалённом `127.0.0.1:<port>` уже никто не слушает — пользователь увидит именно `channel ... open failed: connect failed: Connection refused`.
- Для сервисов, которыми пользователь должен пользоваться дольше одной agent-сессии, предпочитай отдельный supervisor: `systemd --user`, контейнерный restart policy, либо явный standalone process manager.
- После перевода под отдельный supervisor перепроверь `ss -ltnp`, HTTP health и статус unit/service, а не ограничивайся одним `curl`.

5. Отдельно проверь, не маскируется ли проблема истории под потерю данных.
- Если пользователь говорит, что «всё обнулилось», не делай вывод о сбросе базы без живой проверки.
- Сначала проверь фактические записи в app DB: количество `threads`, `messages`, последние `updated_at`, последние сообщения.
- Затем проверь те же данные через пользовательский API (`/api/threads`, `/api/threads/<id>`) именно под тем аккаунтом, под которым работает человек.
- Для multi-user MVP частая ловушка — данные в базе есть, но во вьюхе они скрыты фильтрами: `archived`, текущий `user_id`, текущий scope, активная сессия или другой аккаунт.
- Если админская вьюха показывает больше данных, а пользовательская меньше, это ещё не потеря истории; сначала объясни разницу между «данные есть в БД» и «данные видны текущему пользователю».

6. Убери ложные console noise.
- Если всё работает, но в консоли шум из-за `favicon.ico`/аналогичных мелочей, закрой и это.
- Для QA важно отличать реальные runtime-ошибки от мусорных 404.

7. Проверяй тексты интерфейса на продуктовый язык.
- После техфикса пройди видимые кнопки, фильтры, статусы, onboarding и admin blocks.
- Убирай смешение русского и английского в пользовательском UI, если продукт русскоязычный.
- CSS-классы, внутренние enum и API-поля можно оставить англоязычными; пользовательский текст — нет.

7. Для админки показывай не только “чистый старт”, но и рабочую эксплуатацию.
- Явно покажи, где подключается текущая/новая база.
- Покажи путь, env-переменные и что произойдёт при старте, если файла базы ещё нет.
- Если ручной ввод пользователей не подходит, первым делом добавляй импорт по шаблону (`CSV`/`JSON rows`), а уже затем думай про AD/LDAP sync.

8. Для внешних directory-источников сначала делай честную ступенчатую интеграцию.
- Этап 1: диагностика и конфиг-поверхность (`required_env`, status/configured/not configured).
- Этап 2: шаблонный импорт в текущую базу.
- Этап 3: живая AD/LDAP-синхронизация после настройки библиотек и параметров.
- Не выдавай “поддерживается AD” как готовый production sync, если реализована только подготовка к интеграции.

# Проверочный минимум

- UI открывается по одному URL через тот же способ доступа, что использует пользователь.
- Через этот же origin отвечают `/api/health`, `/api/service-info`, `/api/setup/status`.
- Нет блокирующего `Failed to fetch`.
- Нет явной смеси русского и английского в видимой продуктовой поверхности.
- Backend smoke-тесты проходят.
- Если добавлен импорт пользователей, проверь на живой базе временной записью и затем убери её.

# Node

Если нужно обновить Node в пользовательском Linux-окружении без перестройки всей машины:
- сначала выясни текущий путь `node`/`npm` и способ установки;
- если допустим user-local способ, можно использовать отдельный префикс в домашнем каталоге;
- после обновления обязательно перепроверь `node -v`, `npm -v`, синтаксис JS и runtime UI.

Не фиксируй в skill конкретный менеджер версий как единственный правильный путь: это зависит от среды.

# Подводные камни

- `browser_navigate`/встроенный browser snapshot может вести себя иначе, чем реальный Chromium. Если snapshot пустой, это не доказательство поломки приложения; перепроверь через `curl` и headless browser.
- Не путай CORS/транспортную проблему с багом backend-логики.
- Не ограничивайся “работает на сервере”: проверяй именно тот маршрут доступа, которым пользуется человек.
- Не фокусируй UX только на fresh install, если пользователь просит работу на текущей базе.
