# Когда использовать

Используй этот навык

## Урок из product-level polish для zero-state

Если задача — дожать внутренний local-first UI с ~8/10 до более взрослого уровня, first screen/empty-state нужно рассматривать как single-entry сценарий, а не как место для нескольких onboarding-слоёв.

Практические правила:
- один главный стартовый сценарий лучше, чем hero + welcome + empty-state + composer одновременно;
- если уже есть сильный composer/input area, смысл онбординга лучше переносить в него, а не добавлять отдельный hero-блок;
- в zero-state стоит скрывать secondary guide/header элементы, если они конкурируют с основным действием;
- если после cleanup live-оценка застряла около 8.5/10, это обычно признак не нехватки ещё одного CSS-твика, а структурного лимита текущей композиции;
- в такой точке следующий шаг надо называть не polish, а focused redesign пустого состояния, sidebar и размещения composer.

Используй этот навык, когда нужно не просто «подправить фронт», а довести local-first web UI до рабочего и понятного состояния после серии backend/frontend изменений:

- экран живой, но UX спорный или непоследовательный;
- в UI всплывает `Unexpected token '<'` или похожая JSON-ошибка;
- create/edit сценарии смешаны в одной форме;
- формы открываются inline под таблицей, хотя должны быть overlay/modals;
- поведение sticky-блоков, intro-плашек и кнопки `Вверх` в чатах не совпадает с ожиданием пользователя;
- во вкладке `Обзор` вместо реальных визуальных дашбордов остались только сухие KPI-карточки.

# Принципы

1. Сначала отличай frontend-симптом от backend-корня.
   - Ошибка вида `Unexpected token '<'` почти всегда значит, что frontend ждал JSON, а получил HTML-страницу ошибки.
   - Проверяй endpoint и статус ответа до того, как переписывать UI-логику.

2. Не смешивай create и edit в админских сущностях.
   - Если пользователь явно просил отдельный сценарий создания, не прячь его внутри selector `mode=create/edit`.
   - Создание должно запускаться отдельной кнопкой и отдельным потоком.
   - Редактирование должно открываться из строки выбранной записи.

3. Create/edit/detail поверх таблицы — по умолчанию overlay.
   - Для user/reference/admin сущностей форма или detail должны открываться как modal/overlay поверх таблицы.
   - Не вставляй форму под таблицу, если это ломает обзор списка и контекст.

4. Для chat UX разделяй две вещи:
   - поведение intro/notice блока;
   - момент появления кнопки `Вверх`.
   Не решай обе проблемы одним грубым `sticky` или полным его удалением.

5. Для `Обзора` проверяй не только наличие метрик, но и наличие именно визуальных дашбордов.
   - Если пользователь просил графики, простые summary cards не считаются завершением.

6. Если пользователь жалуется, что экран на desktop выглядит «слишком жирно» или помещается только при `67%`, считай это отдельным приёмочным дефектом, а не вкусовщиной.
   - Для wide desktop (`1920x1080` как минимум) делай отдельный pass по визуальному масштабу.
   - Сначала уплотняй вертикальный ритм самыми дешёвыми ходами: `padding`, `gap`, высоты `topbar`, кнопок, `input/textarea`, welcome-карточек, composer и empty-state.
   - Для chat-first экранов проверяй не только welcome, но и соседние служебные блоки: заголовок чата, инфо-плашки, левую колонку, пустое состояние.
   - Если welcome — это onboarding-слой, заголовок конкретного чата не должен конкурировать с ним на одном экране: в welcome-state его обычно лучше скрывать и возвращать после dismiss.
   - Не считай задачу решённой по ощущениям в маленьком viewport браузерного инструмента. Для финальной приёмки отдельно эмулируй `1920x1080` и сравни, сколько контента реально помещается above the fold.

7. Всё подтверждай по живому runtime, а не только по коду.
   - Для visual polish не ограничивайся ощущением от screenshot. Если меняешь плотность, высоту welcome/composer, ширину левой панели или компактность job-cards, снимай простые DOM-метрики до/после: `getBoundingClientRect()` по ключевым блокам, ширины колонок, количество starter-prompts, высоты active-card и composer.
   - Практический паттерн premium-pass: сначала зафиксировать 3–5 самых дорогих по вертикали или визуальному шуму зон, затем сделать дешёвый pass через `padding`, `gap`, `border`-контраст, короткие time-labels и сокращение secondary CTA, после чего подтвердить эффект не только глазами, но и цифрами из DOM.

8. Для chat-first первого экрана отдельный ROI-pass почти всегда выгоднее, чем общий «косметический» редизайн.
   - Если цель — поднять восприятие с ~8 до ~8.5+, сначала лечи не всё подряд, а три главные зоны: hero, sidebar empty-state и composer.
   - Хороший дешёвый набор ходов: центрировать рабочую колонку через общий `max-width`, сократить hero-copy до 1 ясного тезиса + 1 короткой подписи, уменьшить число starter-prompts, ослабить border/shadow шум, сделать empty-state в sidebar визуально отдельным от обычного item.
   - Для chat welcome предпочитай деловой, короткий русский copy: без маркетинговой «заставки», без длинного onboarding-абзаца и без CTA вроде `Сфокусироваться на чате`, если более естественно работает `Начать диалог`.
   - Composer после такого pass должен читаться как одна рабочая зона: одинаковая ширина с welcome/message-column, компактный title, короткий lead и без лишнего декоративного градиента.
   - Если пользователь просит упростить блок `Сообщение в чат`, считай это не вкусовщиной, а high-ROI cleanup signal. Для telegram-подобного composer базовый ход — вообще убрать служебные заголовки `Сообщение в чат` / `Продолжить диалог`, оставить только textarea, вторичные action-кнопки и primary send.
   - Placeholder в compact composer должен быть коротким и рабочим. Предпочтительный baseline — просто `Сообщение`, а не длинные фразы вроде `Напишите сообщение для текущего чата…`.
   - Для compact source policy в chat-first UI не привязывайся к постоянному inline select. Если пользователь хочет telegram-подобную плотность, `Параметры` лучше прятать за компактной кнопкой, а внутри popover держать только decision-relevant controls. Для этого контура минимальный набор — `reasoning / обычная модель` и `Политика источников`; debug-опции, длинные чекбоксы и source-level overrides не должны жить в основном chat composer.
   - Для вложений в chat composer предпочитай один вход через иконку скрепки. Внутри popover сначала короткие action-кнопки `Новый файл` и `Из профиля`, лучше вертикально друг под другом и в окне, ширина которого подстроена под размер самих кнопок, а не под будущий список файлов. Список profile files раскрывай только по запросу, а не держи его видимым по умолчанию.
   - Если пользователь жалуется, что приложенные изображения `не автоматически масштабируются`, это не cosmetic issue, а acceptance bug. Для image-файлов нужен встроенный preview/modal с `object-fit: contain`, ограничением по viewport и возможностью открыть файл отдельно; не отправляй пользователя сразу во внешнюю вкладку, если можно дать нормальный in-app preview.
   - В таких UI-pass не уходи в инфраструктурную отладку, если пользователь просит именно починить экран. Если runtime URL уже открыт и пользователь прямо говорит не лезть по SSH в этот сервер, приоритет — правка JSX/CSS, сборка и проверка артефакта, а не дополнительные SSH-попытки или backend-обсуждение.
   - Для telegram-подобного composer поле ввода по умолчанию лучше держать однострочным (`rows=1`) с минимальной стартовой высотой около высоты соседних кнопок, но оставлять возможность вертикального расширения. Кнопки параметров, вложений и отправки выравнивай по вертикальному центру textarea, а не по нижнему краю контейнера.
   - В welcome-блоке `С чего начать` следи не только за copy, но и за vertical spacing: между intro-текстом, быстрыми сценариями и warning-плашкой `Внимание` должны быть явные отступы. Если плашка визуально прилипает к starter prompts, считай это product-level дефектом плотности.
   - Если после pass live-оценка всё ещё ниже 9, не «дорисовывай» оценку из головы. Для этого класса задач честно фиксируй реальный уровень (`примерно 8.7/10`, `ещё не 9`) и формулируй, какой именно следующий pass нужен.

   - Для отправки в compact composer уместнее квадратная кнопка высотой в ряд control-элементов, часто с иконкой вместо текста, если пользователю важнее экономия места, чем текстовая явность.
   - Если пользователь жалуется, что сообщения «ютятся в маленьких окошках», проверяй не только паддинги, но и `max-width` bubble. Практичный desktop-контракт для chat-first UI: верхний предел до примерно `75%` ширины viewport, при этом короткие сообщения не растягиваются искусственно.
   - Если после pass live-оценка всё ещё ниже 9, не «дорисовывай» оценку из головы. Для этого класса задач честно фиксируй реальный уровень (`примерно 8.7/10`, `ещё не 9`) и формулируй, какой именно следующий pass нужен.

9. Для экрана `Задачи` после функционального cleanup делай отдельный harmony-pass по содержанию и визуальной иерархии.
   - Если нужен второй, уже premium-level pass, сначала уплотняй левый список: более короткий формат времени (`06.06, 18:20` вместо полного timestamp), ниже карточки, более явный active-state, меньше визуального шума в meta-строках.
   - В правом detail обязательно разводи два разных измерения: `Состояние задачи` и `Результат запуска`. Не оставляй их как почти одинаковые `Текущий/Последний статус`, если экран читают люди, а не разработчики.
   - Смотри на экран не только как админ, но и как обычный пользователь, который заходит понять, что делает задача и в каком она состоянии.
   - На первом экране оставляй только decision-relevant сигналы: `Название`, тех. название, `Источник`, `Текущий статус`, `Последний статус`, `Следующий запуск`, `Последний запуск`, `Приватность`, `Отдельные чаты задач` и основные действия.
   - Служебные поля вроде owner/role/`своя задача`/тонких meta-card рядов и технического `description` по умолчанию убирай с первого экрана, если они не меняют решение пользователя.
   - После сокращения контента обязательно делай визуальную унификацию: одинаковые карточки, согласованные размеры заголовков/значений, без смеси developer-facing label'ов и человеческих названий.
   - Для локальных alias/job-name действий используй человеческие подписи: `Название`, `Сохранить название`, а не внутренние формулировки вроде `Визуальное имя в этом браузере` или `Сохранить ярлык`.
   - Если после harmony-pass detail всё ещё выглядит как `card-inside-card`, делай отдельный selective de-boxing pass, а не полный редизайн. Практический паттерн: главный summary-слой можно оставить карточным, если он реально помогает ориентироваться, а вторичные секции (`Приватность`, `Куда отправляется результат`, `История запусков`, `Параметры`) переводить в более лёгкий режим: без outer border/radius, с прозрачным фоном секции, с одним верхним divider и только мягкими inset-блоками внутри.
   - Такой de-boxing-проход считай «дешёвым улучшением с хорошим ROI»: он меняет ощущение цельной страницы без новой архитектуры, tabs или сложного layout rewrite.
   - Если пользователь уже специально убрал из UI формулировки про `только для этого браузера`, не возвращай их потом косвенно в help-тексты, info-banner'ы, toast-сообщения или reset/save confirmations. После такого решения весь пользовательский контур должен оставаться в одной линии: `Название`, `Сохранить название`, `Название сохранено`, `Название сброшено` — без повторного объяснения внутренней browser-local механики, если пользователь прямо сказал, что это только путает.

10. Если после functional parity пользователь поднимает планку до product-level `8.5+`, перестраивай работу как отдельный polish-cycle, а не объявляй задачу завершённой.
   - Сразу переопредели backlog: отдельно `visual gap`, отдельно `high-ROI polish pass`, отдельно `live-приёмка`.
   - Не считай прежний verdict про `parity` достаточным доказательством качества UI. Для этой фазы нужен новый факт: живая оценка экрана после правок.
   - Самый быстрый паттерн для такого цикла: сначала снять базовую оценку по ключевым экранам (`chat`, `jobs`, `admin`, `profile`) через `browser_vision`, затем лечить не всё подряд, а самый дешёвый high-ROI разрыв.
   - Если один экран тянет весь продукт вниз сильнее остальных, прекращай «размазывать» pass по всему приложению и отдавай следующий круг почти целиком этому экрану.
   - Для chat-first экранов практичный порядок такой: сначала прояснить semantics composer, потом уменьшить шум sidebar/right-panel, затем лечить low-activity/empty-state центра. Это даёт больше ROI, чем ранняя тонкая полировка цветов.
   - Если live-оценка растёт ступенчато (`7.3` → `7.8` → `8.1` → `8.3/8.4`), не дорисовывай `8.5+` из оптимизма. Честно фиксируй текущий уровень и называй два самые дорогие остатка, которые ещё мешают порогу.
   - Для правой панели chat/composer сначала убирай шум простыми средствами: disclosure для bulk-контекста, более короткий список файлов, один главный CTA и пошаговый funnel `описать → добавить контекст → отправить`.
   - Для левой колонки chat-list быстрый premium-pass обычно состоит из de-boxing, более агрессивного truncation и ослабления вторичной строки. Это дешёвое, но повторяемо полезное улучшение.

## Дополнительные уроки из этого цикла

- Для copy-плашек вида `Внимание + текст` не полагайся на то, что соседние inline-элементы сами дадут читаемый результат. Если `strong` и `span` стоят рядом, добавляй явный разделитель или пробел как часть разметки/компонента и потом проверяй это live не только по JSX, но и по реальному DOM/видимому тексту. Иначе легко получить слепленное `ВниманиеРабота...` даже при формально корректном CSS.
- Если пользователь просит «сделать UI качественнее» после функционального фикса, не ограничивайся одним багом. Для chat/profile contour делай короткий compact-pass по четырём зонам сразу: vertical spacing, button padding/disabled state, hover/active feedback и плотность служебных блоков. Это дешёвый ход с высоким ROI и обычно заметнее для product-level восприятия, чем ещё один точечный текстовый фикс.
- Для кнопок и control-элементов считай anti-sticky / anti-clutter поведение отдельным приёмочным критерием. Практический минимум: кнопки не должны выглядеть залипшими в disabled, hover не должен быть резким, а secondary action не должна спорить с primary по весу. После CSS-pass подтверждай это на живом runtime, а не только по diff.
- Сценарий `новый аккаунт не увидел onboarding` нельзя честно закрыть в уже заполненной сессии существующего пользователя. Нужна отдельная first-run проверка: создать или взять пользователя с пустыми `goals`, `constraints`, `assistant_profile.about_user` и `pinned`, войти под ним и подтвердить, что onboarding/modal реально открывается и ведёт в нужный профильный раздел.
- Для first-run onboarding лучше использовать явный overlay/modal, а не пытаться замаскировать отсутствие сценария обычным banner/welcome-блоком. Если цель — быстро настроить стиль взаимодействия, хороший контракт такой: modal открывается автоматически для пустого профиля, кнопка `Настроить сейчас` переводит в `Профиль -> Как отвечать`, а после успешного сохранения modal закрывается.
- Но такой onboarding overlay нельзя делать блокирующим для всей навигации по приложению, если пользователь уже может работать без него. Практический контракт: либо `onDismiss/Позже`, либо backdrop с `pointer-events: none` и интерактивным только самим modal-контейнером, плюс явное закрытие overlay при ручном переходе в другой раздел (`handleNavigate`). Если overlay перехватывает клик по `Задачи`/`Профиль`, считай это не косметикой, а acceptance bug навигации.
- После проверки нового пользователя не оставляй acceptance-runtime в тестовом аккаунте молча. Если не получилось вернуть браузерную сессию в исходный smoke/admin-пользовательский контур, явно отметь это в отчёте как инструментальное состояние, чтобы не создавать ложное впечатление, будто live-поверхность сама собой переключилась.

- Для chat-first mobile adaptation в local-first интерфейсах не пытайся сразу сделать «полный mobile product». Сначала фиксируй minimal iPhone contour: `Чаты`, `Профиль`, чтение дашбордов и composer. Если пользователь явно говорит, что mobile admin не нужен, скрывай admin-навигацию на mobile breakpoint вместо попытки уместить весь desktop IA на узком экране.
- Если раздел `Задачи` не является частью мобильного пилота, честнее и дешевле временно скрыть его в mobile nav, чем оставлять полурабочий или перегруженный сценарий. Но как только пользователь явно говорит, что mobile `Задачи` нужны, запрет на скрытие перестаёт действовать: возвращай `Задачи` в mobile nav и лечи сам сценарий, а не маскируй дефект `display: none`.
- Для mobile chat shell хороший минимум такой: sidebar превращается в верхний блок, список чатов — в горизонтальную прокрутку карточек, main chat получает всю ширину, sticky-блоки ослабляются, а dashboard cards складываются в одну колонку.
- Для mobile height/layout в chat-first UI не держись за `100vh`, если экран должен жить внутри мобильного браузера. Базовый safe-path для современных iPhone/Android — перевод основных контейнеров (`app-layout`, `main-panel`) на `100dvh` и отдельная проверка, что composer/messages не теряются из-за address bar resize.
- Если пользователь жалуется, что новые сообщения не видны без ручного refresh, считай это product-level regression даже при успешной отправке. Для local-first chat UI нужен хотя бы базовый polling/refresh-контур: немедленный refresh при входе в активный чат, более частый poll при pending assistant message и более редкий idle poll в обычном режиме. Это часть UX-доставки ответа, а не «опциональная оптимизация».
- Если в UI есть действие `В архив`, заранее уточняй и потом жёстко соблюдай семантику: архивный чат должен исчезать с основной страницы/из sidebar, но оставаться доступным через `Все чаты` или отдельный архивный список. Это не cosmetic rename. Если архивируется текущий активный чат, UI должен сразу переключиться на следующий неархивный поток или безопасный fallback, а не продолжать держать архивный чат в основном рабочем контуре.
- Если пользователь отдельно говорит, что mobile уже `ок`, а дополировать нужно desktop/tablet, не лечи это через грубую перепрошивку mobile breakpoint-ов. Предпочитай системный pass через общие typography/spacing tokens, desktop-only width rules и повторное использование одного visual contract для `Файлы`, `Параметры`, `Управление`, `Задачи` и `Профиль`. Для popover-пар типа `Файлы/Параметры` целевой контракт такой: одинаковая шкала шрифтов, line-height, поля, размеры кнопок и близкая визуальная ширина на desktop, при сохранении уже работающих mobile override-ов.

См. также `references/nonblocking-onboarding-and-chat-refresh.md` и `references/chat-archive-and-popover-harmony.md`.

# Рабочий порядок

## Отдельный паттерн для policy/source UI в chat-first local-first интерфейсах

Если пользователь просит упростить политику источников и развести зоны ответственности между чатом и админкой, используй такой контракт:

- в чате обычный пользователь управляет только режимом маршрутизации запроса: `local_only`, `global_only`, `local_first`;
- чат не должен показывать чекбоксы верхних источников, списки коннекторов и другие admin-level controls;
- глобальная конфигурация источников, состав реестра и принадлежность коннекторов к внутреннему/внешнему контуру живут только в админке;
- если backend строит inventory автоматически, admin-решение о принадлежности коннектора к `internal`/`external` надо хранить как явный override поверх discovery/sync, чтобы очередной sync не затирал ручную классификацию;
- в админке не оставляй англоязычные label'ы и длинные архитектурные объяснения, если пользователь явно просит более человеческий управленческий UI; policy-блок должен быть экранным, читабельным и объяснять решение коротким деловым русским текстом;
- при таком разделении приёмка идёт в два слоя: (1) chat UI реально оставляет только 3 режима; (2) admin UI реально сохраняет глобальную политику и классификацию коннекторов read/write round-trip.
- summary/current-state строка рядом с выбором режима должна вычисляться из фактически выбранного значения, а не быть жёстко прошитой плашкой вроде `файл пользователя, интернет-исследование`. Если label не меняется вместе с селектом, считай это product defect, а не косметикой.

Частая ловушка этого класса задач:
- сначала упростить только helper-функцию/submit payload в чате, но оставить старые чекбоксы источников и коннекторов в JSX;
- или наоборот, перерисовать админку, но продолжать вычислять `internal/external` только из discovery без backend-backed override.

1. Зафиксируй пользовательскую претензию буквально.
   - Что именно видно сейчас.
   - Что именно пользователь ожидает.
   - Не сглаживай различие между «не должно липнуть всегда» и «должно вести себя корректно в верхней зоне экрана».

2. Для JSON/UI ошибок сначала проверь API-контур.
   - Если в UI ошибка парсинга JSON, проверь, не прилетает ли HTML.
   - Особенно внимательно проверь mixed id типы:
     - local DB id могут быть numeric;
     - внешние/Hermes id могут быть string.
   - Не пытайся насильно искать string id в local таблице с `INT`-ключом.

3. После backend-фикса сделай frontend graceful handling.
   - Даже если корень в backend, `api()` должен уметь показать осмысленную ошибку, если пришёл не JSON.
   - Покажи статус и короткий фрагмент ответа, а не голый `Unexpected token`.

4. Для admin CRUD выстрой IA так:
   - таблица остаётся главным контекстом;
   - `Создать` — отдельное действие;
   - `Редактировать` — действие из строки;
   - detail/edit открываются в overlay.

5. Для chat scroll UX проверяй поведение относительно viewport.
   - Кнопка `Вверх` должна появляться, когда стартовые блоки реально ушли из видимой области.
   - Intro/notice блок не должен бездумно жить как глобальный sticky на весь экран.
   - Если нужен sticky, он должен быть ограничен рамкой chat screen и проверен в runtime.
   - Для компоновки с двумя постоянными зонами (`верхняя плашка` + `composer`) оставляй единственной scroll-областью список сообщений между ними. Не делай так, чтобы sticky-блоки сами становились scroll-контейнером и визуально прижимали переписку к верху.
   - После таких правок отдельно проверь, что сообщения реально прокручиваются, а не только что sticky-элементы "красиво стоят" в DOM.

6. Для `Обзора` собирай web-first визуализации.
   - Минимум: отдельный графический блок/дашборд, а не только числовые карточки.
   - Основа — данные web UI: пользователи, чаты, сообщения, задачи, события.

7. Завершай только после runtime-проверки.
   - Открыть проблемный экран.
   - Проверить конкретный сценарий пользователя.
   - Убедиться, что не осталось HTML вместо JSON, inline-форм вместо overlay и KPI-вместо-графиков.
   - Если pass затрагивал auth/login, профильные фильтры, logout-flow или общий first screen, отдельно прогоняй `logout -> login-screen` в live runtime, а не только текущую авторизованную сессию.
   - На login-screen проверяй не только верстку, но и product-copy: первый экран не должен раскрывать внутреннюю админскую механику обычному пользователю, если задача была сделать пользовательский вход чище и нейтральнее.

# Частые ловушки

- Лечить `Unexpected token '<'` только на frontend, не проверив backend 500.
- Если backend сидит на DuckDB или другом контуре с конфликтами записи, не держать скрытую запись внутри auth/read path. Отдельная ловушка — обновлять `sessions.last_seen_at` на каждом GET через `require_auth()`: при параллельном boot это может давать плавающие `500` на `/me`, `/bootstrap`, `/jobs/meta`, `/files`, а во frontend выглядеть как «сервис вернул не JSON».
- Считать, что tabs/sections сломаны, когда проверялись не те CSS-признаки активного состояния.
- Оставлять create/edit в одной форме «ради универсальности», когда пользователь явно просил разделить поток.
- Считать `sticky`/`not sticky` бинарным выбором без привязки к viewport и конкретному scroll trigger.
- Называть KPI-карточки «дашбордами», если пользователь просил именно графики.
- Для визуальной жалобы про слишком белую переписку сразу уходить в полный редизайн палитры. Сначала попробуй дешёвый ход: слегка посерить conversation-area и чуть подтонировать bubble ассистента, не ломая остальную тему.
- Игнорировать прямой пользовательский сигнал про масштаб (`«только на 67% помещается»`) и лечить только тексты/цвета. В этом классе задач проблема часто в суммарной высоте `topbar + helper cards + thread header + empty-state + composer`, а не в одном отдельном блоке.
- Оставлять заголовок чата видимым одновременно с крупным welcome-блоком, если пользователь явно просит спрятать его «под welcome». Для chat-first onboarding это создаёт лишний вертикальный слой и визуальный шум.
- Показывать в jobs/detail сырой рабочий prompt или системный инструктаж из `description` как обычный пользовательский текст. Если поле фактически содержит prompt (`Ты — ...`, `You are ...`, `Требования:`, `[IMPORTANT: ...]`) или просто слишком длинное служебное содержание, скрывай его за нейтральной заглушкой вроде `Описание скрыто: задача использует длинный рабочий prompt.`. Для приёмки проверяй это на реальной cron-задаче в live runtime, а не только по коду.
- Оставлять в UI технические подписи, понятные только разработчику, когда пользователь просит более человеческий интерфейс. Для локальных alias/job-name полей предпочитай короткий деловой label (`Название`) вместо внутренних формулировок вроде `Визуальное имя в этом браузере`, если сохранена функциональная точность. Кнопки тоже держи в человеческом деловом стиле: если действие сохраняет локальное имя, по умолчанию лучше `Сохранить название`, а не `Сохранить ярлык`.
- Если пользователь уже согласовал более человеческую формулировку, не откатывайся назад к технически точной, но путающей подписи «ради честности». Для этого контура формулировки вроде `только для этого браузера`, `локальное название`, `локально` допустимы как внутренняя модель, но не как основной copy на первом экране `Задач`, если они ухудшают понятность для обычного пользователя. После copy-polish обязательно перепроверь live runtime и убедись, что старая формулировка не осталась ни в help-тексте, ни в banner/toast, ни в detail-блоках.
- Для локального delivery target в jobs/detail не показывай голое `Локально` как самостоятельный пользовательский ответ. Базовый человеко-понятный паттерн: `Без отправки в чат` + пояснение, где остаётся результат (`во внутренней истории задачи` / `только в интерфейсе`), чтобы обычный пользователь не гадал, куда делся вывод.
- Для машинных статусов cron/job-run не оставляй сырой `ok`, если экран читается людьми. На summary/detail/history по умолчанию прогоняй статусы через humanize-слой (`успешно`, `с ошибкой`, `выполняется` и т.д.), а fallback-формулировки вроде `Без краткого результата` заменяй на естественный деловой русский (`Краткий итог не указан.`).
- Для jobs/detail не показывай на первом экране техническое `description`, если там живёт рабочий prompt, системная инструкция или просто служебный текст, не помогающий пользователю принять решение. В таком сценарии базовый путь — убрать описание из основного detail целиком, а не пытаться смягчить его заглушкой, если пользователь прямо говорит, что описание не помогает.
- При упрощении экрана `Задачи` считай приоритетными именно операционные сигналы, а не служебные метаданные. Ядро первого экрана: `Название`, тех. название, `Источник`, `Текущий статус`, `Последний статус`, `Следующий запуск`, `Последний запуск`, `Приватность`, `Отдельные чаты задач` и основные кнопки действий. Кандидаты на удаление с первого экрана: владелец, роль, `своя задача`, дубли блоков доступа, отдельный ряд мелких meta-карточек и прочие поля, не меняющие пользовательское решение.
- Для jobs/detail не прячь `активна / на паузе` только в chip или в тексте кнопки. Если пользователь смотрит экран как оператор, текущее состояние задачи должно быть отдельным явным показателем `Текущий статус`, а не только косвенным сигналом.

# Что считать готовым

Задача закрыта, если одновременно выполнено всё ниже:

- проблемный API/JSON сценарий исправлен по корню;
- frontend показывает осмысленную ошибку на случай не-JSON ответа;
- create и edit больше не смешаны в одном пользовательском потоке;
- формы/карточки открываются поверх таблицы;
- кнопка `Вверх` и верхняя плашка в чатах ведут себя по viewport-логике;
- во вкладке `Обзор` реально есть визуальные дашборды;
- всё проверено на живом UI.
