# Per-user delivery vs foreign-thread verification

## Когда это нужно

Когда пользователь говорит не просто «проверь UI», а именно:
- «зайди под Викторией»
- «проверь под этим пользователем»
- «у меня ничего не работает»
- «не надо смотреть абстрактный backend, проверь как у меня»

## Главный риск

Ложноположительная проверка: агент находит нужные сообщения или рабочий thread у другого пользователя и ошибочно объявляет, что проблема не воспроизводится.

Это особенно опасно для:
- recurring / digest delivery
- per-user threads
- self-subscribe / recipient routing
- job-based chat threads
- shared названий чатов (`ТГ Дайджест`, `KPI`, `Новый чат`)

## Обязательная дисциплина

1. Сначала установить конкретную user identity в live UI.
   - Проверить email / имя пользователя на экране.
2. Определить фактический thread этого пользователя.
   - Не полагаться на один только title.
   - Один и тот же title может существовать у многих пользователей.
3. Проверить ownership / доступность объекта через API именно под токеном этого пользователя.
   - Если thread под этим токеном даёт `404`, это уже сильный сигнал, что проверяется чужой контур.
4. Сравнить:
   - что пользователь реально видит в UI;
   - какие message ids есть у его thread;
   - какие сообщения существуют у других пользователей с тем же title.
5. Если у других пользователей delivery есть, а у целевого пользователя нет — классифицировать это как delivery / subscription / recipient / ACL problem, а не как «UI всё показывает нормально».

## Быстрые sanity-check вопросы

- Этот thread точно принадлежит нужному пользователю?
- Эти message ids доступны под его токеном?
- Совпадает ли last visible message in UI с last message in that exact thread?
- Не проверяю ли я случайно другой `ТГ Дайджест` / `KPI` с тем же названием?

## Симптомы, которые нельзя сглаживать

- Под нужным пользователем чат открыт, но новые сообщения отсутствуют.
- Под другим пользователем те же сообщения есть.
- Live API под нужным токеном возвращает `404` на thread, который агент раньше использовал как доказательство.

В такой ситуации правильный вывод:
- проблема реальна;
- прежняя проверка была проведена не по тому пользовательскому контуру;
- root cause likely in routing / subscription / recipient mapping / per-user delivery.

## Формулировка результата пользователю

Говорить прямо:
- что именно было проверено под его пользователем;
- что реально работает;
- что реально не работает;
- где раньше был ложный вывод из-за проверки чужого thread.

Не маскировать это фразами вроде «в целом система работает» или «частично подтверждается», если пользовательская delivery-цепочка реально сломана.
