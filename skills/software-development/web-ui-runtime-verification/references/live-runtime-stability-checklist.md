# Live runtime stability checklist

Использовать при финальной приёмке local-first web UI, когда код уже изменён, но нужно доказать, что live runtime действительно подхватил правки.

## Когда добавлять этот проход
- После правок в auth/session/bootstrap.
- После исправлений «автопрыжков» между вкладками/разделами.
- Когда build зелёный, но live-поведение не совпадает с кодом.
- Когда backend process мог остаться старым после частичного restart.

## Практический паттерн
1. Разделить три состояния и не смешивать их в выводе:
   - код на диске;
   - build/test результат;
   - live runtime на порту.
2. Если `curl`/browser показывает старое поведение, считать первым кандидатом stale process, а не ошибку в патче.
3. Для backend-проверки после security/session правок обязательно перепроверить именно live endpoint на целевом порту, а не только unit/smoke.
4. Если restart не дал эффект, проверить, какой PID реально слушает порт, и только после этого делать повторную live-валидацию.
5. В финальном отчёте явно маркировать статус:
   - `код обновлён`;
   - `build/test подтверждены`;
   - `live runtime подтверждён / не подтверждён`.

## Что проверять при жалобе на автопереключение экранов
Искать не только polling и router bugs, но и принудительное восстановление state в bootstrap-функциях:
- выбор первого чата/первой задачи вместо последнего активного;
- принудительный возврат на default screen;
- сброс admin section;
- безусловный reset welcome/local UI flags.

Надёжный адресный фикс для такого класса проблем:
- сохранять `screen`, `activeThreadId`, `activeJobId`, `adminSection` в localStorage;
- при bootstrap восстанавливать их через безопасный `pickExistingId`/sanitization;
- на logout очищать сохранённый UI-state;
- не считать первый элемент списка корректным default, если у пользователя уже был явный выбор.

## Что проверять при правках auth/session concurrency
Если цель — снизить конфликтность и write-amplification:
- проверить, не пишет ли `require_auth()` или аналог каждый auth-check в БД;
- для session keepalive использовать throttled touch по интервалу;
- session restore/check endpoint по возможности не должен модифицировать сессию на каждый запрос.

## Формулировка результата
Если упёрлись в старый процесс и не успели довести live-перезапуск, не писать «всё проверено». Корректная формулировка:
- код и тесты готовы;
- live runtime ещё требует адресного restart/recheck.
