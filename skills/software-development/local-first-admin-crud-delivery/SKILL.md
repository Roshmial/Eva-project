# Когда использовать

## Новые акценты и подводные камни

- Не смешивай создание и редактирование в один двусмысленный admin-flow, если пользователь явно просит отдельный сценарий создания. Для админских CRUD-экранов предпочитай отдельную точку входа `Создать ...` плюс ro
- При переносе bulk UX с пользователей на другие admin-сущности (например, элементы справочников) сначала сверь helper-функции и нормализаторы с реальным frontend bundle. Нельзя тащить имена вроде `safeText` по аналогии с backend или другой веткой фронта: `node --check` и backend smoke tests это не поймают, а live UI упадёт с `ReferenceError`. Для bulk-паритета обязательна отдельная runtime-проверка цепочки `выбрать один -> выбрать всех -> снять выбор -> bulk action`.
w-level edit actions, а не общую форму с переключателем режима.
- В табличных admin-разделах формы `создать` / `редактировать` должны открываться поверх таблицы как overlay/modal, а не встраиваться под таблицу, если пользователь отдельно не просил inline-editing.
- Ошибку вида `Unexpected token '<'` на JSON endpoint сначала трактуй как вероятную backend HTML error page, а не как frontend parsing bug. Проверяй живой ответ exact-route и отдельно подтверждай, что backend-процесс действительно перезапущен: старый процесс на том же порту легко маскируется под «код не помог».
- Для chat UX не смешивай две задачи: поведение intro/help-блока и порог появления кнопки `Вверх`. Кнопка должна появляться, когда стартовый/intro-блок ушёл из видимой области, а не только когда пользователь уже глубоко проскроллил экран.
- Если пользователь говорит, что информационная плашка должна быть «всегда доступна», по умолчанию переноси её в верхний навигационный контур экрана (рядом с вкладками/topbar), а не пытайся лечить это `sticky`-логикой внутри прокручиваемой ленты. Постоянно доступная подсказка — это элемент навигации/контекста экрана, а не часть scrollable chat-feed.
- Перед правкой chat-scroll обязательно измеряй реальный scroll host в живом DOM. В local-first web UI им может оказаться не `.content`, а `document.scrollingElement`/`body`; если повесить логику на неверный контейнер, плашка и кнопка `Вверх` будут вести себя «почти правильно», но нестабильно.
- Если после нескольких попыток `sticky`-поведение всё ещё спорное, предпочитай упрощение: оставить intro-блок обычным (`relative/static`), а постоянную справку вынести в topbar и оставить только простую логику кнопки `Вверх` по понятному scroll-threshold.
- Для справочников и пользователей различай `active`, `inactive` и `deleted` как отдельные рабочие состояния. Неактивные/удалённые сущности должны исчезать из новых выборов, логинов, access-list и assign-flow, но ранее сохранённые значения нельзя тихо обнулять только потому, что элемент позже выключили.
- Для reference-driven select/lookup используй паттерн `preserve historical inactive value`: в новых выборах показывай только активные записи, но если текущая сущность уже хранит неактивный key/value, временно подмешивай его в options как помеченный `не активно`, чтобы форма честно показывала текущее состояние без возможности назначить этот вариант заново.
- При возврате soft-statuses в admin CRUD проверяй не только форму редактирования, но и все производные контуры: login/auth, user options в jobs/access, bootstrap/runtime user lists и row/table labels. Иначе статус формально сохранится, но недоступность для новых выборов останется неполной.

Используй этот навык, когда нужно довести внутренний admin-контур web-приложения до состояния "реально работает", особенно если задача включает:

- перенос справочников из hardcode во backend/БД;
- admin CRUD для пользователей или справочников;
- локальную схему данных без внешних SaaS;
- русификацию пользовательских строк фронта;
- добавление аудита, истории изменений и простого versioning;
- обязательную живую проверку API и UI, а не только синтаксис.

# Что считать готовым результатом

Не считать задачу завершённой, пока не подтверждены все уровни:

1. схема БД создана или мигрирована;
2. backend стартует на новом коде;
3. чтение и запись проходят живыми запросами;
4. история изменений реально заполняется;
5. версия сущности увеличивается после update;
6. пользовательские строки во фронте показаны по-русски;
7. итог подкреплён реальными логами, ответами API и проверкой данных.

Синтаксическая проверка (`py_compile`, `node --check`) — это только ранний фильтр, не доказательство работоспособности.

# Рекомендуемый подход

## 1. Сначала восстанови модель данных

Для admin-контура зафиксируй явно:

- какие сущности становятся таблицами;
- какие поля обязательны;
- где нужен `version`;
- где нужен append-only change log;
- какие endpoint-ы должны быть read/write/history.

Для справочников предпочитай универсальную модель:

- каталог справочника;
- элементы справочника;
- `payload_json` для расширяемых полей;
- `sort_order`, `is_active`, `created_at`, `updated_at`, `version`.

## 2. Делай cheap-but-usable аудит

Если не нужен полноценный event sourcing, используй простой и полезный минимум:

- поле `version` в основной таблице;
- отдельную append-only таблицу логов;
- `snapshot_json`, а не diff;
- `actor_user_id`, `change_type`, `created_at`.

Это быстрее внедрить, легче читать и проще проверять вручную.

## 3. Не доверяй старым SQL-допущениям

Если backend работает на DuckDB или похожем движке с более строгим SQL, не полагайся на свободный `GROUP BY` в стиле SQLite.

Правило:

- если в `SELECT` появилась новая неагрегированная колонка, проверь все запросы с `GROUP BY` вокруг этой сущности;
- особенно helper-запросы вида `get_*_with_stats`, которые вызываются после create/update.

После добавления `version` в `users` или `reference_items` проверь не только list endpoint, но и detail/helper query, вызываемую после записи.

## 4. Миграции проектируй под реальный движок

Для DuckDB не рассчитывай, что `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...` всегда сработает.

Безопасный паттерн:

1. попытаться добавить колонку как задумано;
2. если движок не поддерживает добавление с ограничениями, добавить более мягкую колонку;
3. дозаполнить `NULL` через `UPDATE`;
4. затем уже использовать колонку в приложении.

Навык не должен считать миграцию завершённой, пока backend не был реально перезапущен на новой схеме.

## 5. Для Миши доводи до рабочей проверки, а не до красивого описания

В задачах этого класса у Миши важны:

- фронтовые пользовательские подписи на русском;
- русские статусы, ошибки, preview-тексты и служебные сообщения, а не только переведённые названия полей;
- отсутствие незавершённых хвостов под видом "почти готово";
- явная проверка `create`, `update`, `history`;
- подтверждение, что `assistant_profile.about_user` реально сохраняется и возвращается;
- честная фиксация, что именно проверено, а что пока только гипотеза.

Если пользователь просит "доделать под ключ", не останавливайся на стадии "backend и frontend уже в основном готовы". Для этого класса задач результат считается завершённым только после живого подтверждения критического пользовательского сценария. Если один обязательный smoke/live path ещё падает, это не "почти готово", а незавершённая задача.

## 6. Минимальный обязательный сценарий живой проверки

После изменений прогоняй как минимум:

1. login под admin;
2. `GET` списка;
3. `POST` создания сущности;
4. `PATCH` обновления сущности;
5. `GET history`;
6. проверка роста `version`;
7. проверка появления записи в change log;
8. проверка, что bootstrap/reference endpoints не сломались побочным эффектом.

Для пользователей отдельно проверь поля профиля, включая `assistant_profile.about_user`.

Если personalization переведена на backend-справочники, обязательный сценарий расширяется:

9. `GET /api/bootstrap` реально возвращает нужные datasets personalization;
10. `PATCH /api/me` проходит с валидным `assistant_profile`;
11. `PATCH /api/me` отвергает невалидный key с ожидаемой русифицированной ошибкой на фронте;
12. admin create/update пользователя принимает nested `assistant_profile` и корректно читает его обратно.

## 7. Разделяй проблемы записи и проблемы возвратного payload

Если после `PATCH` сущности ответ API показывает старую `version`, не объявляй запись сломанной, пока не проверишь два независимых признака:

1. `history` endpoint показывает новую запись `update`;
2. прямое чтение из БД или повторный detail/list endpoint показывает фактическую новую `version`.

Если история и БД уже отражают изменение, а update-ответ содержит старое значение, это обычно не дефект сохранения, а read-after-write/serialization inconsistency в возвращаемом payload. Такой хвост нужно зафиксировать отдельно, но не путать с поломкой audit trail или versioning.

# Частые ловушки

- Починили `GET /admin/users`, но забыли, что после `POST` вызывается отдельный helper с другим SQL.
- Добавили `version` в сериализацию, но не в `GROUP BY` у detail query.
- Добавили `version` в таблицу `reference_items`, но забыли включить его в `SELECT` внутри helper-а, который собирает dataset payload для admin response. В итоге update реально сохраняется и попадает в history, но ответ API после `PATCH` возвращает старую версию.
- Миграция прошла на коде, но не была реально применена к живой БД до рестарта backend.
- Legacy SQLite migration пытается читать из старой таблицы колонки, которых там ещё нет (`version`, `assistant_profile_json`, `onboarding_completed`). Безопасный путь: сначала читать `PRAGMA table_info(...)`, выбирать только реально существующие legacy-колонки, а новые поля дозаполнять дефолтами при вставке в новую DuckDB-схему.
- История endpoint существует, но логи не пишутся при import/update/create.
- Admin user save path использует ту же нормализацию, что и import. Если `normalize_import_user()` понимает только плоское поле `about_user`, а UI шлёт nested `assistant_profile`, `about_user` тихо теряется при create/update. Для admin CRUD обязательно проверяй nested payload `assistant_profile` целиком.
- Self-profile save path может разойтись с admin CRUD. Частая ловушка: `PATCH /api/me` отклоняет валидный nested `assistant_profile` с `nothing_to_update`, потому что обработчик считает изменениями только плоские поля. Если personalization переведена на backend references, `PATCH /api/me` обязан принимать сценарий, где меняется только nested `assistant_profile`.
- Для `PATCH /api/me` не собирай pending-profile только из `default_assistant_profile(style)`, если payload частичный. Сначала возьми текущий сохранённый `assistant_profile`, поверх него наложи присланные поля и только потом валидируй по активным reference keys; иначе частичный update может тихо сбрасывать неотправленные поля.
- Если self-profile входит в тот же governance-контур, что и admin CRUD, он тоже должен увеличивать `users.version` и писать запись в `user_change_log` (например, `self_update`), а не обходить audit только потому, что пользователь редактирует себя сам.
- Фронт частично русифицирован: форма переведена, а сообщения об ошибках или служебные подписи остались на английском.
- Проверка ограничилась синтаксисом и `GET`, без живого `POST/PATCH`.
- Smoke-тесты могут устареть после архитектурного разворота. Если jobs переведены в Hermes-as-truth и web create/update сознательно запрещены, тесты должны проверять read-only / rejection behavior (`jobs_create_use_hermes_cron_directly`), а не продолжать ожидать старый app-owned CRUD.
- Для DuckDB job run path особенно опасно дробить один логический write-flow на несколько независимых `db_connect()`-транзакций: запись `job_runs`, доставка в `messages`, обновление `threads` и финальный `UPDATE jobs` могут словить `TransactionException: write-write conflict`, даже если UI list/detail уже работают. Если smoke падает именно на ручном запуске job, сначала проверь, не разбит ли run-path на несколько отдельных подключений; предпочтительный fix-pattern — держать критичный write path в одной транзакции или добавить узкий retry вокруг доставки/обновления thread preview.
- Если mixed-source jobs list/detail уже подтверждены в живом UI, а падает только `POST /api/jobs/<id>/run`, не объявляй весь jobs-контур незавершённым без разделения. Это отдельный backend-дефект run-path, который нужно чинить и логировать отдельно от UI/list/detail acceptance.

# Дополнительные обязательные проверки после доработки

- Для `reference_items` сверяй три независимых сигнала: update-response, direct detail/list payload и history snapshot. Если history уже показывает `version = 2`, а response всё ещё `1`, ищи проблему в serialization/read-after-write path, а не в сохранении.
- Для admin user CRUD отдельно прогоняй nested `assistant_profile.about_user` на create, update и detail readback.
- Если пользовательский сценарий — массовые операции по users (`bulk inactive`, `bulk delete`), проверяй их как отдельный класс CRUD, а не как частный случай одиночного update. Минимум: несколько user IDs в одном запросе, рост `version`, корректные change types в history и серверный guard против выключения/удаления последнего активного администратора.
- Для живой bulk-проверки пользователей не переиспользуй фиксированные тестовые email: создавай уникальные адреса/имена на каждый прогон, иначе повторная проверка быстро превращается в ложный `409 Conflict` и маскирует реальное состояние bulk-route.
- Если пользователь просит «привести список задач в нормальный вид», по умолчанию минимизируй шум в list-view: оставляй визуальное название, техническое имя и статус, а расписание/видимость/получателей уноси в detail. Для job list это не косметика, а продуктовая читаемость; live-приёмка должна подтвердить, что длинные технические поля больше не раздувают строку.
- Для плотных admin-таблиц с агрегатами не прячь несколько разных контуров в один общий столбец, если пользователь просит читаемость и управление данными. Предпочитай отдельные числовые колонки вроде `Чаты`, `Задачи`, `Сессии` вместо одного summary-поля `Контур`, чтобы каждая метрика была видна и сортируема сама по себе.
- Если добавляешь sortable-заголовки в admin-таблицу, проверяй не только наличие стрелок в `thead`, но и реальное изменение `state` и первой строки после переключения сортировки. Для этого класса UI нормальный приёмочный набор такой: (1) дефолтная сортировка активна; (2) первый клик меняет `state.admin.*Sort` на `asc`; (3) второй клик по тому же заголовку меняет направление на `desc`; (4) первая строка таблицы реально меняется вместе с числовым столбцом.
- Если текущая задача не про destructive bulk-write, а только про механику массового выбора в UI, не запускай `bulk inactive/delete` ради галочки. Отдельно подтвердись на безопасном selection-pass: `Выбрать всех`, частичное снятие выбора у одной строки, `Снять выбор`, пересчёт summary (`Выбрано ...`), синхронность master-checkbox и переход bulk-кнопок из `disabled` в enabled и обратно.
- Для плотной users-таблицы не считай единичный `browser_click` по bulk-кнопке достаточным доказательством. Если snapshot не меняется, проверь фактическое состояние через DOM/state (`selectedUserIds`, checkbox.checked, summary text, disabled-state кнопок`) и при необходимости воспроизведи действие адресным DOM-click через `browser_console`; в этом контуре именно так надёжно подтверждается, что selection logic рабочая, даже если accessibility-click дал ложный no-op.
- Если frontend ходит в backend через отдельный proxy/origin (например, `8790/api` -> `8788`), после добавления нового admin endpoint всегда подтверждай, что запущен именно свежий backend-процесс. Симптом `404` на новом route после успешных unit/smoke-тестов чаще означает stale runtime на живом порту, а не ошибку в коде endpoint.
- Практический runtime-check для такого `404`: (1) посмотреть, какой PID реально слушает порт; (2) сверить `cwd`, `cmdline` и время старта процесса; (3) дернуть exact-route напрямую через `curl`, минуя frontend; (4) после перезапуска ожидать уже не `404`, а как минимум auth-gated ответ (`401 auth_required`) на route без токена. Это быстро отделяет stale process от ошибки маршрута.
- Если пользователь зафиксировал каноническое дерево и боевые порты, перед любым browser/live-pass выпиши для себя матрицу `repo -> frontend port -> backend port -> launch script` и проверь именно её, а не dev/runtime "по умолчанию". Иначе легко честно прогнать не тот contour и дать ложный verdict по UI.
- Для policy/source-блоков не держи два независимых источника истины по одним и тем же коннекторам — например, hardcoded seed-список и отдельно редактируемый DB-реестр без явной синхронизации. Предпочтительный local-first паттерн: один системный registry в backend-коде как platform baseline, а UI/admin читает operational-слой из `reference_items`/аналогичной таблицы, который синхронизируется из этого registry. Иначе admin показывает одно состояние, runtime опирается на другое, а эволюция source-capabilities начинает расходиться по веткам.
- Для source registry не привязывай верхний уровень к одному частному датасету или текущему продукту доставки вроде `telegram_digest`. Верхний слой должен описывать классы источников/каналов платформы (`local_dataset_registry`, `internal_connector`, `external_connector`, `web_research` и т.п.), а не один конкретный feed. Если пользователь напоминает, что в системе есть Google API, Telegram API, tender/procurement API и другие data flows шире одного дайджеста, воспринимай это как сигнал перепроверить inventory по реальным интеграциям и environment-discovery, а не как просьбу просто переименовать label.
- Если вводишь request-level source override поверх admin policy, сразу разделяй семантику `policy allowed sources` и `явно выбранные источники запроса`. Не называй оба слоя одинаково. Практический совместимый паттерн: оставить старое поле вроде `allowed_source_ids` как legacy alias, но в новом контракте ввести явное имя (`explicit_source_ids`/аналог), чтобы не смешивать governance policy с конкретным выбором пользователя в запросе.
- Если live policy/admin UI показывает payload, не совпадающий с ожидаемой новой моделью (например, 3 верхних источника вместо 5 или отсутствие `child_connectors`), не уходи сразу в косметический UI-polish. Сначала стабилизируй backend runtime и сними живые `bootstrap`/policy JSON: пока `/auth/login`, `/bootstrap` или `/admin/...` дают `500/502`, финальная UI-приёмка будет ложной. Для этого класса задач правильный порядок такой: runtime health и source payload -> save/read round-trip policy -> только потом визуальная доводка и итоговый UX score.
- Для admin health/overview-метрик после эволюции схемы не считай analytics-query второстепенным хвостом. CRUD и policy routes могут быть зелёными, а `admin_health` всё равно падать на live БД из-за data-shape drift. Если запрос читает `messages.user_id` или другую "очевидную" колонку, сначала сверяйся с реальной схемой/serializer текущей БД: в живом контуре в `messages` могут существовать только `thread_id` и `meta_json`, а user-level агрегацию надо получать через join на `threads` или другой фактический источник истины.
- Для Hermes Web MVP после cache-busting navigation или нового открытия вкладки сначала восстанавливай авторизованное состояние штатным `restoreSession()`, а не `bootstrapAdmin()`. `bootstrapAdmin()` относится к initial setup/create-admin flow и даёт ложные ошибки вроде `valid_email_required`, которые маскируют реальную проверку admin UI.
- Для bulk-проверки справочников разделяй две приёмки: безопасный selection-pass и destructive mutation-pass. Сначала подтвердить live `Выбрать всех` -> частичное снятие -> `Снять выбор` -> summary/master checkbox/buttons; только потом идти в `bulk inactive/delete`, и decision-log обновлять после подтверждения mutation-path или явно фиксировать, что принят только selection/UX слой.
- Для destructive bulk-проверки пользователей в live admin не используй существующие рабочие учётки. Создавай уникальных тестовых пользователей на каждый прогон, проверяй `bulk-status` через UI/API, а затем подтверждай не только итоговый статус, но и `version` + change log (`create` -> `bulk_delete` / `bulk_inactivate`) для каждого пользователя.
- Для jobs/рассылок различай два типа получателей и проверяй их отдельно: `fixed_user` и `fixed_thread`. Оба сценария должны приводить к доставке в отдельный `job`-чат (`thread_kind='job'`), а не в обычный пользовательский чат. Для `fixed_thread` отдельная обязательная инварианта: выбранный чат используется только как источник владельца (`user_id`), а сообщение должно появиться в новом/отдельном job-thread этого владельца, не в исходном thread.
- Если на фронте возвращаешь выбор получателей для jobs, не ограничивайся только thread-picker. В этом контуре пользователи ожидают оба варианта: прямой выбор пользователя для рассылки и выбор чата как способа определить владельца отдельного job-чата.
- Если пользователь просит убрать из admin-формы технический JSON, делай это как product rule, а не как косметику: скрывай raw payload из видимого UI, автособирай служебные поля по dataset-specific правилам и отдельно проверяй live, что карточка редактирования показывает живое название справочника и элемента вместо технических key.
- Для паролей в admin users не полагайся на скрытую логику общего edit-flow. Если backend принимает `password` в `PATCH /admin/users/<id>`, но отдельного admin reset/set-password действия нет, продуктово это всё равно читается как отсутствующая функция. Предпочитай явное действие `Задать новый пароль` / `Сбросить пароль` с отдельной кнопкой или диалогом, и отдельно различай его от self-service `POST /api/me/change-password`, который требует текущий пароль самого пользователя.
- После изменения схемы или миграции не ограничивайся живым backend: обязательно гоняй smoke-тест на чистой временной БД, чтобы поймать несовместимость с legacy migration.
- Если текущая архитектура по jobs уже read-only через Hermes cron, закрепляй это не только в документации, но и в automated tests.

# Чек-лист завершения

Перед финальным ответом проверь:

- backend стартует после миграции;
- новые колонки и audit-таблицы существуют в БД;
- `POST/PATCH/history` работают живьём;
- `version` увеличивается на update;
- change log заполняется;
- пользовательские строки admin UI на русском;
- decision-log обновлён, если решение архитектурно значимое.
