# Chat guide placement + soft-status semantics

## Когда пригодилось

Во втором проходе по Hermes Web MVP пользователь уточнил два UX-правила:

1. Информационная плашка `Как работать / Внимание` не должна теряться в чате и не должна лечиться `sticky`-логикой внутри ленты.
2. Статусы `не активен / удалён` для пользователей и табличных справочников должны влиять на новые выборы, но не ломать уже сохранённые значения.

## Практический вывод

### 1. Постоянная справка по чатам

Если подсказка должна быть всегда под рукой, её место — рядом с переключателем экранов (`Чаты / Задачи / Управление`) или в topbar, а не над сообщениями.

Почему:
- скролл чата и скролл экрана часто живут в разных контейнерах;
- `sticky` внутри feed даёт нестабильный UX и сложнее в отладке;
- topbar-плашка явно относится к режиму экрана, а не к конкретному сообщению.

### 2. Soft-statuses

Рекомендуемая модель:
- `active` — можно логиниться / выбирать / назначать;
- `inactive` — нельзя заново выбирать и использовать в новых назначениях, но старые ссылки сохраняются и помечаются;
- `deleted` — также исключается из новых выборов и логина, но старые исторические связи не должны тихо исчезать из форм/detail.

## UI-паттерн для select

Для reference/user select нужен режим `preserve historical inactive value`:
- базовый options-list строится только из активных записей;
- если текущее значение формы уже указывает на неактивный элемент, этот элемент временно подмешивается в options;
- подпись должна явно маркировать состояние: `· не активно` или `· удалён`.

Это позволяет одновременно сохранить историческую целостность и не допустить новых выборов в выключенные сущности.

## Что обязательно проверить

- login заблокирован для `inactive/deleted` пользователей;
- user options в jobs/access/select не показывают `inactive/deleted` как новые варианты;
- existing entity/detail-form по-прежнему отображает уже сохранённый неактивный reference/user value;
- таблицы admin UI показывают статус отдельной колонкой, а не прячут его в неявную логику.
