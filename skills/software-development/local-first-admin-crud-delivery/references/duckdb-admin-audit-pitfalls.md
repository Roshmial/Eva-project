# DuckDB и admin CRUD: практические заметки

Краткая выжимка из реальной доработки local-first admin-контура.

## 1. `GROUP BY` после добавления новых колонок

Если в сущность добавили `version`, `created_at`, `updated_at` или другие новые поля, нужно проверить не только list query, но и helper-запросы, вызываемые после `POST/PATCH`.

Типовая ловушка:

- `GET /admin/users` уже починили;
- `POST /admin/users` всё ещё падает;
- причина в том, что после записи вызывается `get_user_with_stats()`, где `SELECT` уже расширен, а `GROUP BY` — нет.

Практическое правило: после добавления неагрегированной колонки ищи все SQL-блоки по сущности, где есть `GROUP BY`, а не только самый очевидный endpoint.

## 2. Миграции DuckDB с `ADD COLUMN`

DuckDB может не принять `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...`.

Устойчивый путь:

1. попробовать добавить колонку как есть;
2. при ошибке добавить без ограничения;
3. заполнить `NULL` через `UPDATE`;
4. затем уже использовать новую колонку в runtime-логике.

Важно: считать миграцию завершённой только после реального рестарта backend и проверки, что новая схема видна приложению.

## 3. Что обязательно проверять живьём

Для admin users:

- login;
- list;
- create;
- update;
- history;
- рост `version`;
- сохранение `assistant_profile.about_user`;
- запись в `user_change_log`.

Для reference data:

- list;
- create item;
- update item;
- history;
- рост `version`;
- запись в `reference_item_change_log`.

## 4. Несовпадение update-ответа и фактической версии в БД

Возможен сценарий:

- `PATCH /admin/reference-data/...` вернул элемент с прежней `version`;
- `history` уже содержит `update`;
- прямой запрос к БД показывает, что `version` реально выросла.

Практическая интерпретация:

- сначала считать это проблемой возвратного payload или read-after-write consistency;
- не объявлять поломанными versioning и audit trail, пока не проверены история и фактическая строка в БД;
- после этого уже отдельно смотреть сериализацию, refresh dataset или источник строки, из которого собирается update-ответ.

## 5. Что не считать доказательством готовности

Недостаточно:

- успешного `py_compile` / `node --check`;
- успешного `GET`, если `POST/PATCH` не прогнаны;
- наличия новых таблиц без проверки, что они реально наполняются.

## 5. Пользовательский контур для Миши

Если работа касается admin UI для Миши:

- фронтовые строки должны быть на русском;
- остаточные англоязычные подписи, ошибки и служебные названия надо дочищать до финального прохода;
- не выдавать статус "готово", пока живая проверка create/update/history не завершена.
