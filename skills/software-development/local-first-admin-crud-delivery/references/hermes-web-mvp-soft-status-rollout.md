# Hermes Web MVP: chat guide + soft-status rollout

Краткий session-level конспект для повторного захода в похожую задачу.

## Когда пригодится

Когда в local-first admin/web UI нужно одновременно:
- вынести постоянную подсказку из прокручиваемой ленты в верхний контур экрана;
- вернуть soft-statuses `active / inactive / deleted` не только пользователям, но и табличным справочникам;
- сохранить исторически выбранные inactive/deleted значения в формах, но убрать их из новых выборов.

## Практический паттерн

### 1. Постоянная chat-плашка

Если пользователь хочет, чтобы `Как работать` / `Внимание` были всегда доступны, не держать их sticky внутри scrollable chat-feed.

Лучший паттерн:
- вынести блок рядом с верхними вкладками/topbar;
- старый intro-блок в теле чата скрыть или оставить только как резервный контейнер без sticky-поведения;
- логику показа собирать отдельной функцией рендера верхнего баннера, которая вызывается при переключении screen/tab.

Почему это устойчивее:
- не зависит от реального scroll-host (`body` vs `.content`);
- не конфликтует с кнопкой `Вверх`;
- не создаёт ложного ощущения, что help-блок — часть переписки.

### 2. Soft-statuses для users и references

Если вводится тройка состояний `active / inactive / deleted`, протягивать её нужно насквозь:
- схема БД;
- сериализация API;
- формы create/edit;
- таблицы/list/detail;
- auth/login;
- options/selects в зависимых сценариях.

Минимальный backend-пакет:
- `is_active` как operational flag;
- `deleted_at` как маркер soft-delete;
- вычисляемый `status` в API response;
- нормализатор входного payload, который понимает и новый `status`, и legacy-поля.

Минимальный frontend-пакет:
- select статуса с тремя значениями;
- единый humanizer для надписей статуса;
- row/table badges и detail labels из общего helper, а не вшитые строки в разных местах.

### 3. Preserved selection pattern

Правило для reference-driven select:
- в новые назначения показывать только активные и неудалённые записи;
- если текущее сохранённое значение уже inactive/deleted, временно подмешивать его обратно в options;
- явно маркировать такие значения как `· не активно` или `· удалено`.

Это защищает от двух плохих исходов:
- silent data loss, когда старое значение просто исчезает из формы;
- повторного назначения невалидного значения новым объектам.

### 4. Что обязательно проверить в runtime

После правок нельзя ограничиваться diff/patch. Нужен живой проход:
- верхняя плашка реально видна рядом с вкладками;
- в теле чата нет визуального дубля;
- кнопка `Вверх` появляется по простому и предсказуемому порогу;
- create/edit справочника открывается через overlay;
- inactive/deleted корректно сохраняются;
- старое inactive/deleted значение видно в форме, но не предлагается как новый выбор.

## Частые ошибки

- Чинить доступность help-блока через всё более сложный `sticky`, вместо переноса в topbar.
- Вернуть `status` только в user form, забыв list/detail/login/selects.
- Поддержать `deleted` во frontend, но не довести `deleted_at` и сериализацию backend.
- Фильтровать inactive/deleted из select без preserved fallback для уже сохранённых данных.
- Размазывать отображение статусов по коду без общего helper — потом часть экранов остаётся в legacy-терминах.

## Рекомендуемый порядок добивки, если проход оборвался

1. Закончить backend write-path (`create/update`) для reference items.
2. Довести frontend humanizer + status labels + save flow.
3. Прогнать syntax/smoke.
4. Только после этого делать browser acceptance по chat/topbar/reference flows.
