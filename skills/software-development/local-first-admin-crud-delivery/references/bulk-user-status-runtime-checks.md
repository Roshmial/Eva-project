# Bulk user status runtime checks

Краткий session-level конспект для задач, где в local-first admin UI добавляют массовые действия по пользователям.

## Что оказалось полезным

- Массовый выбор на фронте лучше держать state-driven, а не как набор несвязанных DOM checkbox'ов. Иначе после rerender легко теряется согласованность между строками, select-all и toolbar actions.
- Для bulk-операций по users лучше иметь отдельный backend route (`/api/admin/users/bulk-status`), чем пытаться многократно вызывать одиночный update-route из UI. Так проще тестировать guards, историю и versioning.
- Историю bulk-действий полезно писать отдельными change types (`bulk_inactivate`, `bulk_delete`), чтобы audit trail не выглядел как серия неразличимых одиночных update.

## Диагностический паттерн

Если новый bulk endpoint уже есть в коде и smoke проходит, но живая проверка через продуктовый URL возвращает `404`:

1. не объявляй route сломанным сразу;
2. проверь, нет ли proxy-контура (`frontend /api` -> backend);
3. проверь, какой процесс реально слушает backend-порт;
4. исключи stale backend после неполного рестарта;
5. только потом возвращайся к коду маршрута.

## Практический приём для live-smoke

Для повторяемой live-проверки создавай тестовых пользователей с уникальным суффиксом во всех идентификаторах (`email`, `name`). Это убирает ложные `409 Conflict` от прошлых прогонов и даёт чистый сигнал по bulk-механике.

## Что включать в приёмку

- create 2+ test users;
- bulk inactive;
- readback статусов и версий;
- при необходимости bulk delete для части выборки;
- проверка history/change types;
- защита последнего активного администратора остаётся серверной, а не только UI-ограничением.
