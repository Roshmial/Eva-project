# Profile tabs, thread recipients, and safe patching

Контекст: local-first web MVP на ванильных `index.html + app.js`, где пользователь дал точные UI/UX-требования, а экран уже был частично связан со старой логикой.

## Что оказалось полезным

1. Жёсткие пользовательские требования лучше сразу переводить в DOM-контракт
- не «улучшаем примерно», а фиксируем буквально:
  - ровно 3 вкладки профиля;
  - таблица, а не карточки;
  - warning-плашка на общем экране чатов, до открытия конкретного диалога;
  - кнопка `Вверх` на длинных экранах.
- после этого составлять checklist: HTML ids/classes, copy, render-функции, state, event listeners, smoke.

2. Для больших экранов безопаснее идти через адресные патчи
- сначала перечитать нужные блоки файла;
- потом править секциями;
- не делать большой rewrite поверх частично прочитанного `index.html`, если экран уже живой и связан множеством `id` и `data-*`.

3. В chat/job UX допустим thread-first frontend поверх user-owned backend
- если job-чаты в backend фактически принадлежат пользователям, но пользователь мыслит сущностями «чаты/контуры», frontend может давать выбор thread/чата;
- backend затем резолвит owner этого thread в user-oriented delivery/ACL модель;
- такой компромисс лучше прямого возврата к списку пользователей в UI.

4. Частичный HTML-pass нельзя считать почти завершённой задачей
- признаки незавершённости:
  - вкладки в HTML уже новые, а JS всё ещё переключает старые секции;
  - контейнер под таблицу уже есть, а `render...()` по-прежнему рисует список;
  - placeholder блока вернули в HTML, а `render...()` его не наполняет;
  - copy уже chat-based, а summary/payload logic ещё user-based.

## Практический порядок следующего прохода

1. Разметка и copy.
2. Синхронизация `state` и `set*Section`.
3. Синхронизация `render*`-функций.
4. Обработчики (`data-*`, scroll-to-top, tab switching).
5. Payload/contracts (`collect...`, summary helpers, recipients mapping).
6. Только потом smoke/runtime.

## На что смотреть в подобных задачах

- нет ли рассинхрона между `index.html` и `app.js`;
- не остались ли старые `id`, старые тексты и старая терминология после смены IA;
- не превратился ли UI-pass в «визуально похоже, но логика старая»;
- не пытается ли интерфейс думать users, когда пользователь работает категориями chats/threads.
