# Daily pipeline improvement roadmap

Краткая выжимка из сессии 2026-05-28: что улучшать в ежедневном Telegram monitoring pipeline без перестройки стека и без ухода от local-first подхода.

## Уже подтверждено как базовая архитектура

- Инкрементальный сбор через `tg-since-id-it_consulting.json`.
- Безопасный порядок: API -> raw log -> `summary_input` -> JSONL archive -> update since.
- Пользовательская статистика и production-дайджест считаются только по непустым сообщениям.
- Post с `media_type` и текстом в `message`/`raw_text` — это не media-only, а media + caption; он должен входить в `summary_input`.
- Настоящие media-only сообщения пока не включаются в production-дайджест и не влияют на основную статистику.

## Рекомендуемый порядок улучшений

### Этап 1. Повысить надежность без изменения архитектуры

1. Добавить fail-fast / health-check проверки после каждого шага:
   - API отвечает на `localhost:8001`;
   - создан новый raw log;
   - создан новый `*_summary_input.json`;
   - `non_empty_messages` совпадает с длиной `messages`;
   - создан CSV;
   - используется свежий файл, а не вчерашний.
2. Убрать production-зависимость от разового ручного скрипта с жестко зашитыми путями и ID сообщений.
3. Сделать универсальный генератор CSV:
   - вход: путь к последнему `*_summary_input.json`;
   - выход: CSV в `/home/hermes/.hermes/cache/documents/`;
   - без хардкода на конкретный snapshot.

### Этап 2. Развести ответственность внутри Hermes

1. Логически разделить pipeline на два шага, даже если оба живут в Hermes:
   - collect job: только `ensure_api.py` + `monitor_client.py` + проверка артефактов;
   - digest job: читает последний `summary_input`, делает дайджест и CSV.
2. Это упрощает повторный запуск дайджеста без повторного сбора и делает диагностику ошибок прозрачнее.

### Этап 3. Повысить качество отбора

1. Добавить rule-based preclassification перед агентским reasoning:
   - `исследование`, `опрос`, `benchmark` -> чаще `исследование`/`аналитика`;
   - `конференция`, `форум`, `саммит`, `выступление` -> `мероприятие`;
   - `внедрили`, `проект`, `для клиента`, `автоматизация` -> `кейс`.
2. Спорные случаи оставлять агенту; новые типы не создавать.
3. Добавить мягкую дедупликацию по теме, а не только по URL:
   - похожие события,
   - общие external links,
   - одинаковая компания/конференция/инфоповод.
4. Если новость дублируется в нескольких каналах, не удалять ее слепо, а понижать приоритет дублей.

### Этап 4. Операционный QA поверх daily run

1. Отдельный weekly QA/reporting слой может собирать:
   - число запусков;
   - число запусков без новых сообщений;
   - среднее число непустых сообщений;
   - долю `требует уточнения`;
   - каналы с высоким шумом и каналы с высокой полезностью.
2. Это помогает улучшать мониторинг по фактам, а не по ощущениям.

## Что пока не вносить в production-контур

### Media-only через vision/OCR

Это признано потенциально полезным направлением, но только как отдельный experimental layer.

Почему не стоит смешивать это с основным дайджестом прямо сейчас:
- OCR/vision может ошибаться;
- preview может не покрывать весь смысл поста или карусели;
- надежность такого источника ниже обычного текстового сообщения.

Если возвращаться к теме позже, правильный порядок такой:
1. Взять выборку media-only сообщений.
2. Замерить качество извлечения смысла.
3. Только после этого решать, нужен ли отдельный `media_only_experimental.json/csv` слой.

## Практический приоритет

Лучший баланс `цена -> эффект`:
1. универсальный CSV generator;
2. health-check / fail-fast;
3. разделение collect/digest;
4. rule-based classification + soft dedupe;
5. weekly QA;
6. experimental media-only layer — только потом и отдельно.
