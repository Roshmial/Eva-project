# Telegram IT-consulting monitor: архив, ссылки и grounded-сводки

## Контекст

В ходе доработки ежедневного мониторинга Telegram-каналов пользователь уточнил требования к хранению данных, ссылкам на источники и стилю итоговой сводки.

## Зафиксированные решения

1. Дополняемый архив

- Все записи, которые пришли из Telegram API, сохранять в `archive/telegram_messages.jsonl`.
- Формат: JSONL, одна строка = один JSON-объект сообщения.
- Архив должен включать все записи, включая пустые и media-only.
- `raw_logs/` остаётся для снимков конкретных запусков.
- `summary_input` используется только как подготовленная выборка для анализа.

2. Пустые/media-only сообщения

- В архив: сохранять.
- В `since.json`: учитывать при обновлении состояния, чтобы не получать повторно.
- В аналитическую выборку и сводку: не включать, если нет полезного текста.

3. Порядок сохранения

Безопасная последовательность в `collect()`:

- получить данные из API;
- сохранить raw log;
- подготовить и сохранить `summary_input`;
- добавить все сообщения в `archive/telegram_messages.jsonl`;
- только после успешного сохранения обновить `since.json`.

4. Ссылки на оригиналы

Каждая запись для анализа должна иметь поле:

`original_url = https://t.me/<channel>/<message_id>`

Где `<channel>` берётся из `chat`, а `<message_id>` из `id`. Если API уже вернул `original_url`, клиент использует его; иначе строит fallback сам.

5. Ссылки внутри сообщений

Желательный уровень API:

- извлекать скрытые ссылки из `MessageEntityTextUrl`;
- извлекать видимые ссылки из `MessageEntityUrl`;
- возвращать их в поле `external_links`.

Fallback на стороне клиента:

- регулярным выражением извлекать обычные `http://` и `https://` URL из текстового поля.

Ограничение: старые raw logs, полученные до доработки API, могут не содержать скрытые ссылки из Telegram entities. Их нельзя восстановить из одного только сохранённого текста.

6. Формат боевой ежедневной сводки

Боевой формат должен включать:

- канал;
- дата;
- оригинальная ссылка;
- тема/заголовок;
- краткая суть строго по тексту сообщения;
- ссылки из сообщения, если есть;
- категория: исследование / мероприятие / кейс / HR / стратегия / финансы / продукт / другое.

Блок `Почему важно` не включать в боевую ежедневную сводку. Он допустим только в тестовой выборке или при отдельной просьбе пользователя.

7. Анти-галлюцинационные правила

- Не объединять несколько сообщений в один общий "вывод рынка", если это не следует явно из источников.
- Не добавлять причинно-следственные связи от себя.
- Не писать "рынок движется", "компании массово переходят", "это подтверждает тренд", если это не сказано или строго не подтверждено текстом.
- Каждый пункт должен иметь ссылку на исходное сообщение.
- Числа, даты, имена, компании, спикеры и утверждения брать только из текста сообщения.
- Если интерпретация всё же нужна, явно отделять её от факта; для боевого режима предпочтительно не добавлять интерпретации.

8. Формат отображения ссылок и содержания

- В сводке использовать формулировку `Краткое содержание`, а не `Суть по сообщению`.
- Блок `Ссылки из сообщения` показывать только если `external_links` непустой.
- Если ссылок из сообщения нет, не добавлять отдельный блок и не писать заглушки вроде `ссылок нет`.

9. Дополнительные поля Telegram API

API стоит извлекать и сохранять дополнительные поля Telethon, если они реально доступны:

- `views` — просмотры;
- `forwards` — количество пересылок;
- `replies_count` — количество ответов/комментариев;
- `comments_enabled` — признак включённых комментариев;
- `reactions` — реакции с количеством, в компактном виде `{reaction, count}`;
- `edit_date` — дата редактирования сообщения;
- `grouped_id` — идентификатор группы/альбома медиа;
- `post_author` — автор поста, если Telegram его отдаёт;
- `media_type` — тип медиа на уровне Telethon-класса.

Правило использования: метрики показывать в сводке только если они непустые и реально пришли из API. Не делать выводов о важности новости только из отсутствующих или неполных метрик.

10. Безопасная техническая последовательность

В `monitor_client.py` порядок в `collect()` должен оставаться таким:

- получить данные из API;
- сохранить raw log;
- создать `summary_input` только из непустых текстовых сообщений;
- append всех сообщений в `archive/telegram_messages.jsonl`, включая пустые/media-only;
- только после успешного сохранения обновить `since.json`.

## Практическая проверка перед cron

Перед созданием или запуском Hermes cronjob проверить:

- `python -m py_compile app.py monitor_client.py`;
- API отдаёт `original_url`, `external_links` и, если доступны, дополнительные метрики (`views`, `forwards`, `reactions`, `replies_count`, `media_type` и т.п.);
- `monitor_client.py` пишет raw log, `summary_input` и append в JSONL-архив;
- `since.json` обновляется после успешного сохранения;
- тестовая сводка строится из `summary_input`, а не из догадок агента.
