# Разовая историческая выгрузка Telegram API и аналитика по каналам

Справка фиксирует проверенный паттерн для ретроспективных выгрузок по Telegram-каналам, когда нужно временно снять `since/id` ограничения, но не нарушить ежедневный мониторинг.

## Когда применять

Использовать, если пользователь просит:

- выгрузить сообщения с конкретной даты;
- снять ограничения по message id;
- сделать аналитику по всем каналам за прошлый период;
- сравнить активность каналов, темы, услуги, проекты, мероприятия, исследования и партнерства.

Не использовать как замену ежедневному мониторингу. Это отдельный one-off workflow.

## Главный принцип

Постоянный мониторинг должен остаться неизменным:

- не менять `channels.yml` без явной причины;
- не сбрасывать и не перепроектировать `tg-since-id-it_consulting.json`;
- не использовать эксперимент для обновления daily since-state;
- не отключать существующий Hermes cron job.

Для ретроспективы создаётся отдельный config, например:

`channels_experiment_YYYYMMDD.yml`

В нём задаются:

- `date_from` — старт периода;
- `limit_per_channel` — верхний предел на канал;
- `global_limit` — общий предохранитель;
- тот же профиль и список каналов, если пользователь не просит изменить состав.

## API-вызов

Вызов должен идти через локальный `/export` без параметра `since`, например:

`http://localhost:8001/export?profile=profile_1&config=experiment_YYYYMMDD`

Если передать `since`, ретроспектива снова будет ограничена state-файлом. Для one-off исторической выгрузки `since` не передавать.

## Артефакты, которые стоит сохранять

Минимальный набор:

1. Полный raw export:
   `raw_logs/experiment_YYYYMMDD_full_export.json`

2. Общий evidence-файл:
   `raw_logs/experiment_YYYYMMDD_channel_evidence.md`

3. Для больших выгрузок — per-channel evidence:
   `raw_logs/experiment_channel_evidence/<channel>.md`

4. Итоговая аналитика:
   `telegram_channel_analytics_from_YYYY-MM-DD.md`

## Методика анализа

Для каждого канала полезная структура:

- количество сообщений за период;
- потенциальная целевая аудитория;
- ключевые темы, желательно не более 8;
- исследования / обзоры / аналитические материалы;
- публичные мероприятия;
- видимые услуги и направления консалтинга / ИТ;
- проекты и внедрения;
- партнерства и сотрудничества;
- ограничения анализа.

Media-only и пустые посты учитывать в общем количестве, но не использовать для тематической классификации, если нет текста.

Использовать `original_url`, если он есть. В отчёте важно сохранять проверяемость выводов: утверждения должны опираться на текст сообщений или ссылки из выгрузки.

## Специальный pitfall по партнерствам

В консалтинговых каналах слово «Партнер» часто означает должность человека. Это не является партнерством компаний.

Партнерством считать только случаи, где из текста видно сотрудничество организаций, интеграция, совместный проект, альянс, совместное мероприятие или договоренность между компаниями/институтами.

Если таких фактов нет, писать: «в выгрузке не выявлено».

## Как отчитываться пользователю

Короткий финальный ответ должен содержать:

- что эксперимент выполнен;
- что выгрузка была без `since/id`, но только разово;
- что ежедневный мониторинг и `tg-since-id-it_consulting.json` не изменялись;
- сколько сообщений выгружено;
- путь к итоговому `.md` отчёту;
- путь к raw export;
- краткое распределение сообщений по каналам;
- ограничения, если часть анализа была частично автоматической или требовала дальнейшей QA-проверки.

## Проверенный пример 2026-05-27

Для выгрузки с 2026-04-26 был создан отдельный config `channels_experiment_20260426.yml`, API вызван без `since`, результат сохранён в raw export, затем подготовлен итоговый markdown-отчёт по каналам.

Этот пример полезен как шаблон последовательности, но конкретные количества сообщений и состав каналов не считать универсальными правилами.
